### 关键认知（拆分自举编译器的核心难点）
- **语言禁止循环 import（`T_IMPORT_CYCLE`）** ⇒ 模块图必须是 DAG，单体里的双向引用必须靠「把符号搬到最早引用它的模块」消解。
- **⚠ 跨模块调用要类型正确，调用方必须 import 被调方**：否则 sema 找不到被调函数签名 → 返回类型错判（实测 `bool` 被当 `i64`）→ clang 报 IR 类型不匹配 / 链接期 undefined。
  曾试图在 LLVM 后端加 `llfn_bare` 裸名回退来绕过（只修了调用标签），**不够** —— 类型推断仍错。已全部回退，正解只有搬迁。
- **⚠ 未定义的「变量」是硬错误，未定义的「函数」只降级为 `; UNSUPPORTED call` 警告并静默产出坏 IR** ⇒ 编译器自己兜不住，必须静态扫。首轮构建只报 9 个错，实际有 17 处反向引用。
- 拆分方向不可拍脑袋：实测 `codegen_c → codegen_ll` 顺序有 17 处反向引用，交换成 `codegen_ll → codegen_c` 反而涨到 36 处。先量化再动手。

### 方法论（可复用）
1. `tmp/dagcheck.py` 静态求「反向引用」全集（字符串/注释感知的分词 + 顶层声明表 + 引用表）。
2. `tmp/fixdag.py` 按「搬到最早引用者」迭代到不动点 —— 3 轮 26 次搬迁收敛，无雪崩。
3. `tmp/verify_split.py` 证明拆分是**纯置换**：拆分文件去 import 后的非空行多重集 == 单体。曾靠它抓到手工搬迁把 `tdf_pstart/pcount/params` 的 `[]i64` 写成 `i64` 的隐蔽 bug。
4. 三重等价验证：`tc.exe` 与 `tc_split.exe` 对同一输入（单体源 / 拆分源）产出的 `.ll` md5 全同；且 `split_by_tc == split_by_split` ⇒ 一代即达不动点。

### ✅ 已修：ir_snapshot 工作目录假死（`tools/ir_snapshot.mjs`）
- **症状**：gate「产物快照比对」步骤 8 分钟硬超时被 SIGKILL，还会因此误报 WARN「0 处差异」。独立跑却只要 49s。
- **根因**：固定目录 `out/dbg/irsnap` ⇒ 每轮必须先清理上一轮残留。Windows 上刚写出的 `.ll/.c` 被杀软/索引器持有数分钟，`rmSync` 在 EPERM 上反复重试；**连 `renameSync` 都会因目录内有打开的文件而失败**，同步兜底一样卡死。实测两轮都恰好卡在同样的 32 个 `.ll` 上。
- **解法（根除依赖，而非加重试）**：工作目录改为**每轮独占**的 `out/dbg/irsnap.<pid>` —— 不存在残留，就不需要在关键路径上清理。收尾与启动扫尾都用 `spawn(detached+unref)` 的 `rd /s /q` 后台删除，本进程不等待。
- **效果**：gate L0 从 515s（含假 WARN）降到 **72.4s 全绿**；快照步骤 480s → 29.2s。
