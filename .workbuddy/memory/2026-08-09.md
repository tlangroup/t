## 修复：编译器静默接受未定义类型名（用户报 vi32）

用户报：`is_odd fn(v:vi32) bool { return v % 2 == 0; }` 编译通过，未提示 `vi32` 未定义。

### 根因
`sema.tc` 的三个类型解析入口对「命名类型」分支从不校验名字是否已声明，直接 `return Named/unknown` 静默放过：
- `resolve_ti` named 分支（~688）
- `resolve_type_desc` named 分支（~7407，GEN:td_rnamed）
- `deser_type_of` ident 分支（~7265）

### 修复（src/sema.tc）
- 三处都改报 `T_UNKNOWN_TYPE`（顺序：`tm_get` → `sym_lookup(global_scope)` → `menv_find` 跳过 meta 已绑定 → `gen_tparam_has` 跳过泛型类型参数 → `fc_err`）。
- 新增全局 `g_gen_tparams: []string` + helper `gen_tparam_has`，用于识别「泛型类型参数」（comptime/meta T: type）而非未定义类型。
- `register_decl` 的 FuncDecl 分支：若为泛型，临时把 comptime/meta 类型参数名填入 `g_gen_tparams`，解析完返回类型/参数类型后还原（避免跨函数泄漏）。
- `deser_type_of` ident 分支报错后，`T_FID_DESERIALIZE_NEEDS_TYPE` 现场（~2448）改为仅 `return Unknown`（避免双重报错）。

### 关键坑（泛型假阳性）
- 初版只在 `resolve_ti/resolve_type_desc/deser_type_of` 加报错 → 泛型 `id fn(comptime T: type, x: T) T` 误报 `T_UNKNOWN_TYPE`。
- 原因：`check_decl` 对泛型 `return` 跳过 `check_func_decl`（sema.tc:3494），但 `register_decl` 仍无条件对模板的返回/参数类型调 `resolve_ti` → 模板定义期 `T` 尚未绑定 → 误报。
- ⚠ **`check_func_decl` 的形参登记循环对泛型函数永不执行**（被 3494 挡在门外），在那里登记 T 是死代码，不要走这条路。
- 正解：`g_gen_tparams` 在 `register_decl` 期识别模板类型参数。

## 修复：REPL 定义 bool 返回的子句组函数 → clang 链接失败

用户报：REPL 输入 `is_odd fn(v:u32) bool { return (v%2) == 0; }`（会话中同名已定义过一次触发 `desugar_func_clauses` 合并）→ 报错 `out\repl\repl_exe.ll: error: '%t5' defined with type 'i8' but expected 'i64'`，`clang link failed`。

### 根因
- 同名多定义 / 含模式参数的函数经 `desugar_func_clauses`→`fc_merge` 脱糖成 `return match(__p0){...}`（`parse.tc:2446`，参数改名 `__p0`）。
- `codegen_ll.tc` 的 `ll_etd`（L600）对 `match` 节点无专门分支，落到默认 `expr_type_desc(e)`；脱糖合成的 match 节点在 sema 之后产生、`.td` 未设 → 返回默认 `i64`。

- `return` 处 `ll_cast_v(v, ll_etd(match), bool)` 用 `i64` 做真值化 → `icmp ne i64 %t8, 0`，而 `%t8` 实是 `i8` → LLVM 类型校验失败。

### 修复（src/codegen_ll.tc，~L655）
- `ll_etd` 增加 `match` 分支：`return ll_etd(match_first_body(e));`（与 `emit_lle` 的 `mv_rtd` 完全一致）。
- C 后端（`codegen_c.tc:1355`）本就用 `expr_type_desc(match_first_body(e))`，无此 bug。

## 新增诊断：W_OVERFLOW_LITERAL（整数字面量超出目标类型范围）

用户报：REPL 里 `is_odd fn(v:i8) bool`，调 `is_odd(258)` 返回 `true` 且**一个警告都没有**。

### 根因（两层）
1. `can_cast`（sema.tc:272-311）第 290-291 行 `if (is_int_ti(fi) && is_int_ti(ti2)) { return true; }` —— **任意整数↔整数一律放行**，`258`(u16) → `i8` 静默按模截断成 `2`。
2. `overflow_literal` 这个警告名**注册了但从未发射**：`vv_warnings()`(6729) 列了它、`is_valid_warning`(6705) 认它，但全库 grep 无任何 `diag_new("overflow_literal"|...)` —— 纯占位。
3. 字面量类型按量级推断（sema.tc:2217-2229，选能装下的最小无符号类型），所以 `258` 静态类型是 `u16`，溢出只在**收窄点**才可见。

### 实现（src/sema.tc）
- `u64_pow2(bits)`：循环乘法算 2^bits（无 `u64_shl` 可用；64 位时 u64 回绕为 0 = max+1，正好当上界）。
- `intlit_overflow_warn fn(e: i64, target: i64) void`：
  - 只对 `tip_kind==Scalar` 且 `is_int_name` 且非 bool 的目标生效；
  - 剥 `paren`；识别负号形态 —— **`-257` 的 AST 是 `kind=="unary" && sa=="-"`，`na` 指向 `int` 子节点**（不是独立 `neg` kind）；
  - 上界：无符号 `lim=2^bits`、有符号 `lim=2^(bits-1)`；正数超 `lim-1` 报，负数无符号一律报、有符号超 `lim` 报；
  - `diag_new("W_OVERFLOW_LITERAL", "warning", msg, n_file/n_line/n_col(lit_id), ...)`。⚠ `diag_sev()` 对未注册码返回 `""`，**必须显式传 `"warning"`**（照抄 `T_ANNOTATION_UNKNOWN` 的写法）。
- 接线**四个收窄点**：`check_call_args`(~471，拿到 `pt` 后)、`var_decl` 初始化(~3085)、`assignment`(~3221)、`return`(~3211，对 `cur_ret`)。
- 新增 `has_warnings()` / `print_warn_summary()`（在 `has_errors` 之后），后者按 `warning: <msg> (<file>:<l>:<c>)` 打到 **stdout**。

### 让警告在 build / REPL 里可见
- `src/tc.tc`：`build`/`emit-ll`/`run` 分支里，`has_errors()` 早退之后加 `if (has_warnings()) { print_warn_summary(); }`。
- `src/tc.tc`：`Generated:`(L322) 与 `Built:`(L385) 由 `print` 改 **`eprint`** —— 成功构建时 stdout 只剩警告行。
- `src/repl.tc`：`repl_build` 把 `2>&1` 改成 `2> "<rep_dir>/build.err"`（stdout=build.log 只装警告，clang 噪声进 build.err）；新增 `repl_surface_warnings(rep_dir)` 读 build.log 非空则 `eprint`；三条 REPL 路径（声明式 ~208 / 值形态 ~217 / 语句形态 ~222）构建成功后都调它。
  - 原来 REPL 只在**构建失败**时才回显 build.log，`tc build` 也只在 `has_errors()` 时 `print_json()` → 警告在 REPL 里 100% 不可见。

### 踩坑
- 第一版 `-257` 警告定位到 L1C1 且文案丢负号：`lit_id = nn.na` 写在 `nn` 被覆写成操作数**之后**，取到的是操作数的 `na`（类型节点 id / -1）。修法：`var opid: i64 = nn.na;` **先存后换**，文案 `neg` 时前缀 `"-"`。
- `sb_cat6` 最多 6 实参，`print_warn_summary` 一次传 9 个 → `T_CALL_ARITY`。改成 `sb_cat6(...)` + `sb_cat3(...)` 链式拼。

### 验证
- `tc check tmp/ovf_final.tc` → 4 warnings 0 errors：`var a:i8=258`、`var c:u8=300`、`is_odd(258)`、`is_odd(-257)`；`var b:i8=127`（在范围内）与 `is_odd(2)` **无警告**。

## 修复：类型别名成员访问段错误（LLVM 后端）

`tests/conformance/pass/p43_forward_type_ref.tc` 编译干净但运行期 SIGSEGV（exit 139）。二分定位：**唯一崩溃场景是经 typealias 访问成员**（`Box Holder;` 后 `b.n` / `h.n`），与是否前向引用无关（非前向的 `Box Holder;`（Holder 在前）同样崩）。

### 根因
`codegen_ll.tc` `ll_addr` 的 `member` 分支（~851）：对象类型 `obt.name=="Box"`，`llt_find("Box")` 的 `llt_kinds[ti]=="alias"`（既非 `struct` 也非 `union`）→ 两个分支都不进 → `return "null"`。生成的 GEP 变成 `store i64 5, ptr null` / `load i64, ptr null` → 运行期解空指针崩溃。变量 `h` 本身分配正确（`alloca %st.Holder`），但成员 GEP 没解析别名到底层聚合类型，与分配端不一致。

### 修复（src/codegen_ll.tc）
- 新增 `ll_alias_base_name(name) string`：沿 `llt_find`→`llt_atd`（`tds[utd].name`）链式解别名到最底层具名类型（guard<64 防环）。
- `ll_addr` `member` 分支先 `base = ll_alias_base_name(obt.name)`，之后 GEP 用 `%st.<base>`、`llsf_find(base, n.sa)`，与变量分配的底层类型一致。
- 非别名类型 `ll_alias_base_name` 原样返回 → 既有行为零变化。

### 验证

- **`src/sema.tc`**：`desugar_format_call` 消费 `!conv`，按值类型选 `sb_append_fmt_{str,int,uint}_conv`（仅在字符串上 `!r/!a/!j`、整数上 `!c/!p` 时启用，其余走原 `sb_append_fmt_*`）；类型不匹配报 `T_FMT_CONV_TYPE`。
- **`runtime/t_runtime.{c,h}` + `t_shim_ll.c`**：`fmt_str_convert` 实现 `!s/!r/!a/!j`，`!c` 整数码点→UTF-8（越界 U+FFFD），`!p` → `0x…`（负数 `-0x…`）。
- **双后端**（`codegen_c.tc` `td_calls`+emit / `codegen_ll.tc` emit+`llph` declare）：3 个新内建的六处注册全齐。

### 踩坑
1. **lexer off-by-one**：短式扫描起点 `fsi = i + 1` 落在开头引号上 → 立即当闭合 → 报 `unterminated string literal`。改 `i + 2` / `col + 2`（长式 `f"""` 的 `i + 4` 本就正确）。二分法逐行隔离定位。
2. **`!a` 输出错**：原对非 ASCII 直接按字节 `fmt_esc_hex` → `\xe4\xb8\xad`。改为 UTF-8 解码 + 新 helper `fmt_esc_u_cp`（`\uXXXX`/`\UXXXXXXXX`），`中文` → `\u4e2d\u6587`。顺带修 `fmt_utf8_cp` 边界判断笔误。
3. **`{!ok}` 被误判为转换字段**：conv 提取加 `fstr_prev_ends_expr` 判 `!` 前是否完结表达式；非法 conv 字母（如 `!z`）给清晰解析期错误。
4. **代码落进 GEN 区**：319 行 f-string 手写块原在 `>>> GEN:parser_rules ... <<<` 区间内（标 DO NOT EDIT），用 python 脚本整体前移到标记之前。⚠ 通用教训：手写新解析代码别落进 GEN 区。
5. **`t` 无三元 `?:`**（冒烟用例误用，与 f-string 无关）；入口是 `main_fn fn() i32 @main`；`flag` 是保留字（用例变量名改 `okv`）。
6. **`{-255!p}` → `0x1`**：整数字面量按量级推 `u8`，`-255` 求值即 `1`——**语言既有语义，非 f-string bug**，未改（真实 `i64` 变量 `!p` 正确输出 `-0xff`）。
