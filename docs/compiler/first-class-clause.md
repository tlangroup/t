## 0. 一句话定位

> **Clause 是「携带未求值 AST 的编译期一等值」。**

它是**编译期相位内的真值**（可绑定、可传参、可作返回、可入数组、可参与并集），但这个相位的边界就是它的存在边界——**运行期不存在**（裁定 E，§4）。

它看起来是函数（`@clause(...)` 的调用形态），本质是 **AST 构造器（quote form）**：参数**整体不求值**，被原样捕获为语法树片断，再由 `match` 在编译器内部展开。它不是宏展开的文本替换，而是编译期一次真实的构造 → 传递 → 展开求值。

## 1. 核心裁定（为什么必须是这样）

### 1.1 为什么参数必须「整体未求值」（本次最硬的一条）

考虑带守卫的形态（**本次更正**：守卫由 `when` 关键字在参数表内引出，占独立一段，故是**五个段位**而非四个）：

```t
@clause(.pattern, n, when n > 0, n * 2)
  ①        ②     ③   ④    ⑤     ⑥
//  ① 子句类别（枚举成员）  ② pattern  ③ 守卫引导关键字  ④ 守卫表达式  ⑤ ret_exp（⑥=binding 引用）
```

注意末段 `ret_exp = n * 2` —— **`n` 是 pattern 绑定出来的名字**。若 `@clause` 按普通求值语义处理参数，则：

- 构造期内尚未进入任何 `match`，`n` 无任何绑定 → 报「未定义的标识符」；
- 即便强行先绑定，`ret_exp` 的语义也应是「在命中该臂时才求值」，而非「构造时求值一次」。

对比三种合法形态：

```t
@clause(.pattern, n,            n * 2)     // 无守卫：pattern=n, ret=n*2
@clause(.pattern, n, when n > 0, n * 2)    // 有守卫：`when` 引出，占独立段位
@clause(.pattern, _,            "other")   // 通配句型：pattern=_
```

⇒ **`when` 之所以必须显式写出**（而不是靠元数 4 vs 5 隐含）：guard 与 body 都是 `Expr`，二者在 AST 上无从区分；写不写 `when` 才是唯一可靠的判别位。它同时复用了既有 `match` 臂的语法直觉（`n when n > 0 => ...`），且与 `#1` 起形参折叠进守卫的既有铁律同源。

同理 `pattern_exp` 中的 `_`（通配占位）在 t 中根本**不是合法表达式**（`src/parse.tc:804` 只在模式位把 `"_"` 记号转成 `mk_ident("_")`；表达式位写裸 `_` 是解析错误）。

⇒ **裁定 A：`@clause(...)` 的 pattern / guard / body 三个位置是 AST 位置，不是值位置。** 解析期把子树原样挂上，`meta_eval_mbuiltin` 的 `clause` 分支**不得**对其调用 `meta_eval`。这一条取代了初稿里 `@//` 想表达的「未求值」语义——那个语义仍然成立，只是改由「按名特判的内建」承担，不需要新词法记号。

### 1.2 为什么 group 走数组、`++` 走 `++`

初稿设想并集用 `&&`。**裁定 B：改用既有的集合合并算子 `++`**，理由有三：

1. **`++` 已经是 t 的集合合并符**：`src/lex.tc:59` 产出 `PlusPlus`，注释原文「集合合并符 `++`（bitstr/Slice/String/... 合并，与数值 `+` 解耦；§15.6）」；`src/parse.tc:537-546` 的 `parse_concat` 已建立独立优先级层，产出 `binary("Concat", L, R)`。
2. **Array 分支的类型规则已经就位**：`src/sema.tc:8025-8036` 已实现 `[N]T ++ [M]T ⇒ [N+M]T`，并用 `ti_equal` 校验两侧元素类型一致，不一致报 `T-BIT-E515`。把元素类型取作 `clause`，**这条规则零改动即可复用**。
3. **不和 `&&` 撞**：`&&` 当前承担两职——值级布尔合取（`src/parse.tc:5178`，`&&`/`and` 同义产出 `"and"`）与类型约束位的 concept 合取（`src/parse.tc:431-439`）。再叠第三职会让 overload 消歧成本陡增；而 `++` 目前唯一的语义就是「合并」，语义完全对齐。

⇒ **group 的类型是 `[N]clause`（定长数组）**，而非 `[]clause` 切片。选定长的理由：① 数组字面量 `[c1, c2]` 天然是 `array_lit`，长度编译期已知；② 展开时要构造确定条数的臂，定长让「元数」在类型层就写死，不必在 sema 里再推一次；③ 已有 `[N+M]` 的长度相加规则可直接复用。

### 1.3 为什么「展开时才排重」

**裁定 C：一致性检查在 `++` 期做，排重（shadow 判定）在展开期做。**

这个分工是被数据流逼出来的，不是随意切的：

| 检查 | 能否在 `++` 期做 | 原因 |
|---|---|---|
| 两侧都是 clause 数组、元素类型一致 | ✅ 能 | Array 分支已有 `ti_equal` 判据 |
| pattern 的**结构形态**一致（都是字面量 / 都是构造子 / 都是通配） | ✅ 能 | pattern AST 自足，不依赖 scrutinee |
| ret_exp 的静态类型一致 | ❌ 不能 | ret 引用 pattern 绑定，脱离 scrutinee 无从推断类型 |
| pattern 与 scrutinee 类型匹配 | ❌ 不能 | scrutinee 在展开点才到场 |

⇒ 于是：

- **`++` 期**：只做「元素类型一致」+「pattern 形态一致」，报 `T-CLA-E723` / `T-CLA-E722`。
- **展开期**：把 group 摊成臂，交给**既有的 match 检查**——scrutinee 类型一致性（`T-MAT-E743`）、返回类型统一（`T_MATCH_ARM_TYPE`）、穷尽性（`T_MATCH_NONEXHAUSTIVE`）。
- **排重**也落在展开期，因为它本质是「臂级可达性」，与既有 `T-MAT-W744`（不可达臂警告）同源。

> 这条分工的最大收益：**几乎不新增语义检查**。clause 展开后就是普通 match 臂，所有既有诊断原样生效，`T-MAT-*` 不用改一行。

### 1.4 为什么通配符必须在 clause 层解决（裁定 D）

> **用户定向（2026-10-25）：「通配符问题必须在 clause 里解决，不然展开时，会出现 match 没有完全展开的问题。」**

这条定向指出上一版的一处真空：我原先把 `_` 当作「一条普通的、pattern 恰好是通配的 clause」，**既没说清它在 clause 里以什么形态存在，也没说清它何时、由谁获得最终语义**。于是「展开后到底是不是一个完整的 match」成了没有判据的一句话。

正确的理解是（**据 2026-10-25 用户三条更正**）：

> **「通配符在 clause 里解决」＝ clause 必须能携带「通配」这回事本身。**
> `_` 是 clause 的一等形态（与「字面量」「构造子」并列），不是待补的洞，也不是某个遗漏环节的代称。它从构造那一刻起就以完整形态存在。

据此逐条修正我上一版的两个**错误论断**：

**(a) ❌ 已撤回 ——「`_` 会退化为绑定 ⇒ 静默吞掉后续臂」。**
这是错的。**`_` 不是陷阱，它是 `else`**：展开时经**重排**落到最后一个臂位，扮演不可反驳的收尾——语义与 if 链末端的 `else` 同构。既然按定义它就落在末位，自然不存在「吞掉后续臂」这回事。
> 判错的根因：我把 `match.md` §7.4 那个历史灾难（模式位裸 `Red` 被当绑定 ⇒ 后续臂全不可达且零诊断）不当外推到了 `_`。那个坑的成因是「**裸标识符**没有区分大小写语义」；而 `_` 从来不是裸标识符，它是独立的记号。**两者不同源，类比不成立。**

**(b) ❌ 已撤回 ——「同一 group 在不同 scrutinee 下展开不同 ⇒ 语义不稳」。**
这条错的根源是**我把「值」的定义搞混了**。用户更正：**语义其实已经确定，只是被匹配的值还未输入。**
> 一个含 `_` 的 group 表示一个**确定的偏函数** `scrutinee → result`，构造完成即已定型；scrutinee 是它的**入参**。入参晚到 ≠ 函数未定——这与「同一个 `f` 先后以 `1` 和 `2` 调用、返回不同结果」是同一件事，没人会因此说 `f` 语义不稳。我把「输入未绑定」误读成了「语义未确定」。

**(c) ⇒ 唯一保留下来的结论，而且恰是前两条的必然推论：`_` 的最终语义在展开时才定形。**
既然它是完整的偏函数而非待补的洞（a），缺的只是入参而非语义（b），那么「把它代入具体 scrutinee、得到逐臂的具体形态」就必然只能发生在 scrutinee 到场的那一刻 —— 也就是**展开期**。

⇒ **裁定 D（改写版）：clause 携带符号化的通配，展开期才给通配定形。**

> **INV-1（改写版 · 结构自足不变式）**：任何成功构造出的 `[N]clause` 值，其**结构**必须自足且可指纹化（含「这是一条通配 clause」这一区分信息）；但它的**语义**（`_` 究竟覆盖哪些取值）**不要求**在 group 出口处确定 —— 那是展开期的职责。
> 展开期的产出满足 **INV-2（终端保证）**：摊平后的臂列**至多有一条无守卫通配臂，且必居末位**（经重排得到），其余臂按原序在前。有了这条终端保证，「match 有没有完全展开」才有客观判据，不再是悬案。

（上一版在这里要求「组出口时 scrutinee 类型必须已知」并做 eager 类型回填 —— **已撤销**，它是错误论断 (b) 的产物。值模型中的 `nd` 类型槽随之移除，见 §3。）

> 与 §1.3「排重在展开期」的关系：二者现在**同处展开期**且互相咬合 —— 重排先把通配挪到末位（INV-2），排重才能在确定的顺序上判定谁被谁遮蔽。

具体规则见 §5.2（携带）与 §5.4（定形）。

## 2. EBNF

```ebnf
// —— 匹配子句字面量（编译期 AST 构造）——
// guard 由 `when` 显式引出，故是「段位数」而非「位置 arg3/arg4」的判别：
ClauseLit: "@clause" "(" ClauseKind "," ClausePat "," ClauseTail ")"
ClauseTail: ClauseBody
          | KwWhen Expr "," ClauseBody          // 有守卫：`when` 占独立段位

ClauseKind : "." ClauseKindMember              // 子句类别枚举的成员，见 §5.1.1
ClausePat  : PatternExpr | "_"                 // 未求值；`_` 通配占位，不绑定（L-02）
ClauseBody : Expr                              // 未求值；可引用 ClausePat 的绑定名

// —— 子句声明组 = clause 的定长数组 ——
ClauseGroup: "[" ClauseLit ("," ClauseLit)* "]"     // ⇒ [N]clause
            | ClauseOperand "++" ClauseOperand      // ⇒ [N+M]clause

// —— 展开位：match 臂位置直接给一个 [N]clause 值 ——
MatchExpr: "match" "(" Expr ")" "{" ( MatchArm+ | ClauseGroupOperand ) "}"
```

**形态判别靠 `when` 关键字，不靠数逗号**：`@clause(.pattern, n, n * 2)` 是三段（无守卫），`@clause(.pattern, n, when n > 0, n * 2)` 是五段（有守卫）。理由见 §1.1 —— guard 与 body 同为 `Expr`，元数判别会把「两段看起来都像表达式」的歧义一直带到 sema。这消掉了原 §7 Q2 的风险，该题关闭。

**为什么展开位不需要新记号**：现行每条臂必含 `=>`（`src/parse.tc` `parse_match_arm`），因此臂位置出现一个**不含 `=>` 的裸表达式**在今天是解析错误。令其承载 `[N]clause` 值即展开，是**零新增语法**的空位利用。（备选：显式 `..G`，见 §7 Q3。）

## 3. 值模型（AST 层）

新增一个节点 kind（**不进**双后端发射路径）：

| kind | `sa` | `na` | `nb` | `nc` | 说明 |
|---|---|---|---|---|---|
| `clause` | 类别成员名（如 `"pattern"`） | pattern AST | guard AST（`-1` = 无） | body AST | 单条子句，编译期值 |

- **通配不占额外槽位**：「这是一条通配 clause」是**可判定的派生属性** —— `na` 是规范通配节点（`mk_ident("_")`，`src/parse.tc:4315` 同形状）**且** `nb < 0`（无守卫）。二者缺一不可：带守卫的通配不是不可反驳的收尾臂，不参与 §5.4 的重排。
- **上一版的 `nd`（scrutinee 类型槽）已移除**。它存在的理由（eager 类型回填）已随裁定 D 改写而失效；留着只会变成一个「可能填、也可能不填」的不可靠字段。§1.4 (b) 记录了这件事。
- group 的**容器**复用既有 `array_lit`（`meta_eval_array_lit`，`src/sema.tc:13091` 已支持把 array_lit 当编译期值），元素为 `clause` 节点。这样「取长度 / 按下标遍历 / `++` 合并」全部复用数组既有设施，不新建容器 —— 不再需要 `clause_set`（删，避免两套容器并存）。

`clause` 作为编译期值还须参与**单态化键**（Phase 3 需要）：既有 `meta_val_key`（`src/sema.tc:1985`）的做法是「长度 + 前 12 字符 + FNV-1a」，clause **不能沿用** —— 两块不同源码可能有相同文本前缀，且 `_` 的文本恒为 `"_"`，直接塌键。改用**结构指纹**：递归拼接 `(sa, kind(na), sa(na), kind(nb), kind(nc), 子节点数)` 后取 FNV-1a。

> ⚠ **键必须能区分「通配」与「恰好同形的其它东西」**：指纹里要显式带上 §3 那条派生判定（通配与否），不能只拼 `sa(na)` —— 否则 `@clause(.pattern, _, R)` 与任何 pattern 文本也是 `"_"` 的东西会撞键。这是 §5.2 唯一保留下来的一条实现告诫。

## 4. `clause` 是「编译期一等值」（裁定 E）

> **用户裁定（2026-10-25）：「它只活在编译期，它是值，同时成立。」**

这两半**必须同时读**，缺一半就会设计歪：

| 只读一半 | 会歪成什么 |
|---|---|
| 只承认「它是值」 | 会去争取运行期表示 ⇒ 要给 `clause` 设计布局、逃逸盒、双后端发射……成本是另一个量级（§7 Q7 的宽口径） |
| 只承认「它只活在编译期」 | 会退化成「纯语法构造」⇒ 不能绑定、不能作实参、不能参与并集，本文 §5.5/§5.6 直接做不成 |

正确的形态是：**它在编译期相位内享有完整的一等值身份，只是这个相位的边界就是它的存在边界。**

### 4.1 一等值身份（编译期相位内成立）

在编译期相位里，`clause` 可以做真值能做的一切：

- 绑定到名字（`const c = @clause(...)`）；在 comptime 上下文里也可作局部 `var`；
- 作为**实参传递**、作为**返回值**返回（从一个编译期函数返回给另一个）；
- 存入聚合：group 就是 `[N]clause` 数组，`clause` 因而天然是数组元素类型；
- 参与运算：`++` 并集（`[N]clause ++ [M]clause`）；
- 有稳定可判的身份：结构指纹（§3）——这正是一等值该有的性质。

### 4.2 越界即错

- 一旦出现在**运行期**位置（运行期 `var` / 结构体字段 / 运行期函数的返回 / 全局变量）→ `T-CLA-E724`。形态对齐既有 `T-MTA-E605`（CTFE-only 内建漏到运行期）。
- ⇒ **双后端零改动**：clause 在 check 结束前已被折叠 / 展开 ⇒ 发射侧永远看不到它。这是本设计刻意追求的性质——与「enum/slice 都要改两后端」形成对照。

### 4.3 类型注册

参照 `TypeInfo` 的注册先例（`src/sema.tc:1482-1485`，经 `sym_define(global_scope, ...)` 挂 `resolve_ti` 能识别的合成描述符）：在 `sema` 初始化期为 `clause` 注册一条 named TD，`cat = "clause"`，登记 `tip_kind → "Clause"`。

## 5. 语义规则逐条

### 5.1 构造（`@clause`）

| 项 | 规则 |
|---|---|
| 执行相位 | 编译期（CTFE）。`@clause` 是内建，走 `parse_meta_builtin` → `meta_eval_mbuiltin` 的 `"clause"` 分支 |
| 参数求值 | **不求值**（裁定 A）。仅挂 AST，并承接 `ln`/`cl` 供诊断溯源 |
| 返回类型 | `clause` |
| 段位数 | 4（无守卫）或 6（`.pattern` `,pat` `when` `guard` `,body`；含类别位共 5 段 / 7 记号）；否则 `T-CLA-E720` |
| 形态判别 | 看第 3 段是否为 `KwWhen`，**不数逗号**（§1.1） |
| `nd` 初值 | `-1`（未规约）；由 §5.2 填写 |

#### 5.1.1 `.pattern` 是子句类别枚举的成员（本次更正）

> **用户更正（2026-10-25）：「`.pattern` 实际为子语句的枚举类型，之后会添加更多子语句类型。」**

`.pattern` 不是一个自由字符串标签，而是**一个枚举的成员引用**——存在一个「子句类别枚举」，当前只有 `pattern` 一个成员，后续子功能往同一个枚举里加成员即可，语法不变。

```t
// 编译器登记的合成枚举（用户可写首成份的名字，不能自行追加成员）
enum ClauseKind : u8 {
    pattern,          // 匹配子句（本次唯一实装）
    // 后续子功能追加：type / regex / guard_only / …
}
```

裁定要点：

1. **登记方式与 `TypeInfo` 同构**（`src/sema.tc:1482-1485`：`sym_define(global_scope, ...)` 挂 `resolve_ti` 能识别的合成描述符）。初始化期注册 `ClauseKind`，后续加一趟末尾成员即可，不需要改 `@clause` 的语法。
2. **前导点写法 `.pattern` ≡ `ClauseKind.pattern`**，与既有 `.Red` ≡ `Color.Red` 同规格（`docs/syntax/drafts/match.md` §3 ②·③）。
3. **不与 C2 大小写约定冲突**：C2（首字母大写 = CaseName）是为消歧「模式位的**裸**标识符」而设的；`.pattern` 是显式前导点限定，写了限定就没有歧义，故小写合法。**类别枚举成员名统一小写**，从而与用户自己的 PascalCase 类型/枚举成员在观感上区分开。
4. **未来子功能如何落地**：加成员 → `@clause` 分派分支增加一个 case → 展开器为该类别提供自己的摊平规则。**本文只定义 `pattern` 一档**，其余留白，不在本次交付范围内超前设计。
5. 未知成员 → `T-CLA-E721`（未知子句类别）；诊断应**列出当前全部合法成员**（与 `T_MATCH_UNKNOWN_CASE` 的同款体验）。

### 5.2 通配的携带（construction & merge）—— 裁定 D 前半段

**目标：让 `_` 以一等形态活在 clause 里，结构自足、可指纹化（INV-1）；语义留白到 §5.4 再填。**

#### 5.2.1 三条规则

| 步 | 规则 |
|---|---|
| **C1 构造期落成形态** | `@clause(.pattern, _, R)` 把 `_` 落成**规范通配节点**（`mk_ident("_")`，与既有臂解析器同形状），并延续 L-02 的既有语义：**匹配任意值、不引入任何绑定**。此节点和普通 clause 一样参与结构指纹。 |
| **C2 一律不 eager 求解** | 构造期 / 合并期**都不**试图确定 scrutinee 类型。理由见 §1.4 (b)：group 是一个已定型的偏函数，缺的是入参而不是语义。 |
| **C3 `++` 只做顺序合并** | 通配 clause 就是普普通通的一个元素，享受与字面量 clause 完全相同的处理：顺序拼接，`[N] ++ [M] ⇒ [N+M]`。**没有任何**「向兄弟子句借类型」的动作 —— 上一版的 R3 合流回填已随裁定 D 改写而删除。 |

#### 5.2.2 派生判定：什么才算「通配 clause」

```
is_wildcard(c) := kind(c.na) == "ident" && sa(c.na) == "_" && c.nb < 0
```

`nb < 0`（无守卫）这个合取项很关键，它来自您更正的第 1 点——**只有被重排到末位才谈得上 `else` 语义**：

| 形态 | 是通配 clause 吗 | 参与重排吗 | 语义 |
|---|---|---|---|
| `@clause(.pattern, _, R)` | ✅ 是 | ✅ 参与 | 不可反驳收尾臂（`else`） |
| `@clause(.pattern, _, when g, R)` | ❌ 否 | ❌ 不参与 | 守卫可为假 ⇒ 不是收尾臂，按普通带守卫 clause 处理 |

#### 5.2.3 保留下来的一条实现告诫（原 §5.2.3 大幅收窄）

上一版曾据此断言「必须 eager 求解，否则 Phase 3 做不成」——**该结论已撤回**，它是 §1.4 (b) 那个错误定义的推论。真正站得住的只剩一条**键的构造要求**：

> `meta_val_key` 的结构指纹必须显式带上 `is_wildcard(c)` 这个派生判定位，不能只拼 `sa(na)`。
> 反例：`@clause(.pattern, _, R)` 与某个 pattern 文本也恰好是 `"_"` 的东西，只拼 `sa(na)` 会撞键 ⇒ 两个不同的实参塌成同一单态化实例 ⇒ 一个调用点冒名用上另一个的展开结果。

这类**编译期静默错编**（不报错、不崩溃，输出悄悄错）与本项目 KI-002 同族，也是本项目历史上唯一反复出现、且双后端 + conformance 全绿也拦不住的一类。

> **当前风险等级已下调（裁定 E 之后）**：确立 clause 为编译期一等值 + 带 clause 形参的函数必为编译期函数之后，参数场景走的是 **CTFE `meta_eval_call` 逐调用建帧求值**，根本不经过 `instantiate_generic`，也不产出任何可复用的实例 ⇒ **没有实例可塌**，事故路径自动消解（§5.6.2 第 2 点）。
> 故本节降级为**防御性告诫**：只在未来真的引入「按实参值缓存 / 复用展开结果」的机制时，才需要重新把它拿出来当硬约束。之所以仍留这一行，是因为这类事故一旦发生即为静默错编，代价极高，值得写下来。

### 5.3 并集（`++`）

```
[N]clause ++ [M]clause ⇒ [N+M]clause
```
- 元素类型一致：`ti_equal(elem_l, elem_r)`，否则 `T-BIT-E515`（**复用既有码，不新增**）。
- pattern 形态一致（新增 `T-CLA-E722`）：组内所有 clause 的 pattern 须同类——字面量 / 构造子 / 通配三类不可混。理由与 §1.3 表格一致：跨形态混合在 `++` 期仍可判，提前报错能让定位点落在并集处而非若干层展开之后。
- **通配 clause 在此步不享受任何特殊处理**（§5.2.1 C3）——它就是普普通通的一个元素。这是本轮改动后 `++` 相对普通数组拼接的**唯一**增量消失；实际增量只剩上面两条检查。
- 顺序保留（左在前），排重推迟到 §5.4。

### 5.4 展开（match 接住 group）—— 裁定 D 后半段：**`_` 在此定形**

给定 `match (s) { G }` 且 `typeof(G) == [N]clause`：

0. **前置断言 INV-1**：`G` 的结构自足且已可指纹化。这里**不要求** scrutinee 类型先验已知（§1.4 (b) 已撤回该要求）。
1. **重排（reorder）—— 本是整个机制的核心动作**：
   把组内所有满足 §5.2.2 `is_wildcard` 的 clause **移到臂列末位**（相对顺序保持），其余 clause 按原序在前。
   - 产出即 **INV-2 终端保证**：至多一条无守卫通配臂，且必居末位 ⇒ 它就是 `else`。
   - **为什么是安全的**：被移过去的 clause 本身匹配一切且无守卫，故它原本之后的一切 clause 就是不可达的；移动只改变了「何时才轮到试探它」，没有改变任何可达臂的判定顺序与结果。
   - 重排之后的语义与 if 链末端的 `else` 完全同构：前面都落空 ⇒ 轮到它。
2. 逐个取出 clause 生成熟知的 `MatchArm`：`PatternExpr [when Guard] => Body`。
   —— **这是关键实现取向**：不发明新的分派节点，直接产出既有 `MatchArm`，从而免费继承 match 的全部既有能力（区间模式 `1..5`、或模式 `|`、`@` 绑定、切片模式、不可达臂告警 `T-MAT-W744`…）。
3. 展开后照常跑 match 的全部检查：`T-MAT-E740/741/742/743`、`T_MATCH_ARM_TYPE`、`T_MATCH_NONEXHAUSTIVE`。
   —— 注意 **穷尽性自动成立**：只要组内含一条无守卫通配 clause，重排后它就在末位 ⇒ 必然穷尽（对应当今 `T-MAT-E742` 的那类「缺兜底」不会触发）。
4. **排重（§7 Q4 待裁定）**：在重排**之后**的顺序上遍历；若某 clause 的 pattern 与**更早的某条无守卫 clause** 指纹相同 ⇒ 被完全遮蔽 → **警告 `T-CLA-W727` 并丢弃**。带守卫的 clause 不参与遮蔽判定（守卫可为假）。
   - 多条无守卫通配 clause 会被第 4 步自然收敛为一条并告警 —— 不需要额外规则。
5. **为什么不必把 `_` 摊成逐 case**：有了 INV-2 的终端保证，无论 scrutinee 是 enum 还是 `i64`，`_` 都以同一个形态（`else` 收尾臂）落在同一个位置。上一版 §5.2.2 那张「能否摊为显式 case」的二分表随 eager 策略一并作废 —— 「完全展开」的判据现在是**结构性的**（有没有终端收尾臂），不再依赖 scrutinee 能否枚举。

> **「展开时才确定最终语义」的具体含义**：同一个含 `_` 的 group，套到 `match (c: Color)` 上，`else` 覆盖的就是 `Color` 的全部取值减去前列 case；套到 `match (n: i64)` 上，覆盖的就是全部整数减去前列字面量。**group 自身没变，变的是它的入参** —— 与函数两次调用同构。

### 5.5 子句声明组 → 函数（函数化）

拟议形态：

```t
fn classify(x: i64) string = G;      // G : [N]clause
```

脱糖：在既有 `desugar_func_clauses`（`src/parse.tc:3818`）的紧邻位置另开一条旁路，把 `= G` 的函数体改写为

```t
fn classify(x: i64) string { return match (x) { <展开 G> }; }
```

约束与诊断：
- ret 必须与函数返回类型一致，否则 **复用** `T_MATCH_ARM_TYPE`；
- 多形参（`x`, `k`）沿用既有脱糖策略：`#1` 起的模式折叠进该臂守卫。

> 之所以**不**反过来把既有「多子句 `fn`」改造成「先建 group 再脱糖」：那种统一看似更漂亮，但要重写已在 `desugar_func_clauses` 里跑通、且被 conformance/run_examples/自举四代不动点覆盖的分类逻辑（含裸绑定组 vs 类别组的分流），风险远大于收益。**保持既有路径不动，新增 `= G` 旁路。**

> ⚠ **与 §5.6 的对比很重要，别混淆**：本节的 `G` 是被**完全擦除**的（脱糖产物是一条普通 `match`，编译期就没了），故这个 `classify` 仍是**运行期函数**；而 §5.6 的 clause 是**形参**，它在编译期无法被擦除（值来自调用点），故宿主必须升为编译期函数。
> 判据一句话：**能被展开干净的就是运行期函数，留着 clause 的才必须待在编译期。**

### 5.6 子句作函数参数 ⇒ 该函数必为编译期函数（裁定 E 的推论）

> **用户裁定（2026-10-25）：「带有 clause 作为参数的函数必为编译期函数。」**

这不是一条待选的风格约定，它是 §4.1/§4.2 的**直接推论**：clause 只能活在编译期，那么**接纳 clause 的函数也就无法在运行期存在**——否则它的形参会要求一个运行期不存在的实参。所以它必须是编译期函数。

#### 5.6.1 现有实现已经替我们准备好了整套挂点

翻 `src/sema.tc` 会发现「编译期函数」与「编译期形参」两个概念**都已实装**，本规则几乎不需要新机制：

| 既有设施 | 位置 | 作用 |
|---|---|---|
| `bb` 位在 `FuncDecl` 上 | `base.mk_FuncDecl(sa, ba, **bb**, ...)`，`src/base.tc:3070` | 这就是「编译期函数」标记 |
| `bb` 位在**形参**上 | 形参节点（同 mk_ 系列的 `bb` 形参） | 「编译期形参」标记 |
| `comptime_fn_has_ct_param(d)` | `src/sema.tc:10009` | 判定某 comptime fn 是否为**编译期专用**（存在任一 comptime/type 形参即专用） |
| 体检查上下文切换 | `src/sema.tc:10097`：`if (node_bb(d) and comptime_fn_has_ct_param(d)) { g_in_comptime += 1; }` | 编译期专用 fn 的**函数体按 comptime 上下文检查** ⇒ ctfe-only 内建在体内豁免 `T-MTA-E605`（这也是 f75 回归修出来的那条） |
| 逃逸诊断 | `src/sema.tc:13028` → `T-CLO-E781` | 把编译期函数当运行期函数值用 ⇒ 报错 |

⇒ **落地方式**：登记/检查期一旦发现某形参的声明类型是 `clause` / `[N]clause`，则①该形参置 `bb = true`（编译期形参）、②宿主 `FuncDecl` 置 `bb = true`（编译期函数）。随后 `comptime_fn_has_ct_param` 自然返回真，函数体自动进入 `g_in_comptime` 上下文——**上面那些既有行为全部免费继承**，包括「体可用 ctfe-only 内建」「不可当作运行期函数值」两条。

#### 5.6.2 由此带来的三项连锁后果

```t
fn apply(cs: [2]clause, x: i64) string {     // ⇒ 编译器自动置为编译期函数
    return match (x) { cs };
}
const r = comptime apply(G, 7);              // 全编译期求值，折叠为常量
```

1. **其余形参也随之成为编译期求值语境**：整个调用必须在编译期完成，故 `x` 位置上写运行期变量是不成立的（一个不存在的运行期函数无从接收运行期实参）。这与 t 既有「编译期专用 comptime fn」的行为完全一致，不需要新机制。
2. **不再需要「值参数单态化」，也不再需要 `meta_val_key` 结构指纹**：调用走的是 CTFE `meta_eval_call` 建帧求值（每次调用独立一帧），**不是** `instantiate_generic` 生成运行期实例。⇒ 更有利的是：**不同实参天然产出不同求值结果，不存在「同一实例被复用」的可能**，于是 §5.2.3 那处塌键风险在参数场景下**自动消解**（它只在将来真的引入按参缓存时才需要重新拿出来说）。
3. **该函数永不出现在 IR 里** ⇒ 又一次印证「双后端零改动」。

#### 5.6.3 我的一条保留意见（不阻塞，但请你过目）

按你的措辞「**必**为编译期函数」，我把它实现成**编译器自动置位**——用户不必也不用手写 `comptime fn`；写与否都不改变结果。

这与本项目 L-02（显式）存在一点张力：编译器在这里替用户做了一个不可见的决定。**两条路**：
- **甲（本文采用）**：自动置位。「必为」是必然结论，要求写出来只是冗余仪式；且写错也拦不住。
- **乙**：要求显式写 `comptime fn`，漏写即报错。更贴合 L-02，代价是多一条要背的语法规则。（该码未注册 —— 已裁定取甲案）

倾向甲，但**这是一处可以由你一句话翻转的口径**——若你要的是乙，我加一条 E715 即可，其余不受影响。

| ~~Q7~~ | clause 到底是不是一等「值」？ | ✅ **已裁定（2026-10-25）：「它只活在编译期，它是值，同时成立。」** —— **编译期一等值**（§4）。据此关闭宽口径（运行期表示）选项，并推出「带 clause 形参的函数必为编译期函数」（§5.6）。 |
| ~~Q8~~ | 编译期函数是**自动置位**还是**要求显式标注**？ | ✅ **已裁定（2026-10-25）：自动置位（甲案）**。显式标注 `comptime fn` 仍保留，但**仅限用户主动声明编译期函数的场合** —— 它不再是「带 clause 形参」的前置条件。 |

## 8. 法律验证（对照 L-15）

| 法律 | 判据 | 现状 |
|---|---|---|
| L-04 唯一语义 | clause **不是**第二种分派语义，它只是**构造 match 臂的手段**；展开产物就是既有 `MatchArm`，`match` 仍是值分发的唯一真源 | ✅ §5.4 第 2 点明确保证；不新增分派节点、不改双后端 |
| L-02 显式 | `_` 不绑定延续既有语义；clause 越界到运行期显式报错；带 clause 形参的函数**由编译器强制**升为编译期函数（自动置位，§5.6.1）；其误当运行期函数值用走既有 `T-CLO-E781`；遮蔽发显式警告 | ✅ §5.2.1 C1 + E710 + W720 |
| L-03 静态类型 | group 长度、pattern 与 scrutinee 的匹配、ret 类型统一、穷尽性——**全部在展开点静态确定**（穷尽性由 INV-2 终端保证自动成立） | ✅ 复用 `T-MAT-*` |
| L-14 铁律校验 | 待填：需在实现期补齐 conformance + run_examples + 双后端 + 自举不动点 coverage | 🟡 见 §9 |

> **两条不变式与 L-03 的关系（改写后）**：
> **INV-1（结构自足）** 是「可指纹、可单态化」的前提 —— 没有它，同一实参在两处会塌成同一实例（§5.2.3）。
> **INV-2（终端保证）** 是「穷尽性可静态判定」的前提 —— 没有它，就没法回答「这个 match 展完了没有」。
> 二者都**不需要** scrutinee 类型提前已知：语义定型推迟到展开期是**被允许的**，因为展开仍然全程发生在编译期，L-03 不受影响。

> **坑 P1（已修）**：`clause` 一度注册为 `ti_named("Named", "clause")`。`"Named"` 是**未解析引用**，
> 语义等同 Unknown ⇒ `fn f() i64 { return C; }` **0 error 静默放行**。改用独立种类 `ti_mk("Clause")`
> 并补 `ti_str` / `ti_equal` 两个分支后，该错编被既有 `T-SEM-E202` 拦下（`expected i64 but got clause`）。

> **坑 P2（已修，本批最关键）**：展开**不能**挂在 sema（`infer_expr`）。
> HIR AstGen（`hir_build`）在 run_check **之前**就把 match 的臂链降级成 `HIR_OP_MATCH_ARM`，
> 届时臂链里还是未展开的拼接位 ⇒ AstGen 按「链元即臂」处理而崩（`t_slice_at`）。
> ⇒ 展开是纯语法变换，必须挂在 `parse_unit` 末尾、HIR 之前。这也顺带保证了 CST 与 HIR 两条通路一致。
>
> **坑 P3（已修）**：臂链的 head/tail 是 **`kids` 池的 entry 索引**（`list_push` 的返回值），
> **不是节点 id**。把拼接表达式的节点 id 直接当链元用会写坏链表（实测同一个 `t_slice_at` 崩溃）。
>
> **坑 P4（已修）**：`mk_arm` 末位是**记号索引**（内部走 `tk_line/tk_col`），不是节点 id。
>
> **坑 P5（已修）**：clause 常量**不可从 decl_list 摘除**。摘掉后后续引用失去符号，
> `return C;` 连「未定义标识符」都不报 ⇒ 新的静默洞。正解 = 保留声明 + 跳过发射。
