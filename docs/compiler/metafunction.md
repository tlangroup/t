# t 语言元函数（Metafunction）规范

> 状态：**规范 v3（基于用户裁定更正）** ｜ 相关设计：`docs/compiler/meta_design.md`（`comptime`/`meta` CTFE 总设计）、`docs/compiler/desugar_pass.md`（用户插件 API）
> v3 相对 v2 的关键更正：① **`@` 不是「相位选择符」**——`@name` 是编译期内建函数的**完整名称**（`@` 是名字一部分），仅供编译器内建；普通函数**不能**用 `@` 来编译期运行。② **普通函数的编译期执行用 `comptime name(...)`**：`comptime` 是真实的调用位强制机制（源码已有 `comptime` 节点与 `comptime_fold` 全量折叠），**不是** `comptime fn` 声明标记。③ **元函数是内建 `@name`，与运行期函数唯一区别 = 不定长参数（IR 优势）**。

## 0. 核心裁定（设计原则）

> **元函数总体上「看起来是函数，行为规则也是函数」。**
> 在 t 语言里，`@id_fn(...)` 就是把 `id_fn` **作为元函数调用**——`id_fn` 必是元函数。关键：**`@id_fn` 对用户是一个整体标识符（一个编译期内建）**，`@` 不是施加在普通函数 `id_fn` 上的「编译期开关」。`@name` 在编译器内部如何标识（名字字符串直接含 `@`、还是用 flag / 命名空间区分）是**实现细节，规范不约束**——用户只感知到「`@name` 一个整体」。

> **`@name` 是编译器内建函数，只存在于编译期。**
> 写内建函数（`@`-前缀的名字）都是「编译期运行的函数」。它们由编译器以原生钩子实现，但对外呈现为函数：看起来是函数、行为也是函数（真实编译期求值，非文本宏展开）。

> **普通函数不能用 `@` 来编译期运行。**
> 一个普通 `fn` 若要被强制在编译期执行，写法是 **`comptime name(...)`**——`comptime` 是调用位的强制机制，说明「这个函数被强制编译期运行」。这与「元函数 `@name`」是两回事：前者是被强制的普通双栖函数，后者是编译期内建。

> **元函数（`@name`）与运行期函数的唯一区别：元函数支持不定长参数（variadic）。**
> 这一能力不是语法层拼凑，而是**底层 IR 的直接优势**——元函数调用不生成运行期调用帧，其「调用」在编译期由编译器展开，参数个数在编译期即确定，无需遵守任何运行期 ABI 契约（详见 §5）。

其余一切：形参声明、返回类型、函数体语句、显式返回规则、纯函数约束、求值模型——元函数与运行期函数**完全相同**（差异仅来自「执行相位」带来的约束，见 §2/§4）。

## 1. 定义

**元函数（metafunction）**：以 `@name` 形式调用的、在**编译期**执行的**编译器内建函数**。对用户而言 `@name` 是一个整体标识符；其内部标识方式（名字字符串直接含 `@`，还是用 flag / 命名空间区分）是实现细节，规范不做约束。调用形式固定为 `@name(...)`。

它具备函数应有的一切（对外呈现）：

- 看起来是函数：用与普通函数一致的「名字 + 形参 + 返回」形态调用。
- 行为也是函数：执行语义是真实的编译期求值（CTFE），不是文本宏展开。
- 实参在调用点必须是**编译期已知**的（类型名或字面量 / 可折叠表达式）。
- 返回值是**编译期值**（字面量、类型、或编译期构造的聚合），直接落入调用处的常量位置。

当前 t 中属于「编译期内建 `@name`」的有两类（详见 §6）：

1. **通用编译期内建**：`@type_equal` / `@type_size` / `@type_name` / `@zeroed` / `@str_from_bytes` / `@compile_error` / `@sin`… 等（编译器原语）。
2. **模块系统内建**：`@module(...)`（设置当前模块可见性）、`@import(...)`（导入模块，返回模块对象）。`@module`/`@import` 的名字里也含 `@`，属内建。

> ⚠ **普通函数经 `@` 调用是非法的**（v3 更正）：`@` 仅供内建；若 `@name` 不是已知内建 → `T-MTA-E607` 未知内建。普通函数要编译期执行，必须走 `comptime name(...)`，见 §7。

> ⚠ 变体辅助 fn 是历史遗留：`Name_from_Case` 等由 `meta_eval_variant_call` 分发的辅助 fn 属历史遗留；变体值构造现统一通过匿名结构体字面量完成，不计入元函数，当前 `meta_eval_variant_call` 是要被清掉的遗留路径（见 §10 D6）。

> ⚠ 实现现状：内建目前仍以「按名分发的编译期内建」实现（`meta_eval_mbuiltin` / `meta_eval_builtin`）；`@module`/`@import` 目前仍以文件级声明指令实现（见 §10 D2）。规范将它们统一归为「编译期内建」，未来实现路线见 §10/§11。

## 2. 与运行期调用的对照（唯一区别表）

### 2.1 元函数 `@name(...)` vs 运行期函数 `f(x)`

下表针对「元函数（内建）」与「同形态的运行期函数」——这是元函数规范的核心：差异属于「内建 vs 用户函数 + 执行相位」，唯一结构性区别是**不定长参数**。

| 维度 | 运行期函数 `f(x, y)` | 元函数 `@name(x, y)` |
|---|---|---|
| 名字 | `f`（普通标识符） | `@name`（整体标识符，编译期内建；内部标识方式不限） |
| 声明 | 用户 `fn f(...) {...}` | 编译器内建（原生钩子，对外呈函数形态） |
| 调用语法 | `f(x, y)` | `@name(x, y)` |
| 执行时机 | 运行期 | 编译期（CTFE） |
| 实参性质 | 运行期值（可含运行期引用） | 编译期已知（类型名 / 字面量 / 可折叠） |
| 返回值 | 运行期值 | 编译期值（落入常量位置） |
| 副作用约束 | 允许 IO / 副作用 | 禁止触碰运行期世界（§4 纯函数约束） |
| 不定长参数 | ❌ 不支持（须守 TClosure ABI） | ✅ **支持（唯一区别）** |
| 退化 | — | `@` 调用不退化：实参不全已知 → 编译错误 |

### 2.2 `comptime name(...)`（普通函数强制编译期）vs 元函数 `@name(...)`

两者都在编译期执行，但**是不同机制**，不要混淆：

| 维度 | 元函数 `@name(...)` | `comptime name(...)` |
|---|---|---|
| 被调方 | 编译期内建（`@` 是名字一部分） | 普通双栖用户函数 |
| 机制 | 内建分发 | 调用位 `comptime` 强制 CTFE |
| 形参表 | 由内建定义（可不定长，§5） | 普通函数签名（**定长**，与运行时一致） |
| 是否「元函数」 | ✅ 是 | ❌ 否（是普通函数的编译期执行） |
| 典型用途 | 类型查询 / 编译期原语 | 把用户逻辑放在编译期跑（如查表、生成） |

> 一句话：`@name` 是「编译期内建函数本身」；`comptime name` 是「把某个普通函数强制在编译期跑一遍」。二者都是编译期求值，但前者是语言原语，后者是普通函数的执行相位选择。

#### 2.2.1 同名共存实例：`@type_of` 与 `type_of`

「`@name` 是整体内建、`name` 是普通函数」两者**不冲突**，因为它们属于不同命名空间（`@type_of` 与 `type_of` 是两个独立的标识符）。具体：

```t
// ① 元函数：编译期内建，@ 是其名字一部分
@type_of(x)            // 调编译期内建 @type_of，返回 x 的编译期类型
// 注意：你也可以定义同名普通函数，二者不撞名
fn type_of(x: any) -> string {        // ② 普通双栖函数，名为 type_of（无 @）
    return @type_name(@type_of(x))    // 体内可调用 @type_of 内建
}
// ③ 强制把普通 type_of 在编译期执行（与 ① 不同机制，但结果都发生在编译期）
const s = comptime type_of(some_value)   // 运行普通 type_of，但在编译期求值得字符串常量
```

- `@type_of` → 编译器内建（元函数），`@` 是名字整体前缀。
- `type_of` → 用户普通函数，与 `@type_of` 不在同一命名空间，**可同时存在、互不影响**。
- `comptime type_of(...)` → 强制在编译期执行那个普通 `type_of`，是普通函数的编译期相位（§2.2 右列机制），与 `@type_of` 无关、但能达成「编译期拿到类型信息」同样的效果。

> 结论：元函数与普通函数之间**只靠 `@` 前缀区分命名空间**，不存在「`@type_of` 会遮蔽/冲突普通 `type_of`」的情况。若想要用户自定义的类型查询，就写普通 `type_of`（或任意名字）并 `comptime` 调用即可。

## 3. 调用语法 `@name(...)`

语法落点（当前实现）：`src/parse.tc` `parse_primary` → 表达式起始位 `@` + `Identifier` 即进入 `parse_meta_builtin`，拼接成内建名 `sa = "@" + ident`，生成 `mbuiltin` 节点。模块系统内建 `@module`/`@import` 当前在文件级声明位被拦截（见 §9、§10）。

### 3.1 `@name` 是整体标识符（非相位选择符）

- 写 `@type_size(T)` 即「调用名为 `@type_size` 的编译期内建」。`@` 不是施加在 `type_size` 上的开关——不存在一个运行期的 `type_size` 函数供你 `@` 切换。
- **对用户，`@name` 是一个整体**：`name` 既不是一个独立的、可被 `@` 前缀修饰的普通函数，也不存在「去掉 `@` 的同名运行期函数」。`@` 是内建名字自带的前缀，不可拆分理解（内部是否把 `@` 存进名字字符串、还是用 flag / 命名空间区分，是实现细节，规范不约束）。
- 规范目标：被调名须是已知内建；若 `@name` 未定义 → `T-MTA-E607`（`UNKNOWN_BUILTIN`）。
- 被调内建无可用钩子（如仍处模板本体被跳过）→ `T-MTA-E617`。
- 实参不全为编译期已知 / 含运行期引用 → 编译错误（不退化）。

### 3.2 实参求值顺序

实参在调用方环境逐个先求值（CTFE），再建帧绑定（见 `meta_eval_call`）。类型形参（`meta T: type`）不求值，转成类型节点；其余形参求值成字面量 / 编译期聚合。

### 3.3 类型实参位置歧义

部分内建第 0 位收**类型**而非表达式（`[1024]u8` 不是合法表达式），解析期即按名定死（`mb_arg_is_type`）：`type_name`/`type_size`/`zeroed` 取 idx==0，`type_equal` 取 idx<2，`simd_lanes` 取 idx==0，`type_info` 取 idx==0（见 §6 `@type_info(T)`）。

## 4. 元函数的「函数性」

元函数体（编译器原生钩子）对外呈现为**与运行期函数体一致的语句语义**：

- 支持 `var` / `const` / `auto` / `if` / `while` / `for` / `return` / `break` / `continue`。
- **显式返回规则一致**：所有路径须 `return`，否则 `T-MTA-E616`（`NO_RETURN`）。无隐式返回。
- 控制流（`if`/`while`/`for`/`match`）的求值就是真实解释执行（见 `meta_eval`/`meta_exec`），不是宏替换。
- **纯函数约束（宪法第 7 条可复现）——仅作用于编译期相位**：
  - 禁止 IO / 副作用 → `T-MTA-E615`（`IMPURE`：`file_*` / `sys_run` / `args` / `exit` / `path_resolve`）。
  - 禁止读运行期变量 / 内存 → `T-MTA-E620`（`READ_RUNTIME`）。
  - 禁止把类型当值用 → `T-MTA-E608`（`TYPE_AS_VALUE`）。
- 求值护栏：步数预算 `T-MTA-E612`（`BUDGET`）、递归深度 `T-MTA-E613`（`DEPTH`，64）、除零 `T-MTA-E614`（`DIV_ZERO`）。

> 之所以「行为也是函数」：编译期求值器 `meta_eval` / `meta_exec` 逐节点解释元函数体，与运行期解释器同构；它产出的是**字面量 / 类型 / 编译期聚合节点**，随后由检查器正常类型检查——两层是串行而非并行（见 `meta_design.md` §10 缓解）。

## 5. 唯一区别 —— 不定长参数（底层 IR 带来的直接优势）

### 5.1 运行期调用为何不能不定长

运行期调用必须**降级为具体 C/LLVM 调用**，遵守固定 ABI。t 的函数 ABI 为统一闭包约定 `Ret (*)(void* env, Args...)`（`codegen_c.tc`）：调用点与被调方必须就**参数个数与类型**达成一致。t 目前没有运行期 `stdarg.h` 风格 varargs，故运行期调用**不支持不定长参数**。

### 5.2 元函数为何可以不定长（IR 优势）

元函数是编译期内建，其「调用」**不生成运行期调用帧**。它是编译器在编译期对其实参做解释执行：编译器在调用点已知**全部实参的个数与类型**，直接把实参逐个绑定进形式参数槽（如同 CTFE 建帧 `menv_push2`）。

由于参数数量在编译期即确定，**不存在「运行期 ABI 契约」需要遵守**。因此「不定长」是底层 IR / 编译期展开的自然、直接产物——这是一个 **IR 层优势**，而非语法糖。

> 一句话：运行期调用受 ABI 约束故定长；元函数（编译期内建）在编译期展开故天然不定长。区别的根源是「调用在哪里被实现」。

### 5.3 不定长形参的声明与体内形态（规范）

> ⚠ 当前实现：元函数调用仍强制**精确元数**（`na1 != np1` → `T-MTA-E611`，`ARITY`）。不定长绑定是下一实现步，IR 已结构性允许，规范如下供落地。

- **声明**（以内建形态示意）：末位形参带 rest 标记，收集调用点剩余实参：

  ```t
  @concat(prefix: string, parts: string...) string {   // parts 在元函数体内是编译期 []string
      var s: string = prefix;
      for (p in parts) { s = s + p; }
      return s;
  }
  @id_fn(prefix, args...)   // @id_fn("x", a, b, c) → args 绑定为 [a, b, c] 三个编译期值
  ```

- **体内形态**：rest 形参绑定为一个**编译期聚合**（编译期 `[]T` / 列表），可用 `for` / `len` / 下标遍历——因为遍历本身也在编译期解释执行。
- **约束**：
  - 不定长部分只能接收**编译期已知**实参（与元函数整体约束一致），不可混入运行期值。
  - 一个元函数至多一个 rest 形参，且必须位于形参表末位。
  - rest 的承载类型须为编译期可表示的聚合；其元素类型由调用点实参类型推导（同构则归一并类型，异构则报 `T-MTA-E601` `ARG_TYPE`）。

| `print` / `eprint` | CTFE 日志 | 编译期写 **stderr**（stdout 留给 JSON/IR） | —（仅编译期副作用） |
| `int_to_str` / `i2s` / `str_len` / `str_at` | CTFE 纯查询 | 字符串处理 | —（仅编译期） |
| `sym_intern(buf, len)` | CTFE 符号构造 | 由字节驻留 `Sym` | —（仅编译期） |
| `@module(attr, ...)` | **模块系统内建** | **设置当前模块的可见性**（`pub` / `internal`）；返回 unit | —（编译期副作用） |
| `@import("M" [:: items])` | **模块系统内建** | **导入模块 M，返回一个模块对象**；支持 `const m = @import("M")` 绑定与 `m.foo` 成员访问 | —（编译期，返回模块对象） |

> 旁支：`@derive(Clone, Copy, …)`（P6 已重建 8 trait）与类型位 `@Vector` / `@Tile` 是**类型 / 声明位**的编译期注解或类型构造原语，**不是 `@name(...)` 表达式值调用**，故不计入元函数。此外，变体辅助 fn（`Name_from_Case` 等）属**历史遗留**，变体值构造现统一通过匿名结构体字面量完成，同样不计入元函数。`@desugar` / `@pass` 是编译期插件**注解**（见 `desugar_pass.md`），同样非 `@name(...)` 值调用。

> **普通函数的编译期执行（`comptime name(...)`）不在此表**——它是普通双栖函数的强制 CTFE，机制见 §7，非内建元函数。

## 7. 双栖模型与两类编译期执行

v3 厘清两个经常被混为一谈的概念：

### (a) 普通函数是双栖的，但「编译期执行」靠 `comptime`，不靠 `@`

- 运行期调用 `f(x)`：正常运行期求值；可含运行期引用、IO、副作用，不受 §4 纯函数约束。
- **编译期强制 `comptime f(x)`**：把 `f` 强制放在编译期相位求值（CTFE），实参须编译期已知，体受 §4 全部 CTFE 护栏约束。`comptime` 是**调用位强制机制**（源码 `base.tc` 有 `mk_comptime` / `mk_comptime_block` 节点，`comptime_fold.tc` 提供全量 `comptime` 折叠），**不是 `comptime fn` 声明标记**——无需（也不存在）把 `f` 声明成某种特殊种类。
- `comptime` 调用**不退化**：若实参不全已知 / 含运行期引用，编译器报错，而非偷偷降级运行期。这与「全量 comptime 折叠」（`comptime_fold_pass`，`g_comptime_full`）互补：`comptime name(...)` 是程序员**显式**强制；全量折叠是编译器**自动**把可折叠表达式就地改写。

### (b) 元函数 `@name` 是编译期内建，普通函数不能 `@` 调用

- `@name` 对用户是一个整体内建标识符；你**不能**写 `@f(x)` 去编译期运行一个普通 `fn f`——这会被当作「查找名为 `@f` 的内建」，未定义则 `T-MTA-E607`。
- 普通函数要编译期运行，走 (a) 的 `comptime f(x)`。

```
   ┌──────────── 编译期执行的两类机制（勿混淆）────────────┐
   │                                                     │
 @name(...) 元函数（编译期内建）              comptime f(...) 普通函数强制 CTFE
   │                                                     │
 名字含 @，编译器原语                          f 是普通双栖函数
 仅编译期，可不定长（IR 优势）                 定长（普通函数签名）
 如 @type_size / @module / @import            如 comptime build_table(...)
   │                                                     │
   └────────────────────┬────────────────────────────────┘
                     都在编译期求值
```

## 10. 实现现状 vs 规范（对齐清单）

本规范描述的是**目标模型**。当前编译器实现与规范存在以下差距，需在对齐实现时逐项消除：

- **D1 — `meta_eval_call` 的 `bb`/`is_comptime` 门禁（`✅ 已落实`）**：已移除 `meta_eval_call`（`src/sema.tc:12813`）对被调 `FuncDecl` 的 `bb` 位门禁——非 `comptime fn` 不再报 `T-MTA-E618`，`comptime name(...)` 对任意双栖 `fn` 可用（v3 模型）。`@` 仍只解析内建（`@name` 未定义 → `T-MTA-E607`）。`comptime fn` 语法标记暂保留为无害冗余。
- **D2 — `@module` / `@import` 仍是文件级声明指令，未重分类为内建 `@name(...)`**：当前 `@module(...)` / `@import("...")` 在 `parse_declaration` 被拦截为 `ModuleDecl` / `ImportModDecl`，不进入 `@name(...)` 表达式值调用路径。规范目标：重分类为内建元函数调用；`@import` 返回模块对象（`const m = @import("M")` 的模块值别名机制已部分就绪）、`@module` 作为设置当前模块可见性的副作用内建。
- **D3 — 不定长未接线**：`meta_eval_call` 仍强制 `na1 != np1 → T-MTA-E611` 精确元数（§5.3）。需放松为「末位 rest 形参吸收余参」。
- **D4 — 内建仍按名分发**：`@`-内建目前由 `meta_eval_*` 按名字符串分发，未各自身为首类函数声明。规范统一归为内建（见 §11 路线 5）。
- **D5 — `@derive` 维持注解身份**：按用户口径，`@derive` 是类型/声明位注解（源码级 trait 注入），**不**计入元函数调用形式；类型位 `@Vector` / `@Tile` 同理为类型构造原语；`@desugar` / `@pass` 为插件注解（见 `desugar_pass.md`）。
- **D6 — 变体辅助 fn 属历史遗留**：`Name_from_Case` / `Name_is_Case` / `Name_as_Case[_fK]` 由 `meta_eval_variant_call` 分发的路径是历史遗留；变体值构造现统一走**匿名结构体字面量**，该分发路径应被清理，不纳入元函数体系。

## 11. 开放问题与路线图

1. **`@` 调用门禁重定（D1，`✅ 已落实`）**：`meta_eval_call` 已去掉「用户 `fn` 须 `comptime` 标记才能 `@` 调用」的旧逻辑；`@` 只解析内建（`@name` 未定义 → `T-MTA-E607`），普通函数 CTFE 改走 `comptime name(...)` 路径。
2. **模块系统内建重分类（D2）**：把 `@module` / `@import` 从文件级指令改写为内建 `@name(...)` 表达式值调用；`@import` 返回模块对象（或等价的可成员访问的模块值），`const m = @import("M")` 走统一绑定。
3. **不定长参数落地（D3，§5.3）**：放松精确元数检查，末位 rest 收集编译期聚合；`na1 != np1` 判定改为「末位 rest 吸收余参」。
4. **rest 承载类型与遍历 API（D3 续）**：明确 rest 在体内的类型（编译期 `[]T` / 列表）及 `len` / 下标 / `for` 遍历语义。
5. **首类内建声明（D4）**：把 `@`-内建逐个改写为真正的首类声明，让「看起来是函数」成为字面事实，取代按名分发。
6. **与 M8 `@desugar` / `@pass` 用户插件 API 的关系**：见专门设计文档 `desugar_pass.md`。`@desugar`/`@pass` 是**注解身份**（与 `@derive` 一致），其执行复用「双栖 `fn` + `comptime` 强制编译期执行」载体；编译器只实现一种**通用 `Macro` 捕获**（`IDENT '!' (...|{...}|[...])`），不为任何具体用户语法做适配。
7. **清理变体辅助 fn 遗留（D6）**：移除 `meta_eval_variant_call` 分发与 `Name_from_Case` 等生成逻辑，变体值构造统一收敛到匿名结构体字面量；该路径不进入首类元函数体系。
