# T 语言规范：overload 上下文关键词与类型/结构伪重载脱糖机制

> **状态**：草稿（DRAFT）—— 新特性规范，待语法规则法（L-15）起草工作流评审采纳。
> **依据**：建立在既有「函数子句模式匹配」（`docs/syntax/drafts/match.md`，见 `examples/clause_demo.tc`）与类型系统（`docs/syntax/drafts/types.md`、`docs/constitution.md`）之上；本文仅规范 `overload` 上下文关键词及其类型/结构分派、跨文件扩展与脱糖规则，不重复既有的函数声明、match 表达式与类型文法。
> **本文修订要点（相对原始草稿）**：① 字符串格式化由 Python 式 `"…".format(v)` 改为 t 既有 `format("…", v)` 内建或 f-string `f"…"`；② 类别树移除 t 不存在的 `f128`（标量仅 `f16/f32/f64`）；③ 无返回类型一律写作 `unit`（现行方向：`void` 已进入废弃过渡、`unit` 为规范关键字，见 P5；现行实现层仍以内置标量 `void` 承载，`unit` 与 `void` 在此等价）；有返回值的子句写作具体类型；④ 匹配臂臂体**允许单一表达式与 `{ }` 块两种形式**——有返回值的 overload 子句亦可采用带 `return` 值的块体（原稿误述为「仅单一表达式」）；⑤ 结构模式采用**具名字面量模式** `Point{.x=0, .y=0}`：字段以 `.` 前缀引用（`.x`）、以 `=` 关联值（t 中 `=` 仅表赋值/相等，不引申更多语义）；具名 / 匿名字面量模式的可用性边界与后端限制见 §1.1 与头部修订要点 ⑦。⚠ **语法一致性（已澄清）**：现行 `match.md` / `clause_demo.tc` / `examples` 的结构字面量（构造与模式）多写作 `Point{ x: 0, y: 0 }`（`:` 关联）。但实现层（2a3c4b6 起 `parse_struct_lit`）**同时接受** `Point{.x=0, .y=0}` 与 `Point{ x: 0, y: 0 }` 两种写法且二者等价——`x:` 形式保留以维持自举不动点（见 `docs/reference.md` §3.4/§3.21），故二者并非解析层分歧，而仅是将 `.`+`=` 确立为唯一规范形式、并择机废弃 `x:` 的规范化决策，留待语法规则法（L-15）裁定。另：`.{…}` 匿名复合字面量**不限定为结构体**——依上下文可为结构体，亦可为元组；⑥ 补全原稿缺失的 §2.5（值与结构组的顺序敏感性与不可达子句）；⑦ **结构/元组字面量模式当前受 KI-002 影响（open）**：`match` 中的 struct / 元组字面量模式在 **LLVM 后端运行期错编**——判别条件被整体丢弃、首臂恒命中（2026-09-25 双后端对拍：LLVM 轨 `tc run` 实测 `1`、期望 `0`，C 轨 `0`），仅 **C 后端语义正确**。本规范的 overload 子句若以结构/元组字面量模式为依据（见 §2.2、§2.3、§4.2），在 KI-002 修复前于 LLVM 后端并不安全，须以 C 后端（`tc compile --emit-c` + clang）为运行基准，或暂以字段访问 + `if` 比较替代字面量模式。详见 `docs/compiler/known-issues.md` KI-002 与 `docs/syntax/drafts/match.md` §6.3。

## 1. 引言与范围

### 1.1 术语与约定

本文档使用以下术语，其含义在全文范围内保持一致。

**overload**：T 语言中的一个上下文关键词。该关键词出现在函数声明之前，用于标记一组并列的声明构成同一函数的匹配子句集合。overload 不得被理解为传统意义上的函数重载机制。

**声明组**：由一条或多条带 `overload` 前缀的函数声明构成的集合。声明组内的所有声明共享同一函数名；各声明的形参个数必须相同，形参类型可以不同，形参类型与结构模式同样构成匹配依据。

**子句（clause）**：声明组中的单条声明。每条声明对应匹配集合中的一个匹配路径。本规范以「子句」为正式称法。

注：本项为术语层面的称法变更，overload 关键词以及 `extend` 的用法与书写形式均不随之改变，一条 overload 声明即一个子句。

**类型格（type lattice）**与子类型关系，以及由属性定义偏序的属性式类型（property-based types）：Automated Systems of Property-Based Types，专利文献 US20200250558A1；另见类型信息模型相关文献。

**C++ 标准库类型特征（type traits）**：`is_integral`、`is_signed`、`is_unsigned` 与 `is_arithmetic` 的判定范围与归属，以及 `is_void`、`is_enum`、`is_union`、`is_class`、`is_function`、`is_array`、`is_reference` 等类型分类条目。（定义于 `<type_traits>`，C++11 起；C++17 起提供 `_v` 变量模板。）

注：2.7 节的类别偏序取自本节的包含格与类型格诸条——由包含关系诱导「更具体／更一般」的偏序，距离度量则是在该偏序之上附加的度量。

注：2.8 节的类别树在划分上参照本节的类型特征条目，但二者不等同——C++ 的 `is_integral` 含 `bool` 与字符类型，本规范的 `integralkind` 不含，差异见 2.8 节的注。

注：第 3 章的跨文件扩展语义可与这一支对照。

**上下文关键词**：仅在有限上下文中具有特殊含义、在该上下文之外仍可用作标识符的关键词；`overload` 属此类。相关语言的实践见附录 B.1。

**脱糖（desugaring）**：把表层语法形式改写为语义相同的核心形式的过程，见 4.1 节与附录 B.2。

**类型子句**：以形参类型（类别）为判定依据的子句；与之相对者为值与结构子句，以运行期值（结构模式、字段值）为判定依据。二者的划分与书写要求见 5.4 节。

**函数签名**：由函数名与形参列表构成的、用于核对调用的信息；形参个数由签名确定，见 2.2 节。

**匹配集合**：一个声明组所对应的全部子句的集合，即脱糖前意义上的候选集合，见 2.3 节。

注：本文所讨论的机制在非正式场合亦称「伪重载」；本规范不以该称法作术语（其评估见附录 A.1），全文以「overload 声明组」为正式称法。

**结构模式（模式）**：出现在参数位置的、由具名复合字面量承载的字段值约束，例如 `Point{.x=0, .y=0}`（字段以 `.` 前缀引用、以 `=` 关联值）。结构模式参与匹配判定，其字段值构成匹配条件。本文档以“结构模式”为规范称法，下文简称“模式”者指同一对象。注：当前 `match` 对具名结构体字面量模式（如 `Point{.x=0, .y=0}`）与匿名元组字面量模式（如 `.{1i64, "a"}`）均可解析；匿名 `.{...}` 在模式位置仍需由被匹配值类型推断出具名结构体类型，否则报 `T-DOT-E101`。无论具名或匿名，**struct / 元组字面量模式当前在 LLVM 后端均受 KI-002 影响（运行期错编、首臂恒命中），仅 C 后端正确**——本规范据此将结构/元组字面量模式列为「可用但 LLVM 后端暂不安全」的依据形式（见头部修订要点 ⑦）。结构模式的字段关联形式以 `.` 前缀 + `=` 书写（规范形式；实现层同时接受等价的 `:` 形式，见头部修订要点 ⑤）。

**类别（kind）**：类型在匹配层面所属的类，如 `i32`、`f32`、`Point` 各自所属的类别。类别之间由包含关系构成树形层级，称为包含树；被包含者比包含者更具体。类别层级的参考描述见 2.8 节，具体程度的判定见 2.7 节。

**根节点**：类型匹配中由前置声明绑定的类别。类型子句所声明的类别必须位于该根节点的子树之内；根节点自身视为位于其子树之内。详见 2.2 节。

**前置声明**：置于声明组首部的声明，用于绑定类型匹配的根节点。声明组包含类型子句时必须包含一条前置声明，其形式见 2.1 节与 2.2 节。

**兜底子句**：用于承接未被更具体的子句覆盖的输入的子句。一个声明组只设一类兜底，与该组承担的依据类别一致：值与结构组用数值兜底（以通配模式 `_` 声明的子句），类别组用类别兜底（以根节点作为类别声明的子句）。其认定与数量约束见 2.4 节。

**术语层级**：一条带 `overload` 前缀的函数声明即一个子句；多条并列的 overload 声明构成一个声明组；声明组脱糖后生成一个函数与一列匹配臂，每个子句对应一条匹配臂，匹配臂中的模式即该子句声明的匹配依据。故称法层级为：声明组 → 子句 → 匹配臂；「overload 声明」与「子句」指同一条声明的两个称法，不构成两层。后文一律按此称法使用，不再另作说明。

> **与既有函数子句的关系（合规性注）**：overload 声明组建立在 `docs/syntax/drafts/match.md` 的「函数子句模式匹配」之上（验证见 `examples/clause_demo.tc`）。一条 overload 声明在语法上即一条函数子句（参数位泛化为 `ParamPattern`，允许结构模式与 `when` 守卫），多条同名同元数子句由既有 `desugar_func_clauses` 在 AST lowering 阶段归并为单一 `FuncDecl`，其体为 `return match (__p0) { … }`。overload 在既有机制之上新增两项能力：① 参数位允许以**类别（kind）**为模式做类型分派（见 2.2 节类型子句）；② 允许以 `extend` 跨文件追加子句（见第 3 章）。其余脱糖与穷尽性判定复用既有 `match` 规则，语义真源唯一，满足 L-04 唯一语义。

### 1.2 范围

本文档界定 overload 上下文关键词的声明形式、跨文件扩展语义、脱糖规则及约束条件。

## 2. 声明形式与匹配语义

### 2.1 基本声明语法

一条 overload 声明必须采用以下形式之一：

```
overload fn <函数名>(<模式>[:<类型>]) <返回类型> { <语句块> }

overload fn <函数名>(<模式>[:<类型>], <模式>[:<类型>], ...) <返回类型> { <语句块> }
```

其中 `<模式>` 位置允许以下三种写法，三者居其一：

- **结构模式**：由具名复合字面量承载的字段值约束，如 `Point{.x=0, .y=0}`（字段以 `.` 前缀引用、以 `=` 关联值）；字段值参与匹配判定。结构模式本身蕴含类型，可省略 `:<类型>` 标注（与 `examples/clause_demo.tc` 中 `fn classify(0) string` 的裸字面量模式同构）。
- **形参名**：只指定输入的类型、不施加字段值约束，如 `v: i32`、`p: Point`；此时判定依据只有类型。该形式必须带 `:<类型>` 标注。
- **通配模式 `_`**：不施加字段值约束，如 `_: Point`；用于声明兜底子句（见 2.4 节）。该形式必须带 `:<类型>` 标注。

三种写法均以类型参与匹配判定；结构模式额外以字段值参与匹配判定。本规范下文以「模式」泛指参数位置上出现的上述三种写法，仅在需要区分时称「结构模式」或「通配模式」。

当声明组包含类型子句时，其首部必须包含一条前置声明，用于绑定类型匹配的根节点：

```
overload root(<参数>:<类别>);
```

前置声明必须位于声明组内所有子句声明之前。前置声明只绑定根节点，不产生匹配臂；其所属声明组包含类型子句时不得省略（见 2.2 节）。

**编译期排序，运行期顺序匹配**：编译期必须依据上述规则对子句完成排序——类型子句按具体程度由具体到抽象排列，值与结构子句保持书写顺序。排序完成后，运行期仅需按顺序依次尝试匹配，无须再进行类型比较。该设计的目的是把类型比较的代价前置到编译期，并保证匹配结果确定；对具体程度不可判定的子句，必须按 2.7 节判定规则四诊断为歧义。

类型子句的排序以被匹配对象所在类别为参照：对给定的被匹配对象类别 `K_obj`，各类型子句的具体程度有定值，排序结果唯一且与书写顺序无关；被匹配对象不同，类型子句的次序也可以不同。本规范不要求在与调用点无关的意义上给出全局唯一次序（见 2.7 节）。

以下参考示例中，五条子句均针对参数 `v` 的类别声明，声明组首部含一条前置声明：

```
overload root(v: anykind);
overload fn bar(v: anykind) unit { println(f"anykind : {v}"); }
overload fn bar(v: scalarkind) unit { println(f"scalarkind : {v}"); }
overload fn bar(v: integralkind) unit { println(f"integralkind : {v}"); }
overload fn bar(v: floatkind) unit { println(f"floatkind : {v}"); }
overload fn bar(v: f32) unit { println(f"f32 : {v}"); }
```

排序要求：编译期必须依据上述规则，对给定的被匹配对象类别 `K_obj`，将其适用的全部类型子句按 ≺ 降序排列，即由具体到抽象。除判定规则四所指的不可判定情形外，排序结果必须唯一，且必须与各子句的书写顺序无关。判定规则一、二、四均以 `K_obj` 为参照，故排序是相对于调用点的：不同调用点的 `K_obj` 可以不同，其类型子句的次序也可以不同，本规范不要求在任意两个子句之间给出与调用点无关的全局唯一次序。互斥的具体类别子句（如 `v:f32` 与 `v:f64`）同为候选，其先后由二者与该 `K_obj` 的距离决定：距离不等时适用判定规则二；距离相等时（例如被匹配对象所在类别为 `floatkind` 本身，二者距离均为 1）适用判定规则四，编译期必须报歧义。对具体程度无法判定的两个子句，实现可以按既定顺序（例如类别树的定义顺序）给出确定次序，以便输出稳定；该次序不具有规范效力，实现仍必须按判定规则四报告歧义。判定规则一至四只适用于仅含类别子句的声明组（见 5.4 节）；值与结构组不发生类别排序，不适用本条。

### 2.2 参数形态与匹配依据

在 overload 声明中，参数位置的 `Point{.x=0, .y=0}` 应当被解析为"对类型 Point 的输入施加字段值约束"。该字面量指定输入必须满足的字段值条件，其类型由字面量本身（具名结构体）蕴含。

**匹配依据的范围**：任何函数均可以 overload 形式声明；其参数列表中任何字段的值与类型均可以参与匹配判定。匹配依据不限于形参个数与形参名——形参的类型参与匹配，结构模式所触及的任何字段的取值同样参与匹配。因此，overload 的适用范围并不局限于类型分派：凡可作为匹配条件的参数信息，均可以作为子句的划分依据。

字段值参与匹配，意味着 `Point{.x=0, .y=0}` 与 `Point{.x=1, .y=0}` 是两个不同的结构模式，尽管二者类型相同。

**参数个数**：形参个数由函数签名确定。T 语言不支持不定长参数，故声明组内各子句的形参个数必须相同：单参数与多参数的声明不得并存于同一声明组。形参个数的核对发生于调用与签名之间，不构成子句之间的区分依据。

**类型匹配**：形参类型本身即匹配依据。同一函数名下可以依据不同的形参类型分别声明子句，形参类型不同即视为不同模式，而不因函数名与参数名相同而归并。

**类型匹配的根节点**：由于类型与值在匹配上的差异，类型匹配子句可以包含一条前置声明，用于绑定类型匹配的根节点。其余类型子句所声明的类别必须位于该根节点的子树之内，即必须是根节点的子类别（类别包含关系见 2.8 节）；若某子句所声明的类别不在该子树之内，则为错误，实现必须在编译期报错，不得将其纳入匹配集合，也不得静默忽略。

声明组包含类型子句时，必须包含一条前置声明以绑定根节点；类型匹配声明组缺少前置声明即为错误，实现必须在编译期报错。声明组仅包含值与结构匹配时，不涉及根节点，无须前置声明。

若前置声明绑定的根节点为 `anykind`，即整棵类别树的根节点，则所有类别均位于该根节点子树之内，上段所述的子树约束不产生额外限制。

前置声明的形式如下例所示（以 `integralkind` 为根节点）：

```
overload root(v: integralkind);
overload fn sum(v: i32) unit { println(f"i32"); }
overload fn sum(v: signedintegralkind) unit { println(f"signed"); }
overload fn sum(v: f32) unit { println(f"f32"); }   // 错误：f32 不属于 integralkind 的子树
```

注：上例中前置声明以 `root` 标识所绑定的根节点，其具体语法形式为占位示例，由实现约定。

根节点自身视为位于其子树之内：以根节点为类别声明的子句是合法的，该子句充当类别的总兜底，用于承接类别子句未覆盖的输入（见 2.4 节）。

**匹配判定次序**：形参个数先按函数签名核对；通过后，匹配判定只按该声明组所承担的依据类别进行，两类依据不并列（见 5.4 节）：值与结构组核对结构模式与字段值，任一环节不符则该子句不命中，须继续尝试后续子句；类别组核对形参类型，由 2.7 节判定规则在候选之间择优。

匹配依据分为两类，其优先级的来源不同：值与结构匹配的优先级来自声明的书写顺序，类型匹配的优先级来自类别的具体程度。值的匹配必须按声明顺序依次尝试，先命中者胜出，且兜底子句的检查必须晚于所有结构模式子句；类型的匹配不受书写顺序影响，其排序方式见 2.6 节与 2.7 节。

注：在值与结构组中，若将兜底子句置于更具体的结构模式子句之前，则其后的结构模式子句将永远无法命中，实现必须对此情形给出警告，并指明被遮蔽的子句及其所在位置。该判定的依据是「某子句是否可能匹配到此前子句尚未覆盖的输入」；据此不再可能命中的子句即为不可达子句，实现必须给出警告。该检查与 5.2 节的匹配失败判定一并适用。判定准则见附录 B.3。上述顺序敏感性检查只适用于值与结构组：类别组的兜底子句为类别兜底，不受书写顺序影响，类别子句由编译期按具体程度重排（见 2.6 节与 2.7 节）。

### 2.3 声明与子句的对应

一条 overload 声明对应匹配集合中的一个子句。多条并列的 overload 声明构成一个声明组。以下四条声明构成同一声明组：

```
overload fn foo(Point{.x=0, .y=0}) unit { println(f"o"); }
overload fn foo(Point{.x=1, .y=0}) unit { println(f"x"); }
overload fn foo(Point{.x=0, .y=1}) unit { println(f"y"); }
overload fn foo(_: Point) unit { println(f"unknown"); }
```

上列声明取自示例源文件 `a.tc`；`b.tc` 以 `extend` 形式向同一声明组追加一条子句（见 3.2 节）。该声明组脱糖后的结果见 4.2 节，逐条映射关系见 4.3 节。

> ⚠ **实现状态（KI-002，open）**：上列以 `Point{.x=0, .y=0}` 等结构字面量模式为依据的 overload 子句，其匹配语义依赖 `match` 的结构字面量模式判别。该判别在当前 **LLVM 后端运行期错编**——条件被丢弃、首臂恒命中（双后端对拍：LLVM 轨 `tc run` 输出 `1`、期望 `0`，C 轨 `0`），仅 **C 后端正确**。故本规范的结构/元组字面量模式子句在 KI-002 修复前于 LLVM 后端并不安全；验证请走 C 后端（`tc compile --emit-c` + clang）或暂以字段访问 + `if` 比较替代字面量模式。详见 `docs/compiler/known-issues.md` KI-002、`docs/syntax/drafts/match.md` §6.3。

### 2.4 兜底子句

兜底子句用于承接未被更具体的子句覆盖的输入。由于一个声明组只承担一类匹配依据（见 5.4 节），其兜底子句也只设一类，与该组承担的依据类别一致：

- **数值兜底**：以通配模式 `_` 声明的子句，如 `_: Point`，用于值与结构组。该子句承接未被更具体的结构模式覆盖的输入；其所声明的类型限定该子句的作用范围，并须与该组内其他值与结构子句所声明的类型一致（见 4.1 节）。
- **类别兜底**：以根节点作为类别声明的子句（根节点见 2.2 节，如 `v:anykind`），用于类别组。根节点即该类别的总兜底，承接未被更具体的类别子句覆盖的输入；它不受书写顺序影响，其优先级由 2.7 节判定规则确定。

一个声明组中必须至多包含一条兜底子句：值与结构组至多一条数值兜底，类别组至多一条类别兜底。声明组应当设置兜底子句；未设置时，未命中任何子句的输入必须触发匹配失败（见 5.2 节）。

匹配依据分为两类，其优先级的来源不同：值与结构匹配的优先级来自声明的书写顺序，类型匹配的优先级来自类别的具体程度。一个声明组只承担一类依据，故每组只适用其中一套规则（见 5.4 节）。值与结构组的匹配必须按声明顺序依次尝试，先命中者胜出，且其兜底子句的检查必须晚于该组内所有结构模式子句；类别组不受书写顺序影响，其兜底子句（类别兜底）的优先级同样由具体程度决定，排序方式见 2.6 节与 2.7 节。

编译期排序后，子句顺序调整为：

```
overload fn bar(v: f32) unit { println(f"f32 : {v}"); }
overload fn bar(v: floatkind) unit { println(f"floatkind : {v}"); }
overload fn bar(v: integralkind) unit { println(f"integralkind : {v}"); }
overload fn bar(v: scalarkind) unit { println(f"scalarkind : {v}"); }
overload fn bar(v: anykind) unit { println(f"anykind : {v}"); }
```

注：上例的排序依据是各子句类别的具体程度。`f32` 为被匹配的具体类型，具体程度最高；`floatkind` 是 `f32` 的祖先类别，距离为 1 段路径；`integralkind` 与 `scalarkind` 之间存在祖先与后代关系，故 `integralkind` 较 `scalarkind` 更具体；`scalarkind` 是 `floatkind` 与 `integralkind` 的共同祖先；`anykind` 位于包含树顶层，抽象程度最高，排于最后。排序结果与书写顺序无关。

注：本例中 `floatkind` 与 `integralkind` 之间不存在祖先与后代关系，其相对次序依据 2.7 节判定规则二的路径距离确定。

注：示例中各子句的输出字符串仅用于区分不同子句，不影响匹配语义。

注：该声明组以 `overload root(v: anykind);` 绑定根节点；其中以 `anykind` 声明的子句即类别的总兜底（见 2.4 节）。

### 2.5 值与结构组的顺序敏感性与不可达子句

值与结构组的匹配优先级来自书写顺序（见 2.6 节），故其声明顺序具有语义意义。将兜底子句（数值兜底 `_`）置于更具体的结构模式子句之前，会使后者永远无法命中。

实现必须对此类顺序敏感情形发出警告：若某子句不可能匹配到此前子句尚未覆盖的输入，则该子句即为**不可达子句**，实现必须给出警告并指明被遮蔽子句及其所在位置。判定准则是「某子句是否可能匹配到此前子句尚未覆盖的输入」；据此不再可能命中的子句即为不可达，实现必须给出警告。该检查与 5.2 节的匹配失败判定一并适用，且只适用于值与结构组。

类别组因不受书写顺序影响（由编译期按具体程度重排，见 2.6 节与 2.7 节），不构成上述不可达子句问题；其兜底以类别兜底（根节点）承担，优先级由 2.7 节判定规则确定。

注：上述判定准则与附录 B.3 的模式匹配穷尽性/冗余检查同构；既有 `match` 表达式已对不可达臂发出 `T-MAT-W744` 警告（不拦截编译），overload 的值与结构组沿用同一机制。

### 2.6 匹配语义与子句排序

匹配依据分为两类，其优先级规则不同。一个声明组只承担一类匹配依据，故每组只适用下列规则之一（见 5.4 节）。

**值与结构匹配按顺序优先**：当子句的判定依据是运行时可获得的值（字段值、结构模式）时，匹配优先级即声明的书写顺序。匹配必须自上而下依次尝试，先命中者胜出。

**类型匹配按就近详细程度优先**：当子句的判定依据是形参类型（类别）时，匹配优先级取决于类别之间的具体程度。被匹配对象越接近某个类别，该子句越优先，即越具体、越详细的类别越优先。

**候选的适用范围**：凡声明组中声明的类别子句均构成候选，被匹配对象的类别无须位于某一子句所声明类别的子树之内；命中的子句由具体程度择优决定，即取距离最小的那个已声明类别（判定规则见 2.7 节）。2.2 节关于「类型子句所声明的类别必须位于根节点子树之内」的要求，是对可声明范围的约束，与候选的适用范围是两回事。

类别之间的具体程度由包含关系决定。类别体系为树形包含结构，例如 `anykind` 包含 `scalarkind`，`scalarkind` 包含 `floatkind`，`floatkind` 之下包含 `f16`、`f32`、`f64`。因此形参类型为 `f32` 的子句比形参类型为 `floatkind` 的子句更具体，后者又比 `scalarkind` 更具体，`scalarkind` 又比 `anykind` 更具体。

注：判定规则四所指的歧义与“无匹配”是两类不同的错误：前者存在多个可能命中的子句而规则无法择一，后者无任何子句命中。

注：类别包含关系的层级参考见 2.8 节；本条的理论背景见第 6 章参考文献中关于包含格的条目。

### 2.7 具体程度的判定规则

本条以序关系给出类别具体程度的判定规则，作为 2.6 节“就近详细类型匹配”的操作依据。

**定义 1（具体程度序）**：类别集合上定义偏序 ≼，称为具体程度序。对任意类别 `K1`、`K2`、`K3`：

- （a）自反性：`K1 ≼ K1`；
- （b）反对称性：若 `K1 ≼ K2` 且 `K2 ≼ K1`，则 `K1` 与 `K2` 为同一类别；
- （c）传递性：若 `K1 ≼ K2` 且 `K2 ≼ K3`，则 `K1 ≼ K3`。

记号 `K1 ≺ K2` 表示 `K1 ≼ K2` 且 `K1` 与 `K2` 不为同一类别，读作“`K1` 比 `K2` 更具体”。

**定义 2（包含关系诱导的偏序）**：若类别 `K2` 位于类别 `K1` 的子树之下，即 `K1` 包含 `K2`，则 `K2 ≺ K1`。亦即被包含者比包含者更具体，包含者比被包含者更一般。

**定义 3（距离）**：对子句声明的类别 `K` 与匹配对象所在类别 `K_obj`，其距离 `d(K_obj, K)` 定义为二者在包含树中的最短路径边数。距离自被匹配对象所在类别起算；`K_obj` 必须位于根节点所绑定的子树之内（见 2.2 节）。

**判定规则一（可比者按偏序）**：若子句 A 声明的类别与子句 B 声明的类别可比，即 `K_A ≺ K_B` 或 `K_B ≺ K_A`，则更具体者优先。

**判定规则二（不可比者按距离）**：若 `K_A` 与 `K_B` 不可比，即既非 `K_A ≺ K_B` 亦非 `K_B ≺ K_A`，则必须比较 `d(K_obj, K_A)` 与 `d(K_obj, K_B)`，距离较小者优先。

**判定规则三（抽象类别最低）**：包含树的根类别（如 `anykind`）与其余所有类别可比且为最一般，其优先级最低。本规则是判定规则一的直接推论，单列以便实现。

**判定规则四（不可判定即歧义）**：若 `K_A` 与 `K_B` 不可比，且 `d(K_obj, K_A)` 等于 `d(K_obj, K_B)`，则具体程度不可判定。此时不存在唯一最佳子句，编译期必须将其诊断为歧义并报错，不得静默选取任一子句。为使输出稳定，实现可以按既定顺序（例如类别树的定义顺序）为二者给出一个确定次序；该次序不具有规范效力，不得据以改变匹配结果，亦不得替代歧义诊断。若按判定规则一与判定规则二逐对比较的结果不能构成全序——例如存在 `K_A` 优先于 `K_B`、`K_B` 优先于 `K_C`、而 `K_C` 优先于 `K_A` 的比较循环——同样视为具体程度不可判定，按本规则处理。

注：上述位置只影响类别之间的具体程度关系，不改变匹配的候选范围：类别子句的可声明范围仍受 2.2 节的子树约束，被匹配对象的类别与某一子句所声明类别之间的关系，按 2.6 节的候选适用范围与 2.7 节的判定规则处理。

注：`integralkind` 的划分参照 C++ 的 `is_integral`，但二者不等同：C++ 的 `is_integral` 将 `bool` 与各字符类型一并计为整数类型，本规范的类别树则将 `bool` 与 `charkind` 置于 `integralkind` 之外，与 `floatkind`、`complexkind` 并列于 `scalarkind` 之下。`signedintegralkind` 与 `unsignedintegralkind` 分别对应 `is_signed` 与 `is_unsigned`。本节类别划分与 C++ 类型特征的对应关系及其差异，见 6.1 节。

注：本节所述层级为类别体系的参考性描述。若层级与具体程度判定出现不一致，以 2.7 节规定的判定规则为准。

## 3. 跨文件扩展

### 3.1 extend 的语义

`extend` 用于向已存在的声明组追加子句。其声明形式为：

```
extend fn <函数名>(<模式>[:<类型>]) <返回类型> { <语句块> }
```

`extend` 前缀表明该声明不创建新的函数实体，而是向同名函数的既有声明组追加一个子句。

### 3.2 子句的并入

本节的示例沿用两个源文件：`a.tc` 与 `b.tc`。同一函数 `foo` 的子句分别声明于这两个文件中；`a.tc` 含 2.3 节所列的四条声明。

在 `b.tc` 中声明的

```
extend fn foo(Point{.x=1, .y=1}) unit { println(f"xy"); }
```

必须被并入 `a.tc` 中 `foo` 的同一匹配集合。合并后，该子句与原有子句共享同一函数名与参数类型签名。

### 3.3 相对位置关系

新增的结构模式子句必须排在兜底子句之前生效。若原声明组已包含兜底子句，则新增子句的匹配优先级应当高于兜底子句，但低于其之前已声明的结构模式子句。

具体而言，`b.tc` 的 `Point{.x=1, .y=1}` 子句在合并后位于 `Point{.x=0, .y=1}` 之后、`_:Point` 之前。

### 3.4 实体同一性

扩展后的声明组仍是同一函数的多子句形式，不构成新的函数实体。合并后的集合脱糖后产生同一个函数与同一列匹配臂（见 4.2 节）；`b.tc` 追加的子句仅表现为该列匹配臂中的一行，函数名与形参列表均取自原声明组。

注：`extend` 不得被理解为在另一文件中定义了一个新的 `foo` 函数；合并后的声明组中不存在第二个同名函数实体。

### 3.5 开放集合

`extend` 的设计意图在于将"一组模式"构造为可开放扩展的集合，而非封闭定义。任何持有该函数可见性的文件均可以 `extend` 形式追加子句。

## 4. 语义与脱糖

**形参类型的处理**：声明组包含类型子句时，各子句对同一形参位置声明的类型可以不同，脱糖后该位置的类型取前置声明所绑定的根节点；声明组包含类型子句时必须包含前置声明，缺少前置声明即为错误，实现必须在编译期报错（见 2.2 节）。具体程度的判定转由匹配臂承担。

声明组仅含值与结构子句时，各子句对同一形参位置所声明的类型必须一致；不一致者即为错误，实现必须在编译期报错。脱糖后该位置的类型取该一致的类型。各子句所声明的类型标注由函数形参类型承担，匹配臂中不再重复书写——匹配臂写作 `Point{.x=0, .y=0} => …`，而非 `Point{.x=0, .y=0}: Point => …`。

以分层写法的两层声明组为例（见 5.4 节）：外层只含类别子句，内层只含值与结构子句。

```
overload root(f: floatkind);
overload fn baz(f: f32) unit { baz_f32(f); }
overload fn baz(f: f64) unit { baz_f64(f); }
```

脱糖为：

```
fn baz(__f: floatkind) unit {
    return match (__f) {
        f32 => baz_f32(__f)
        f64 => baz_f64(__f)
    };
}
```

内层子函数各自构成独立的声明组（值与结构组）。以 `baz_f32` 为例：

```
overload fn baz_f32(Point{.x=0, .y=0}) unit { println(f"A"); }
overload fn baz_f32(Point{.x=1, .y=0}) unit { println(f"B"); }
```

脱糖为：

```
fn baz_f32(__p: Point) unit {
    return match (__p) {
        Point{.x=0, .y=0} => println(f"A")
        Point{.x=1, .y=0} => println(f"B")
    };
}
```

注：外层形参 `f` 的声明类型取前置声明所绑定的根节点 `floatkind`，各匹配臂的判定依据只有类别，其次序以调用点的被匹配对象所在类别为参照（见 2.7 节）。内层各子句的形参类型一致（均为 `Point`），类型标注由函数形参类型承担，匹配臂中不再重复书写。多参数声明组的匹配臂按形参位置并列书写各分量的模式，如 `(Point{.x=0, .y=0}, Point{.x=1, .y=1}) => …`。类型臂（`f32 => …`）为 overload 在既有 `match` 之上新增的类别匹配能力，其具体程度由 2.7 节判定规则择优。

### 4.1 脱糖规则

一个声明组必须脱糖为单一函数加一列「模式 => 体」的匹配臂；声明组中的每个子句对应其中一条匹配臂（映射关系见 4.3 节）。脱糖后的函数名取声明组内各声明共享的函数名；形参个数与形参类型参与匹配判定，其脱糖展开须与 2.2 节规定的匹配判定次序保持一致。

**匹配臂的臂体形式**：每条匹配臂的体允许**两种形式**——单一表达式，或 `{ }` 块。对于有返回值的 overload 子句，臂体亦可为带 `return` 值的 `{ }` 块（见 4.2 节示例）。两条形式均落到既有的 `match` 语义，overload 不引入独立的运行期分派路径。

**形式参数处理**：形参个数由函数签名确定。T 语言不支持不定长参数，故声明组内各子句的形参个数必须相同，脱糖后的函数沿用同一形参列表，不引入参数打包；多参数声明组的匹配臂按形参位置并列书写各分量的模式。

**与既有 lowering 的关系**：overload 子句在语法上即 `match.md` 的函数子句，故直接复用既有 `desugar_func_clauses`——按函数名归组，整组合并为单一 `FuncDecl`，其体为对合并后参数（记为 `__p0`）的 `match` 表达式；类型子句经 2.7 节具体程度排序后纳入同一 `match` 的候选臂。原子句节点在 lowering 后下线，对下游检查与双后端发射不可见，保证整组只被诊断一次。

### 4.2 脱糖结果

第 2 章与第 3 章所述声明组脱糖后，结果如下：

```
fn foo(__p: Point) unit {
    return match (__p) {
        Point{.x=0, .y=0} => println(f"o")
        Point{.x=1, .y=0} => println(f"x")
        Point{.x=0, .y=1} => println(f"y")
        Point{.x=1, .y=1} => println(f"xy")
        _ => println(f"unknown")
    };
}
```

注：单元返回型（如上例）以 `return match (__p) { … };` 收尾，亦可以 `match (__p) { … };` 作为函数体末语句。匹配臂的臂体允许单一表达式（如上例）或 `{ }` 块两种形式；有返回值的 overload 子句亦可采用带 `return` 值的块体。例如一个带返回值的声明组：

```
overload fn area(p: Point) i64 { return p.x * p.y; }
```

脱糖为（块体形式）：

```
fn area(__p: Point) i64 {
    return match (__p) {
        p => { return __p.x * __p.y; }
    };
}
```

亦可写作单一表达式臂：

```
fn area(__p: Point) i64 {
    return match (__p) { p => __p.x * __p.y };
}
```

### 4.3 映射关系

脱糖后的每一行匹配臂对应声明组中的一条声明，映射关系如下：

- `Point{.x=0, .y=0}` 臂来源于 `a.tc` 的第一条声明；
- `Point{.x=1, .y=0}` 臂来源于 `a.tc` 的第二条声明；
- `Point{.x=0, .y=1}` 臂来源于 `a.tc` 的第三条声明；
- `Point{.x=1, .y=1}` 臂来源于 `b.tc` 的 `extend` 声明；
- `_` 臂来源于 `a.tc` 的 `_:Point` 兜底声明。

`_` 兜底臂的来源是声明组中的数值兜底声明。该声明组未启用类别匹配，故该数值兜底即本函数的总兜底（见 2.4 节）。该臂必须位于所有结构模式臂之后。

### 4.4 脱糖动机

脱糖的核心动机在于：匹配顺序必须在编译期确定。若按运行期类型分派，则同一输入可能命中多个候选，产生歧义。编译期须完成两项工作：其一，对类型子句按类别的具体程度排序，由具体到抽象；其二，保持值与结构子句的书写顺序。排序完成后，脱糖结果语义等价于"自上而下依次尝试，先命中者胜出"，运行期无须再进行类型比较，从而消除分派歧义。

脱糖必须保持三项属性：语义保持，即脱糖后的形式产生与原始形式相同的结果；类型保持，即原始形式通过检查者，脱糖后的形式以相同方式通过检查；错误位置保持，即诊断信息仍指向原始源码位置。前两项由 4.3 节「一条声明对应一条匹配臂」的映射关系保证；第三项要求实现记录各子句在源文件中的位置，2.7 节判定规则四的歧义诊断与 2.5 节不可达子句的警告，均必须报告到原始声明所在位置。参见附录 B.2。

### 4.5 与真正重载的对比

真正的函数重载依据静态类型或参数类型选择不同的函数实体，重载决策发生于编译期的函数解析阶段，结果指向多个函数实体中的某一个；overload 声明组脱糖后仅产生一个函数实体，其匹配同时考虑形参类型、结构模式与字段值。

二者的区别不在于是否使用类型信息，而在于前者产生多个函数实体、后者产生单一函数的多条匹配臂。本条所述区别的规范结论见 5.1 节，使用约束见 5.2 节。

### 4.6 相近机制的对照

本条为非规范性内容，用于说明本规范与既有语言中相近机制的异同，不属于规范性要求。

Raku 以一组 `multi sub` 声明加一个 `proto` 头承载候选列表，调用先解析到 `proto`，再由 `proto` 从候选中选出最佳者；候选之间的先后以「更窄」关系排序。TypeScript 允许多条只有类型的重载签名加一个实现签名收尾，实现签名自身不可被直接调用，分派逻辑留在实现体内部、不参与类型检查。二者与本规范同向：由若干条声明构成一个组，最终只对应一个实体或一个实现。差异有二：其一，Raku 的候选与 TypeScript 的重载签名仍各自是独立的声明实体，而本规范的脱糖结果只有匹配臂；其二，二者均未把具体程度的不可判定制度化——Raku 对并列候选直接报歧义，TypeScript 交由实现体自行判断——本规范则以判定规则一至四给出可判定的排序依据，仅在不可判定时诊断歧义。

## 5. 约束与边界条件

### 5.1 结论性规定

overload 不得被理解为函数重载。该关键词所区分的语义是同一函数内匹配臂的选择，而非函数实体的选择：该区分不产生独立的函数实体；其声明形式、参数约束与脱糖规则见 1.1 节、2.2 节与 4.2 节。任何将 overload 声明组视为"多个同名函数实体"的解读均不符合本规范。

### 5.2 使用约束

**顺序与排序**：一个声明组只承担一类依据，故只适用一套排序规则。值与结构组的书写顺序即匹配优先级，调整书写顺序将改变匹配结果，实现不得对该类子句重排（见 2.5 节）；类别组的优先级由编译期按类别的具体程度排序确定，书写顺序不影响匹配结果，实现不得按书写顺序决定其优先级（见 2.6 节与 2.7 节）。

**兜底子句应当设置**：声明组应当包含兜底子句，以承接未被更具体子句覆盖的输入。兜底子句与该组承担的依据类别一致——值与结构组用数值兜底（以通配模式 `_` 声明），类别组用类别兜底（以根节点声明）（见 2.4 节）。未设置兜底子句时，未命中任何子句的输入必须触发匹配失败。

**跨文件扩展的插入位置**：`extend` 追加的子句必须与原声明组承担同一类依据，不得改变该组的依据类别；追加的子句必须排在兜底子句之前生效；扩展者应当确认新增子句的匹配优先级符合预期，避免既有子句被遮蔽（见 3.2 节）。

**类型子句须落在根节点子树内**：类型子句所声明的类别必须位于根节点的子树之内，根节点自身视为位于其子树之内；不属于该子树的类别必须在编译期报错，不得纳入匹配集合，也不得静默排除（见 2.2 节）。`extend` 追加的类型子句同受此约束。

### 5.3 实现者须知

实现应当保证脱糖过程对声明组内所有子句一视同仁，不得因子句来源文件不同而改变其匹配优先级。跨文件扩展引入的子句，其优先级仅由合并后的声明组决定：值与结构子句的优先级取决于合并后的声明顺序，类型子句的优先级由编译期按类别的具体程度排序确定（见 2.6 节）。二者的结果与文件加载顺序无关。

### 5.4 类别匹配与值匹配必须分开

**分开原则**：一条子句的判定依据只取其一：依据形参类型（类别）者，为类别匹配子句；依据运行期值（结构模式、字段值）者，为值与结构匹配子句。同一声明组必须只承担一类依据——或全部为类别子句，或全部为值与结构子句。两类依据并列于同一声明组的写法不符合本规范，实现不得接受。

**分开的理由**：两类依据并列时，同一条匹配臂须同时承担类型分派与值分派——类型部分受 2.7 节具体程度约束，值与结构部分受书写顺序约束，两套排序规则叠加，子句的实际优先级难以从源码直接读出；兜底子句也须同时应对两侧，其认定与数量随之复杂。限制为单一依据后，每组只适用一套排序规则、只设一类兜底子句，复杂度得以收敛。

**两类均属必需时的写法**：应当分层——外层声明组只写类别子句，命中后转入对应的子函数；值匹配与结构模式匹配在子函数内部完成。子函数各自构成独立的声明组，其子句顺序仅在该子函数范围内生效，不与外层的类别排序相互影响。例如：外层声明组写成

```
overload root(v: scalarkind);
overload fn handle(v: floatkind) unit { handle_float(v); }
overload fn handle(v: integralkind) unit { handle_int(v); }
```

结构模式与字段值的子句全部移入 `handle_float` 与 `handle_int` 两个子函数；前置声明绑定 `scalarkind` 为根节点，上列两条类别子句均位于该根节点的子树之内（见 2.2 节）。

**理由**：分开之后，每一层只承担一类匹配依据，排序规则单一、可局部验证——外层按 2.7 节核对类别的具体程度，内层按书写顺序阅读优先级；跨文件扩展（见 3.2 节）的插入位置也更易判断，新增值与结构子句只影响其所属子函数，不改变外层的类别分派结果。

注：本条的分层写法与既有语言中同名函数多子句的实践一致——Erlang 的函数子句以守卫承担模式之外的附加判定，与本节将值匹配下移一层同构（见附录 B.3）。另可见函数元数（形参个数）决定函数身份，同名而元数不同者为两个不同的函数，与 2.2 节「形参个数不构成子句区分依据」互为对照。

## 7. 落地路线（Route）

overload 特性的实现按以下路线分期落地。每期独立验收、不破坏既有语义；已完成期在标题标注 ✅，进行中为 🔧，未开始为 ⬜。贯穿约束：struct / 元组字面量模式 overload 受 KI-002 影响（LLVM 后端运行期错编），**验证仅以 C 后端（`tc compile --emit-c` + clang）为基准**，除非显式标注「双后端」。

**Route 1 — 单文件值/结构模式 overload** 🔧
- 新增保留关键字 `overload` 与 `extend`（当前为保留关键字；待 L-15 语法规则法可降级为上下文关键词，以复用既有的 `when` 关键字处理惯例）。
- `overload fn name(...)` 与 `extend fn name(...)` 解析为函数子句（`FuncDecl`，以 `ia` 槽标记 1 / 2），声明组**复用既有 `desugar_func_clauses`** 脱糖为单一函数 + `match` 臂（与 `examples/clause_demo.tc` 同构，语义真源唯一）。
- 约束：`extend` 必须引用本文件内已存在的 `overload fn` 组，否则报 `T-OVL-E901`；跨文件合并见 Route 2。值/结构组按 §2.5 顺序敏感性与不可达子句沿用 `match` 既有 `T-MAT-W744` 警告。
- 验证基准：值 / 标量 / 字符串 / `when` 守卫模式 overload **双后端一致**；struct / 元组字面量模式 overload **仅 C 后端**。
- 交付：`examples/overload_demo.tc`（+`.expected.txt`）、`examples/overload_struct_pat.tc`（C 后端）、conformance pass / fail 用例。

**Route 2 — 跨文件 `extend`** ⬜
- 让 `@import` 把被引入文件中同名 overload 子句并入同一编译单元的脱糖组（需改 import 作用域与 `desugar_func_clauses` 跨来源文件分组；当前 CLI 单文件编译单元，见 `src/tc.tc` argv 门槛）。
- `T-OVL-E901` 的「本文件内」约束放宽到「可见域内」；前置声明 / 根节点绑定在跨文件场景的归属待定。

**Route 3 — 类别格分派（§2.7）** ✅
- **落地方式：静态类型分派（编译期按实参静态类型选最具体子句，不引入运行期类型标签）**。类别格在解析期 / 语义期以字符串名实现：`anykind ⊃ scalarkind ⊃ {integralkind, floatkind}`，`namedkind` 覆盖 struct / enum / flag / variant / typealias 等具名类型；`string` / `bytes` 归入 `scalarkind`（overload.md §2.8）。
- 具体程度（`parse.ovl_specificity`）：`-1`=具体类型精确匹配（最具体）；`0`=类别直接子（`integralkind`/`floatkind`/`namedkind`）；`1`=`scalarkind`；`2`=`anykind`；`<0`=不覆盖。调用点（`sema.ovl_dispatch_call`）取 `spec` 最小且唯一者，存在并列则报 `T-OVL-E903` 歧义，全部不覆盖报 `T-OVL-E901`/对应错误。
- 类型组脱糖（`parse.fc_merge_type`）：每个子句降级为内部真实函数 `__name__cK`（`ia==0`），类别子句（`anykind` 等）保留为 `ClauseDead` 模板，调用点经 `sema.ovl_instantiate` 克隆 + 类型替换单态化；另生成入口包装 `name` 调用首个具体子句。组信息登记于扁平表 `g_ovl_tg_{names,cat,func,n,tmpl}`，供 `ovl_find_group` / `ovl_group_*_at` 查询。
- 分组守卫：`desugar_func_clauses` 仅对裸子句式函数（`FuncDecl.ba==false`）分组；**类型组判定额外要求 `ia∈{1,2}`（`overload` / `extend`）**，普通 `fn` 裸子句组即使全裸带类型仍走值 / 结构组 `fc_merge`，不误入类别格（避免 `T-OVL-E981`）。
- 验证基准：**双后端一致**（`examples/overload_type.tc` 经 LLVM + C 后端对拍，输出 `i64/f64/bool/integral/scalar`）；conformance `tests/conformance/pass/p_overload_type.tc` 通过；失败用例 `f_overload_type_nomatch.tc`（`T-OVL-E903` 歧义）、`f_overload_type_purecat.tc`（`T-OVL-E982` 纯类别组需具体入口）覆盖诊断边界。

**Route 2 — 跨文件 `extend`** 🔧
- 多文件编译单元（`src.tc.tc` `@import` + `tc_load_src` 按序拼接源码、统一 `parse_unit` 填入同一 `lex.decl_list`）已落地；跨文件同名 `overload fn` / `extend fn` 子句由 `desugar_func_clauses` 按名并入同一脱糖组（与同文件一致）。
- `T-OVL-E980`（`extend` 须引用可见域内已存在的 `overload fn` 组）已落地；验证见 `examples/overload_cross_a.tc` + `examples/overload_cross_b.tc`（双文件协作，双后端）。
- 前置声明 / 根节点绑定在跨文件场景的归属细节待 `decl_import` 规则法（L-15）补全，当前不影响编译产物与门禁。

**明确不做**：真正函数重载（多个函数实体）。规范 §5.1 明确 overload 声明组脱糖后仅产生单一函数实体，本路线不偏离。

### A.1 命名考虑

本节记录本机制命名方案的评估结论。本规范现用的名称是「overload 声明组」，以下列出若干备选名称及其评估。

评估维度共五项，取值 1 至 5 分：

- 语义准确度：名称是否直接说出该机制是什么；
- 抗误读：是否会把读者引向既有的另一个概念；
- 生态兼容：既有语言传统中的用法与检索可得性；
- 体例适配：是否中性、能否充当上下文关键词、是否与条文用词一致；
- 耐久：机制语义演进后名称是否仍然贴切。

**clauses（子句）——22 分**（语义 4、抗误读 4、生态兼容 5、体例适配 5、耐久 4）

Erlang、Elixir、Haskell 与 ML 均以「子句」指称"同一函数名下、按书写顺序匹配的多条定义"，与本规范值／结构侧的顺序语义、兜底子句、未命中即匹配失败三点同构，术语中性且简短。其中 Erlang 的函数声明即由分号分隔、以句点结尾的一列函数子句构成，子句头含函数名、参数列表与可选的 `when` 守卫序列，见附录 B.3。不足在于它只覆盖机制的一半：类型子句按具体程度在编译期排序、以及子句可跨文件追加，均无法由该名称表达。

**branches（分支）——17 分**（语义 4、抗误读 4、生态兼容 3、体例适配 2、耐久 4）

若采用该名称，正文需整体回退到分支称法，迁移成本高于 clauses。名词本身亦有缺点：`branch` 在控制流与版本管理语境中出现频率过高，跨语境容易相撞；且"分支"偏向选择的一侧，无法涵盖前置声明只绑定根节点、不产生匹配臂这一部分结构。

**proto（前导声明／原型）——16 分**（语义 3、抗误读 2、生态兼容 4、体例适配 4、耐久 3）

在 Raku 中 `proto` 正是"被安装的实体加候选列表"的头，与本规范由前置声明绑定根节点的结构几乎一一对应。问题是 prototype／原型在脚本语言语境中负载极重，读者易先联想到对象原型；且 `proto` 指头不指臂，以部分代整体。

**multi（多重）——14 分**（语义 3、抗误读 1、生态兼容 5、体例适配 3、耐久 2）

Raku 的 `multi sub`、Clojure 的 `defmulti` 与 Julia 的多重分派已将该词固定为"一组同名声明"，检索认知度最高。但它把读者预期引向运行期多重分派，与本规范编译期定序、单一实体、运行期不再比较类型的立场方向相反，开局即引入一次误读，并暗示存在多个实体。

**pseudooverload／softoverload（自白式）——14 分**（语义 5、抗误读 5、生态兼容 1、体例适配 2、耐久 1）

名称本身即提示"这不是重载"，与本文开篇提出的矛盾点、5.1 节的结论完全同向，消除误读最为彻底，对外辨识度也最高。但规范用词宜中性，"伪／软"把价值判断写入了标识符；且其语义与"重载"强绑定，机制一旦演进为真正的类型分派，该名称立即失效。

**采纳结论**：经评估采纳 `clauses` 作术语。`overload` 作为上下文关键词保持不变，一条 overload 声明即一个子句，正文中「分支」的称法统一替换为「子句」；`extend` 的用法与拼写不变。本项变更仅涉及术语称法，不改变任何语法形式与语义规则，也不改变示例中的书写方式。第 6 章参考文献中的「分支」指决策树的分支，属另一含义，不在本次替换范围内。

### A.2 适用性说明

在输入可由有限组字段值组合穷举、且各组合的处理逻辑彼此独立的场景下，overload 声明组的写法比真正的重载更为直观：匹配条件与处理逻辑在同一处声明，无需借助类型系统构造多个类型。

在输入取值空间开放、或匹配条件依赖运行期计算的场景下，使用 overload 声明组可能引入覆盖风险：新增子句可能遮蔽既有子句，或与既有子句产生非预期的优先级关系。此类场景需审慎评估子句顺序与兜底策略（见 2.5 节）。

## 附录 B　背景资料

### B.1 上下文关键词与规范性措辞

C# 语言中的关键字与上下文关键字（contextual keywords）：保留关键字不得用作标识符，上下文关键字仅在有限的程序上下文中具有特殊含义、可在该上下文之外用作标识符；随着新关键字被添加到语言中，它们以上下文关键字的形式加入，以避免中断在早期版本中编写的程序。示例见 `get`、`set`、`var` 与 `await`（`await` 仅在声明为 `async` 的方法内部被视为关键字）。

Kotlin 语言中的硬关键字与软关键字（soft keywords）之分：硬关键字在任何情况下均不得用作标识符，软关键字仅在其适用场景中不得用作标识符，其他场景中可以用作标识符。

Rust 语言中新增关键字的过渡策略：先在某一版本中给出警告、代码仍可编译，再于后续版本转为编译错误；另提供原样标识符（raw identifier）作为逃生出口。

C++ 语言中引入新关键字的兼容性考量：既有代码规模庞大，向语言添加新关键字会使将新词用作变量或用户定义名称的程序中断，故仅于必要时引入，并以代码检索结果评估冲突可能。

规范文本的措辞体例：技术标准中以一组固定用词表达需求级别（MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL），并以字形区分规范性用法；该用词体系仅应当用于涉及互操作性或防止潜在危害的场景。

注：1.1 节将 overload 认定为上下文关键词，1.2 节将其他上下文关键词排除于范围之外，1.3 节的四级措辞取自这一支。上文所列语言的实现表明：将新词以上下文关键词形式引入，是在既有代码可继续编译的前提下扩充语言的手段；硬保留关键字集合越小，语言越依赖原样标识符一类的逃生机制。

### B.2 脱糖与语义保持

脱糖（desugaring）的一般原理：语法糖的语义由其所代表之物的语义定义，脱糖因此是在构造上保证糖具有正确语义的变换；变换由表层层语言（surface language）指向核心层语言（core language），通常作用于抽象语法树。

脱糖契约：一次正确的脱糖变换应当保持三项属性——语义保持（脱糖后的形式产生与原始形式相同的结果）、类型保持（原始形式通过检查者，脱糖后的形式以相同方式通过检查）、错误位置保持（诊断信息仍指向原始源码位置）。该变换是纯机械的，仅重排、重构或替换语法节点，不进行语义分析、类型推导或优化。

脱糖的动机：若不脱糖，每个下游阶段均须同时处理同一构造的糖形式与非糖形式，维护路径数随糖变体数与阶段数相乘；脱糖将其折叠为对每种糖的一次翻译加上各阶段对核心形式的处理。

注：4.1 节至 4.4 节的脱糖规则取自这一支。其中错误位置保持一项，要求 2.7 节判定规则四的歧义诊断与 2.5 节不可达子句的警告报告到原始声明所在位置。

### B.3 子句顺序、穷尽性与不可达检查

Erlang 语言中的函数声明与函数子句（function clause）：函数声明由分号分隔、以句点结尾的一列函数子句构成；子句头含函数名、参数列表与可选的以 `when` 开始的守卫序列；匹配自第一条子句起顺序扫描，首个模式匹配成功且守卫为真的子句被执行，无命中则报 `function_clause` 错误。函数的元数（形参个数）参与构成函数身份，同名而元数不同者为两个不同的函数。

模式匹配的穷尽性与冗余检查：检查所捕获的问题包括缺失分支（存在未被覆盖的取值）、不可能分支（取值已被移除）与永远无法到达的冗余分支（已被其前的分支覆盖）。判定所依据的中心问题是：给定已有模式集合，一个新模式是否可能匹配到此前任何模式均未匹配的取值；对通配模式施以该判定，即可判断整体是否穷尽。

检查的适用范围：一切可以书写模式的位置，包括匹配表达式、条件绑定、解构绑定与函数参数。

注：2.5 节不可达子句的警告与 5.2 节未命中即匹配失败的判定取自这一支；5.4 节的分层写法可与其中 Erlang 子句与守卫的分工相互对照。
