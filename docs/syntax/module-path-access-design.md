## 1. 已裁定模型（用户 2026-10-07）

> **模块是一等值（first-class module value）；命名空间 = `const` 绑定名，不是路径末段。**
> 即 Zig 模型：`const a = @import("src.d.e");`，此后 `a` 就是模块 `src.d.e` 的命名空间。

由此推出：

1. **文件级（顶层模块）命名空间**：`@import("src.d.e")` 与 `@import("src.x.e")` 是两个不同模块，
   由 importer 自行绑定到不同名字（`de` / `xe`），**互不干扰**。
   同一模块内两个同名顶层变量应当非法 —— ✅ **该规则现已生效**（M1.1 `T-NAM-E405` 同模块内顶层符号重定义、
   M1.2 `T-MOD-E562` 模块末段同名，均已推 main），导入绑定撞名当前**报错**而非 errors = 0。
2. **类型级命名空间**：`struct` / `variant` / `enum` / `union` 亦为命名空间，可携带关联常量，
   访问路径形如 `a.Point.O`（模块 → 类型 → 成员）。
3. **符号查找收窄**：`def_lookup` 只应在**该绑定对应的那个模块**内查找，查不到即报错。

✅ 该模型**在设计层面确实消灭**了原「末段同名静默合并」问题 —— 绑定名由 importer 自选，无碰撞可能。

## 2. 异议一：模型对，但实现尚未落地（关键）

⚠ **当前实现里，`const` 绑定名的目标登记的仍是「路径末段」，不是完整路径**：

```t
// sema.tc:9247
g_modval_set(name, last_segment(path));    // ← 第二参数是末段
```

### 实测证据（2026-10-07）

工程：`src/d/e.tc`（`pub fn deep(x)=x+100`）、`src/x/e.tc`（`pub fn deep(x)=x+777`）

```t
const de = @import("src.d.e");
const xe = @import("src.x.e");
@main fn main() i32 { println(i2s(de.deep(10))); println(i2s(xe.deep(10))); return 0; }
```

| 检查项 | 结果 | 期望 |
|---|---|---|
| `tc check` | 0 error / 3 warning | — |
| IR 符号 | **`@e__deep` 仅 1 个** | 应有两个（`src_d_e__deep` / `src_x_e__deep`） |
| `tc run` | **Segmentation fault** | 110 / 787 |

两个模块都被重整为 `e__deep`，**撞成同一符号**；`de` 与 `xe` 两个绑定名同时指向 `e`。
⇒ **语义层「命名空间 = 绑定名」成立，身份层却仍塌陷为末段**。

### 必改点

| # | 位置 | 现状 | 改为 |
|---|---|---|---|
| 1 | `sema.tc:9247` | `g_modval_set(name, last_segment(path))` | `g_modval_set(name, path)` — 登记**完整路径**作模块身份 |
| 2 | `sema.tc:10518 def_lookup` | 按 alias 线性扫，返回**首个**命中（静默遮蔽根因） | alias 维度 = 完整路径身份（唯一），命中即唯一 |
| 3 | `sema.tc:10509 mangled_name` | `alias__name` | 与 1/2 **必须同时改**；只改其一会导致符号名与查找键不一致 |
| 4 | `sema.tc:6127–6163` | `member` 脱糖取 `last_segment` 作 key | 改取绑定名映射到的完整路径 |
| 5 | `sema.tc:10146 handle_one_import` 注释 | 「Go 风格末段」 | 随模型更新（声明式 `@import` 的别名规则也需一并裁定） |

## 3. 异议二：`const` 形态的 W402 代价（历史已现，须先解决）

`const de = @import(...)` 触发 **`T-NAM-W402` constant name 'de' should be UPPER_SNAKE_CASE**（实测 2 条）。

这正是 2026-08 形态三易其稿时**放弃 const 形态的精确原因**（`cst-design-v2.md:1608–1610`）：

| 趟 | 形态 | 结果 |
|---|---|---|
| 一 | 裸名 | 新增 4 条 `W561` |
| 二 | `const cst = @import(...)` + `cst.` 限定 | 消掉 W561，但新增 4 条 `W402` ⇒ **净零** |
| 三 | 声明式 `@import(...)`（别名 = last_segment） | **528 warning**，最终形态 |

⇒ 推 const 形态必然让 `T-NAM-W402` 常驻。当前 `src/` 的 62 条 W402 中大部分正来自既有的
`const base = @import("src.base")` 写法；迁移后再增 61 条（合计约 123 条）。

### 3.1 ⚖ 裁定 2 改判：**不豁免**（用户 2026-10-07）

用户裁定：撞名/命名规范问题由用户改代码解决，属普通错误，**不为模块绑定开豁免后门**。

**采纳后的两个后果，须二选一并写进迁移约定**：

| 选项 | 绑定名形态 | 调用点改动 | W402 |
|---|---|---|---|
| **甲（默认）** | 保留末段小写 `const base = @import("src.base")` | **0 处** | 常驻 ~123 条（warning，不阻断 gate；基线已有 528 条 warning） |
| **乙** | 改 UPPER `const BASE = @import("src.base")` | **8494 处** `base.foo()` → `BASE.foo()` | 0 |

实测确认两条前提：
- `const M = @import("src.m")` + `M.hi(10)` → **0 error / 0 warning**（UPPER 名确实消掉 W402）。
- W402 是 **warning**（`T-NAM-W402`，`base.tc:4630`），不进 `errors` 计数 ⇒ 不影响 gate 通过判据。

⇒ **建议取甲**：W402 是告警而非错误，123 条对 528 条基线只是增量；取乙要付 8494 处改动，
与 §10.2「调用点零改动」的全部收益相抵。**若选乙，本文档 §10 的迁移成本结论须整体作废。**

## 4. 异议三：`a.Point.O` 是未实现的新特性，应单独立项

实测（2026-10-07）：

```t
struct Point { const O: i64 = 7; x: i64; y: i64; }   // → T-PAR-E101 "expected type"
```

- **struct 关联常量**（`struct X { const O = ...; }`）：❌ **不支持**，解析期即报错。
- **三级路径 `a.Point.O`**：❌ **不支持** —— 多级 `member` 解析缺失，
  与 `src.hello.greet()` 报 `T-SEM-E201 未定义的标识符 src` 同因
  （`sema.tc:10851` Pass 1 与 `6127` 只认单级 `member`）。

⇒ 建议：**struct/variant/enum/union 命名空间 + 关联常量单独立项**，不塞进本 epic，
   否则 epic 边界失控（本 epic 只负责「模块身份」，类型级命名空间是独立的能力缺口）。

## 5. 连带风险：同一模块被重复绑定

用户模型下 `const a = @import("src.d.e"); const b = @import("src.d.e");` **合法**（名字不同）。
须确保模块**只被内联一次**：顶层 `var` 初始化不重复、函数不重复定义、无重复发射。
§2 实测的段错误可能与此相关 —— 建议立为一条显式不变量并加负向测试。

## 8. IR 符号名编码规范（实测，2026-10-07）

### 8.1 点号方案不可行：双后端分歧（实测）

同一符号名 `@src.d.e.deep` / `src.d.e.deep`，分别喂给两个后端：

| 后端 | 结果 | 证据 |
|---|---|---|
| **LLVM** | ✅ 接受 | `clang -c dot.ll` 编译通过（`@src.d.e.deep` 定义 + call 均 OK） |
| **C** | ❌ 拒绝 | `expected ';' after top level declarator`；调用侧 `member reference base type 'int64_t' is not a structure or union` |

⇒ 点号会造成**双后端符号名分歧**，而双后端对拍是 gate 的核心纪律 ⇒ **不可接受**。
对照组：`@src_d_e__deep` 在 LLVM 亦通过。

### 8.1.1 逃生舱：`asm` 符号别名（实测可行，但不采纳）

C 语言可用 GCC/Clang 扩展把**导出符号名**改为任意字符串，而源码内仍用合法 C 标识符：

```c
int64_t deep_impl(int64_t x) asm("src.d.e.deep");
int64_t deep_impl(int64_t x) { return x + 100; }
```

实测：`clang -c`（MSVC target）**接受**，且目标文件中符号名确为 `src.d.e.deep`（二进制 grep 命中），
`deep_impl` 已被完全替代。

**不采纳的理由**：

1. **生态绑定**：`asm` 符号别名是 GCC/Clang 扩展，**MSVC 不支持**。项目 C 产物虽由 clang 编译，
   但链接走 MSVC 生态（`out/<mode>/deps/t_runtime.lib`），把语义绑死在编译器扩展上不可取。
2. **静默错位风险**：符号名与源码名分离，一旦某处漏写 `asm` 声明即静默产生错名，
   而双后端对拍不一定能立刻暴露。
3. **与 `@c_export` 冲突**：`@c_export` 的设计目标正是给 C 消费者**可读的 clean 名**
   （`reference.md` §2241–2252）；导出无法直接书写的点号名与之背道而驰。
4. **头文件侧同样要处理**，C 消费者 `#include` 后仍无法按名调用。

⇒ 结论：**坚持 C 后端 ⇒ 符号名层放弃点号**。`src_d_e__deep` 是唯一稳妥解。

### 8.2 `.` 与 `_` 是否等价？

**在 IR 层：等价，且都不携带层级语义。**
LLVM 标识符规则为 `[-a-zA-Z$._][-a-zA-Z$._0-9]*` —— `.` 与 `$` 只是**合法字符**，
LLVM 不解释其含义；`@src.d.e.deep` 就是一个扁平字符串，LLVM 眼里没有"层级"。

**在 C 层：不等价** —— `.` 非法标识符字符。

**在源码层：不等价** —— `.` 是 member 访问运算符（**携带**层级语义），`_` 是普通标识符字符。

> ⚠ **认知陷阱**：IR 里的点「看起来像层级」，实际不是。这正是点号方案最危险之处——
> 它会诱导后来者以为可以从符号名反解出模块结构，而实际上切不开。

### 8.3 歧义：两种编码都有，根因是扁平化本身

- `src.d.e.deep`：`src.d` 模块 + `e.deep`？还是 `src.d.e` 模块 + `deep`？**无约定则无法切分**。
- `src_d_e__deep`：靠 `__` 作界；但路径段若自身含 `__`（如 `my__mod.tc`）同样歧义。

⇒ 真正的问题不是「点 vs 下划线」，而是**扁平化编码丢失结构**。

### 8.4 推荐写法

1. **首选 `src_d_e__deep`（下划线）** —— 唯一双后端都接受的形态。
   注意分界是**双**下划线 `__`（模块身份 ‖ 符号名），单下划线是路径段分隔符。
2. **更强建议**：内部保留**结构化身份**（路径 + 符号名二元组），扁平化只在**发射瞬间**做；
   永远不要依赖从 IR 符号名反解结构。
3. **若要可逆且无歧义**：长度前缀编码（Itanium / Rust 风格，如 `ZN3src1d1e4deepE`），
   或转义编码（`_` → `__`，段分隔用单 `_`）。代价是符号名更长、可读性下降。
4. **体积代价可忽略**：符号名平均多约 4 字符；对 `out/dbg/tc.ll` 48MB / `tc.c` 2.4MB 而言增幅 < 1%。

## 9. 裁定决议（2026-10-07 用户拍板）

| # | 裁定项 | **裁决** | 关键依据 |
|---|---|---|---|
| 1 | 导入形态 | **唯一方案 `const <name> = @import("...")`**；声明式 `@import("M");` 与 `as` 别名**一并废弃** | §11.1 / §9.2 实测；`as` 存量仅 3 处（2 注释 + 1 fail 测试） |
| 2 | W402 处理方式 | **不豁免** —— 保持 `T-NAM-W402` 现状（warning 级）；用户自行改名或接受告警 | 用户裁定：模块内不可能有同名变量，撞名用户改代码即可，属普通错误 |
| 3 | 重整名形态 | **完整路径扁平** `src_d_e__deep` | §8 实测：唯一双后端可接受；确定性优于「仅碰撞退化」 |
| 4 | §4 类型级命名空间 | **立项** | 排在模块 epic 之后（多级 `member` 解析与模块身份共享地基） |

### 9.0 ⭐ 裁定 1 收窄：`as` 语法一并废弃（用户 2026-10-07 最终裁定）

> **导入只有一种写法：`const <name> = @import("<完整路径>");`**

**用户论据**：底层 IR 的 ABI 已统一为 `@src_d_e`（完整路径扁平，与裁定 3 一致），
故**绑定名只是源码层的局部名字**，模块身份由完整路径承载。`as` 即便保留，也只能朝
「兼容 `const e = @import("src.d.e")`」的方向演化 —— 既然如此，没有保留必要。

**语法澄清（实测）**：用户指出的正确形式 `@import("src.d.e") as e`（`as` 在**括号外**）
当前**并不被解析**：

```t
@import("src.m") as mm;      // → T-PAR-E101 "expected declaration name but found as"
@import("src.m" as mm);      // → 0 error（现有实现在括号内，见 parse.tc:2371 注释）
```

⇒ 废弃 `as` 只需删**括号内**那一种实现形态；括号外形态从未存在，无迁移成本。

**废弃成本实测**：全仓 `as` 存量 **3 处** —— `src/parse.tc:2371`（注释）、
`lib/std/rc/cst.tc:23`（官方用法注释）、`tests/conformance/fail/f131_import_conflict/main.tc:3`
（测 `:: fa as x, fb as x` 冲突，期望 `T-MOD-E560`）。零生产代码依赖。

> ⚠ `f131` 测的是**选择性导入别名冲突**（E560），不是模块绑定撞名（E552）。
> 废弃 `as` 后该测试须**改写**为 const 形态的等价负向用例，不可直接删除（见 §9.2）。

**const 形态优于 as 形态的决定性理由**（裁定 3 成立后才成立）：
`as` 的重整名取**别名**（实测 `@de__deep` / `@xe__deep`），即符号名依赖 importer 的局部命名；
`const` 加重整名取**完整路径**（`@src_d_e__deep`）后，符号名与 importer 无关
⇒ 跨文件用不同绑定名导入同一模块不会符号分裂。**这是「const 更正确」的技术根因。**

### 9.2 ⚠⚠ 裁定 2 的前提当前**不成立**：同名绑定不报错（实测）

用户裁定 2 的论据是「一个模块里不可能出现两个同名的变量，用户必须改代码，这是一个错误」。
实测三种形态下**编译器均不报错**：

| 用例 | 代码 | `tc check` | 实跑 |
|---|---|---|---|
| u6 | `const e = @import("src.d.e"); const e = @import("src.x.e");` | **errors = 0**（仅 2×W402） | **`clang link failed`**（产物 2× `@e__deep` 重复符号） |
| u7 | `@import("src.d.e" as e); @import("src.x.e" as e);` | **errors = 0** | 输出 **110**（静默取先登记者） |
| u8 | `@import("src.d.e"); @import("src.x.e");`（两个都默认绑 `e`） | **errors = 0** | 输出 **110**（静默取先登记者） |

> ✅ **2026-10-07 已修（路线图 M1.1 + M1.2）**：上表三行当前均报错，不再是静默行为 ——
> u6 → `T-NAM-E405`（同模块内顶层符号重定义，M1.1）；
> u7 / u8 → **`T-MOD-E562`**（两个模块路径末段同名，M1.2）。
> ⚠ **M1.2 补出的一条新事实**：`const` 形态**也不能**区分末段同名模块 ——
> `const EA = @import("src.d.e"); const EB = @import("src.x.e");` 的**内部**模块身份仍取末段
> （`modval_load` 传 `last_segment(rest)` 给 `handle_one_import`），故同样触发 `T-MOD-E562`。
> ⇒ 裁定 1「唯一形态 = `const`」要真正具备区分能力，**必须等 M2 完整路径身份落地**；
> 在此之前 `@import("路径" as 别名)` 是唯一能同时导入两个末段同名模块的写法，
> 建议保留到 M2 完成再移除（与裁定 1 的**终态**不矛盾，只是时序后置）。

⇒ 「模块内不可重名」在**当时实现里不是事实，是待补的诊断**（现已补完，见上）。
若只改语法而不补这条，撞名将退化为：const 形态下链接期爆 duplicate symbol、
声明式形态下静默取先登记者 —— **又一次「隐式规则导致静默错编」**（本项目已栽三次）。

**必须新增**（编入 P2a）：同一模块内两个导入绑定同名 ⇒ 报重定义错误
（可复用 `T-MOD-E552` 的语义，或新开码位）。这条是裁定 2 能够成立的**前提**，不是可选项。
> ✅ 已落地为两条：**`T-NAM-E405`**（同模块内顶层符号重定义）+ **`T-MOD-E562`**（模块末段同名）。

> ⦁ 附带观察：u6/u7/u8 均额外冒出一条 `T-MAT-W744`（「match arm is unreachable」），
> 但这些文件里没有任何 `match` —— 疑似诊断状态串扰，值得单独立 KI 核查（C 级）。

### 9.1 裁定 3 的连带不变量（必须写死）

> **重整名基于「模块身份」（完整路径），绝不基于「绑定名」。**

理由：新模型下 `const a = @import("src.d.e"); const b = @import("src.d.e");` 合法。
若重整名取绑定名，同模块会产生两套符号（§5 的段错误即此类症状）。
取完整路径 ⇒ 两个绑定映射到同一套符号，与 §5「只内联一次」自洽。

- 长度复核（实测）：现有最长 `module__sym` 符号名 **44 字符**
  （`comptime_fold__comptime_has_runtime_ref_list`），加 `src_` 前缀后 **48**，仍 < C99 保证的 63。
  ⇒ 扁平化无长度风险（深层模块 `src/a/b/c/d/e.tc` 前缀开销 15 字符，仍安全）。

## 10. 裁定 1 实施方案：声明式 → `const` 迁移（全实测）

### 10.1 存量盘点（2026-10-07 扫描 521 个 `.tc` 文件）

| 形态 | 数量 | 分布 |
|---|---|---|
| `const <n> = @import("...")` | **62** | 全在 `src/` |
| 声明式 `@import("...")`（纯） | **44** | `src/ 15`、`lib/`、`tests/`、`examples/` |
| 选择性 `@import("..." :: a, b)` | **17** | `src/` 为主 |
| `pub @import(...)` 重导出 | **0**（仅注释与实现残留） | `lex.tc:913`、`sema.tc:10137/10151/10546` |

### 10.2 ⭐ 决定性数据：迁移成本 ≈ 61 行，调用点 **0 改动**

1. **现有 62 处 `const` 绑定，绑定名 == 路径末段，62/62 全一致**（无例外）。
2. 现有 8494 处限定访问写法形如 `base.foo()` —— 恰是「末段名 + member」。
3. ⇒ 把 `@import("src.base")` 机械改写为 `const base = @import("src.base")` 后，
   **所有 `base.foo()` 调用点语义不变、无需修改**。

**冲突扫描（521 文件）**：同文件内「声明式末段」与「已有 `const` 绑定名」撞车 = **0**；
声明式之间末段同名 = **0**。⇒ 61 处全部可安全机械迁移。

### 10.3 ⚠ 唯一障碍：`const` 形态不支持 `::` 选择性导入（实测）

```t
const a = @import("src.a" :: f1);   // → T-PAR-E101（解析期即拒）
@import("src.a" :: f1);             // → 0 error（现状可用）
```

17 处选择性导入**不能**直接加 `const` 前缀。两个处置方案：

| 方案 | 内容 | 评价 |
|---|---|---|
| **A 改完整导入** | `const sema = @import("src.sema")`，丢弃白名单 | 实测**产物零差异**（见下） |
| **B 扩展 parse** | 支持 `const m = @import("src.m" :: a, b)` | 保留显式契约，改动限于 parse 一处 |

**实测依据（支持 A 的零代价结论）**：`src/big.tc` 含 `used1/unused1/unused2` 三个 pub fn，
只调用 `used1`：

| 导入形态 | `.ll` 体积 | 产物中 `unused1/unused2` |
|---|---|---|
| 选择性 `:: used1` | 4038 B | **在**（30 处引用） |
| 完整 `const big = ...` | 4073 B | **在**（30 处引用） |

⇒ **选择性导入从不具备裁剪作用**，它只是「可见性白名单」（限制可引用符号），不影响产物。
故方案 A 的产物代价为零，代价仅是丢失白名单的文档性契约。

**依赖安全性**：src 模块 import 图环检测 = **0 环**（DAG）⇒ 17 处改完整导入不会引爆循环依赖。

### 10.4 建议：走 B（扩展 parse），而非 A

虽然 A 零代价，但白名单是**显式契约**——它让读者一眼看出「本文件只依赖 sema 的哪两个符号」，
且能在误用时给出诊断。本项目已在「隐式规则导致静默错编」上栽过三次
（模块末段合并、前导点变体全局反查、enum 成员名不校验），应优先选显式契约。
B 的改动面仅 parse 一处产生式 + `handle_one_import` 的参数处理。

> ⚠ 若选 A，须同步删除 `lex.tc:913` / `sema.tc:10137,10151,10546` 的 `pub @import` 重导出实现
> （存量 0，属死代码）。新模型的重导出形态是 `pub const x = @import(...)`。

### 10.5 迁移后形态示例

```t
// 现状（将废弃）
@import("src.base");
@import("src.tir_to_ll" :: tir_to_ll_emit, g_has_main, build_tlib);

// 迁移后（绑定名 = 末段，调用点零改动）
const base = @import("src.base");
const tir_to_ll = @import("src.tir_to_ll" :: tir_to_ll_emit, g_has_main, build_tlib);
```

调用点 `base.node_kind(...)` / `tir_to_ll.tir_to_ll_emit(...)` —— **均无需修改**
（已实测确认选择性导入的现有用法就是 `tir_to_ll.tir_to_ll_emit(...)`，见 `src/tc.tc:710`）。

## 11. 文档自审：遗留问题（2026-10-07 二次审查）

> 本节记录**本文档自身的缺陷**。A 级会推翻结论，B 级会漏掉破坏面，C 级是论证不严谨。

### 11.1 ⭐⭐ A 级：全文档遗漏了 `@import("path" as alias)` 语法（动摇裁定 1）

**事实**：声明式 `@import` 支持 `as` 自定义别名，且是**官方用法**
（`lib/std/rc/cst.tc:23` 明写 `@import("std.rc.cst" as cst);`）。§2/§3/§10 的整套论证
——「要拿到绑定名命名空间就必须改 const 形态，但要付 W402 代价」——**建立在未发现该语法之上**。

**实测对照（`src/d/e.tc` deep=+100、`src/x/e.tc` deep=+777）**：

| 能力 | `@import("src.d.e" as de)` | `const de = @import("src.d.e")` |
|---|---|---|
| 自定义命名空间名 | ✅ `as de` | ✅ |
| **区分末段同名模块** | ✅ 实跑 **110 / 787**，产物 `@de__deep` + `@xe__deep` 两套 | ❌ 撞成单个 `@e__deep`、**段错误** |
| W402 | ✅ **零触发** | ❌ 每个绑定一条 |
| 同模块重复导入保护 | ✅ **T-MOD-E552**（含跨文件不同别名：亦报 E552） | ❌ 无 |
| 选择性 `::` | ✅ 支持 | ❌ `T-PAR-E101` |

⇒ **`as` 形态在所有维度上均优于 const 形态**，且已实装。
用户的裁定意图「命名空间 = 绑定名」用 `as` 即可满足，**无需迁移到 const、无需 P1 豁免、无需改 parse**。

✅ **已裁定（用户 2026-10-07，见 §9.0）：`as` 不保留，走 const 唯一方案。**

用户论据：底层 IR ABI 已统一为 `@src_d_e`（完整路径扁平），绑定名只是源码层局部名字；
`as` 即便保留也只能朝兼容 `const e = @import(...)` 的方向演化，故无保留必要。
该判断**推翻了本节「as 成本显著更低」的结论**——因为那一栏的「区分末段同名模块 ✅」
依赖的是**重整名取别名**，而裁定 3 后重整名改取**完整路径**，此时 `as` 相对 `const` 的优势
只剩「零 W402」一项（§9 裁定 2 已决定不豁免，该项随之失效）。

⚠ **废弃 `as` 的代价（须在 P2a 补齐，否则是静默错编）**：
`as` 形态自带的 `T-MOD-E552`（同模块重复导入/别名冲突保护）在 const 形态下**不存在**
—— 实测两个 `const e` 指向不同模块：`tc check` **errors = 0**，实跑 **clang link failed**
（产物 2× `@e__deep` 重复符号），详见 **§9.2**。
即：废弃 `as` 时**必须把 E552 的等价保护移植到 const 形态**，否则等于拆掉一道防线。

### 11.2 ⭐ A 级：§8.4 体积估算错误（<1% 实为 5–10%）

实测符号名占比与完整路径化后的增量：

| 产物 | 大小 | 符号名占字节 | `+src_` 后总增幅 |
|---|---|---|---|
| `out/dbg/tc.ll` | 48 MB | **44.7%** | **+8.60%**（+4.1 MB） |
| `out/dbg/tc.c` | 2.4 MB | 20.0% | +5.22% |
| `out/dbg/tc.h` | 126 KB | **47.0%** | **+9.83%** |

符号名在 `.ll`/`.h` 中占近半字节 ⇒ 增幅是文档原估的 **10 倍量级**。
这会影响编译时间、IR 快照体积与自举产物大小，是裁定 3 的真实代价。

### 11.3 B 级：负向测试与 conformance 的破坏面（§10 迁移清单未单列）

`tests/conformance/fail/` 下 5 个测试专门测 import 诊断，**全部使用声明式语法**：

| 测试 | 期望诊断 | 迁移后实测 |
|---|---|---|
| `f123_import_empty_path` | `T-MOD-E559` | 待测 |
| `f54_ext_import_not_found` | `T_IMPORT_NOT_FOUND` | 待测 |
| `f55_module_private` | `T_MODULE_PRIVATE` | ✅ 保持，**新增 W402** |
| `f56_module_no_symbol` | `T_MODULE_NO_SYMBOL` | ✅ 保持 |
| `f_export_on_import` | `T-MOD-E550` | ⚠ 测的正是 `pub @import` 重导出，**裁定 1 删除该机制后此测试失效，需重写或删除** |

另有 conformance 正向测试 **`p42_std_import.tc`**（历史记录点名它用声明式 `@import("std.math")`）。

⇒ 迁移不能「机械替换后了事」，这 6 处须逐个验证诊断码是否保持。

### 11.4 B 级：P0 会让快照**失去等价性判据能力**

`tests/ir_baseline.json` 存的是 **md5**（117 targets / 354 entries，含 `::c` `::h` `::ll` `::dev` 四种形态）。
P0 改名后 **354 个 entry 全部变化** ⇒ 无法用 diff 判断「是否只改了符号名」。

⇒ P0 的等价性判据**必须**改用 **同源码对拍**（变更前 seed 产物 vs 新 g1 产物，逐字节），
快照只能用于「重录后防回归」，不能用于「证明本次等价」。**✅ 已闭环（2026-10-08）**：M2/M4 实施期
实际采用「同源码对拍 + 对 `src/tc.tc` 自身逐字节对拍」作为等价性判据，IR 快照仅在重录后防回归使用；
§7 的 P0 行「⚠ 全量漂移（0 NEW/0 GONE 判据）」即对应此处置。

### 11.5 B 级：库搜索路径导入的「完整路径」是单段（裁定 3 的漏洞）

首段非 `src` 的导入走**库搜索路径**（`<工程根>/lib|libs`、入口目录 `lib`、`out/lib`），
路径身份就是**裸名单段**：

```t
const repl = @import("repl");        // src/tc.tc:28 → lib/repl.tc
@import("json"); @import("colony");  // 裸名
```

实测 `@import("lib.foo")` → **T-MOD-E550 未找到** ⇒ 库导入不接受路径前缀，其"完整路径"只能是单段。
⇒ 裁定 3 下 `repl__x` 这类库符号名**没有命名空间保护**，是已识别的已知限制（与「末段静默合并」
同构，只是换到库层级）。**处置（2026-10-08）**：当前 `lib/` 下库模块（repl / json / colony / std.* 等）
无单段同名冲突，故未观测到相撞；该漏洞仅在「`.tlib` 静态库引入两个单段同名库」时触发，届时须
补库层别名保护或单段唯一性诊断。记为**已知限制，当前可接受**，不阻塞 epic 收尾。
