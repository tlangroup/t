# ECS entity 降解方案设计（`#entity` → SoA 列存）

> 关联：`docs/design/set-ops/DESIGN.md`（类型位 `&&` / `||` 集合运算，Step 2 已写好同款路线）、
> `docs/design/struct-modifiers/DESIGN.md`（D10 generic struct 未实现、`#id` 自定义修饰通道）、
> `docs/design/open-variant/DESIGN.md`（overload / extend 开放组）。
> 范围：**语法走降解器，约束走 concept**。本文档只规定两工程的分工与契约，不规定 ECS 运行时的算法细节。

---

## 0. 一句话总纲

```
#entity struct PlayerArchetype = Position && Health && ?PoisonData && ?BurnData;
```

这一行是**规格**（第二维）。降解器把它翻译成**存储表示**（每组件一列的 SoA 结构体）。
根 tc 只做三件事：**解析 `&&` 与 `?`**、**未认领即报错**、**对降解产物做常规类型检查**。
根 tc 对 ECS 一无所知。

---

## 1. 三层契约（本方案的承重墙）

| 层 | 内容 | 归属 | 是否上下文相关 |
|---|---|---|---|
| **规格层** | `A && B && ?C && ?D` 类型位表达式 | 用户书写 | — |
| **类型层** | `?T` = 类型构造器，语义「可能有 / 可能没有」 | **核心语言（tc）** | 上下文无关 |
| **表示层** | 稀疏（`SparseSet<T>`）还是内联（可选 tag / NPO） | **降解器（ECS 工程）** | 由降解上下文决定 |

三条由此成立：

1. **`T?` 的核心定义只能规定"可能没有"，不能规定表示。** NPO / 内联是默认表示，`#entity` 只是换掉它。
2. **换表示不改用户代码**——行视图恒为 `poison: PoisonData?`，用户只对行视图编程。
3. **降解正确性的判据就是行视图**：降解产物 + 访问器，必须能对每一个 `?` 成员提供 `T?` 语义。

### 闭环

`?T`（选择）→ 降解 → `SparseSet<T>`（事实）。
这与「单态化 = 把选择翻译成事实」是同一个动作的第三次出现：类型参数上叫单态化、extend 上叫 seal、可选上叫稀疏化。

## 2. tc 工程需要做的

### 2.1 已具备（零改动）—— 2026-10-19 用 `out/rls/tc.exe check` 逐个探针实测

| 能力 | 探针结论 |
|---|---|
| 切片字段 `struct P3 { a: []Position; b: i64; }` + 数组字面量 | ✅ 0 error |
| `[]i32` + `[1,2,3]` + `@size_of([]i32) == 32` | ✅ 0 error |
| 泛型函数体内 `var v: []T`（T 为类型参数） | ✅ 0 error |
| 位置匿名元组类型 `.{i64, i64}`；返回类型位 `.{i64, []i32}` | ✅ 可解析 |
| `comptime fn f(comptime T: type) type` | ✅（`tests/conformance/pass/p44_typeval_generic.tc`） |
| **类型位 `A && B`** | ✅ 可解析，仅在值使用处报 `expected <unknown>` ⇒ **今天就能承载降解** |
| `concept` 声明 + `concept_satisfied` | ✅（`p41_generic_concept_ok.tc`） |
| generic 函数 `fn f(T: HasName, x: T)` + 单态化 | ✅ |

### 2.2 必须新增（核心语言）—— 按优先级

| 编号 | 项 | 现状 / 证据 | 说明 |
|---|---|---|---|
| **G1** | **generic struct**：`struct Vec<T> { ... }` | ❌ `struct Box(T)` / `struct Box(T: HasName)` → `T-PAR-E101 期待 LBrace，实际读到 (`；D10 明文"本次不实现" | **唯一硬阻塞**。ECS 是它的第一个刚需用例。泛型函数 + 单态化基础设施已实装，只需把类型参数放到 struct 声明上并支持类型位实例化 |
| **G2** | **具名字段匿名结构体类型** `.{ pos: Vec<Position>, ... }` 或退化方案"降解器直接填字段列表" | ❌ `{x: i64}` / `.{x: i64}` 在类型位均 `T-PAR-E101`；仅位置式 `.{T1,T2}` 可用 | 降解产物的载体。若采用"降解器直接产出字段列表"的退化方案，G2 可省 |
| **G3** | **未认领类型节点 → 派发给注册降解器；无注册 → 硬错** | 未实现 | 可复用 `ovl_dispatch_call` + `ovl_specificity`：按静态类型选最具体、平局报 `T-OVL-E902`。**自动避开 `extend fn` 值守卫那个顺序洞**（分派键是闭项类型，不是运行时值） |
| **G4** | 解析器一致性修正 | `comptime fn` 的**返回类型位**拒绝 `[]T`，但**函数体内** `[]T` 可以 | 两处 type 上下文走的是不同解析器分支。修掉它才能用 comptime 类型函数写容器 |

### 2.3 建议一并做（成本低，但必须提前做，事后补不动）

- **`#entity` 修饰词通道**：复用 `#id` 已走过的注解通道（`struct-modifiers`），不新开机制。
- **来源标记**：降解动作即带来源（包名 + 规则序号），诊断结构增加"扩展来源"字段。
  否则用户扩展报错时无法指回"哪个扩展的哪条规则"。
- **generated 标记**：降解产物打标记，**不再二次进入降解 pass**。
  这条一破，就会出现隐式迭代，而隐式迭代正是螺旋不收敛的来源。
- **archetype 默认封闭**：`#entity` 产出的结构体**不进开放组**，禁止被跨模块 `extend`。
  理由：追加一个组件会改变列索引，编译产物布局随之变化——在 SoA 下开放组是负债不是资产。

### 2.4 明确不做

- **不内建 `Vec` / `SparseSet`**——它们是普通 t 代码，根 tc 对 ECS 一无所知。
- **不做宏 / 不做声明生成**——降解器只产类型，不产 AST。
- **不做隐式表示推断**——写 `?T` 就一定得到稀疏列。推断会让同样源码在不同编译器版本下产出不同布局，IR 基线就废了。

### 2.5 验收（与现有工作流同构）

1. `gate L2` 双后端（C + LLVM）全绿。
2. 自举不动点 `g2 == g3 == g4` 仍成立（**G1 进入自举链路后必须重验，这是最大风险点**）。
3. IR 快照基线重录。
4. 新增判据：**降解产物 + 访问器必须对每个 `?` 成员提供 `T?` 语义**——可机械检查，落成一个普通编译错误。
5. 最小探路：先用 `struct Box<T> { val: T; }` + 一处实例化探一次 G1 对不动点的影响，成本极低。

## 3. ECS 工程需要做的

| 编号 | 项 | 说明 |
|---|---|---|
| **E1** | 组件定义 | 组件 = **可实例化 `struct`**，不是 `concept`（t 的 `concept` 是不可实例化约束，值位置引用报 `T-CON-E100`）。建议加 `#component` 修饰以区别于普通 struct |
| **E2** | 组件契约 | `concept Component { ... }`，由已有 `concept_satisfied` 校验。**约束校验不进降解器** |
| **E3** | 容器 | `Vec<T>` / `SparseSet<T>`。若 std 不提供则自写；`SparseSet<T>` = 三平行数组 `{ sp: []u32; dn: []u32; val: []T; }` |
| **E4** | **降解规则（核心交付）** | 稠密 `C` → `c: Vec<C>`；稀疏 `?C` → `c: SparseSet<C>`；簿记字段（`free_list` / `alive_count`）由本规则追加 |
| **E5** | 访问器（泛型函数，**写一次**） | `fn get<T>(s: SparseSet<T>, eid: u32) T?`、`fn at<T>(v: Vec<T>, row: u32) T`、`has` / `add` / `remove` 同理。**降解器不需要生成任何函数** |
| **E6** | 列序确定性 | 列序 = `&&` 链中的**源码顺序**（显式写在一条表达式里，天然确定，无跨文件遍历顺序问题） |
| **E7** | 实体 id 语义 | `eid` 与 dense row 的映射、free_list 复用规则 |
| **E8** | 查询与迭代 | 基于列的遍历（archetype 内 dense 扫 + sparse 过滤），跨 archetype 查询如何组合 |
| **E9** | 错误定位 | 降解规则自带来源标记，报错可指回"本包的第几条规则" |

### 参考产物形态（用户给的理想形态，非最终语法）

```t
struct PlayerArchetype {
    position:    Vec<Position>;
    health:      Vec<Health>;
    poison:      SparseSet<PoisonData>;
    burn:        SparseSet<BurnData>;
    free_list:   Vec<u32>;
    alive_count: u32;
}
```

行视图（正确性规格，不是产物）：

```t
. { position: Position, health: Health, poison: PoisonData?, burn: BurnData? }
```

## 4. 决策表

| 编号 | 议题 | 决定 | 理由 |
|---|---|---|---|
| D1 | 降解目标形态 | **SoA 列存**（不是 AoS 扁平行） | archetype 是表不是行；AoS 会逼降解器发明 mask / 旁路槽位等**编码语义**，而那属于用户 |
| D2 | `?T` 语义 | 恒为可选，`#entity` 只换**表示** | 换表示不改用户代码；给 `T?` 定边界 |
| D3 | 降解器产出 | **类型**（字段列表），不是声明 | 产出声明 = 生成 AST = 宏，与"非宏"自相矛盾 |
| D4 | 降解遍数 | **一遍**，产物不得含未认领节点 | 否则引入 phase 与终止问题；定这条 ⇒ 降解路径塔高 = 1 |
| D5 | 降解器分派 | 复用 `ovl_dispatch_call` + `ovl_specificity`，平局报 `T-OVL-E902` | 按静态类型分派 ⇒ 闭项 ⇒ 留在第二维，自动避开值守卫顺序洞 |
| D6 | 表示是否推断 | **不推断，显式** | 推断会让 IR 基线随编译器版本漂移 |
| D7 | archetype 可否被 extend | **默认封闭** | SoA 下追加组件会改列索引 |
| D8 | 约束校验归属 | 走已有 `concept`，不进降解器 | 语法走降解器、约束走 concept，两条路径分离 |
| D9 | `Vec`/`SparseSet` 归属 | 普通 t 代码，非编译器内建 | 根 tc 对 ECS 一无所知 |

## 5. 风险与开放问题

1. **G1 进入自举链路**是最大风险：`Vec<T>` / `SparseSet<T>` 若进 `lib/std`，`tc` 编译自己时会实例化它们，IR 基线必须重录，且不动点需重验。**先用 `Box<T>` 最小探路。**
2. **核心语言表达力是唯一硬约束**：用户想要的语义必须能降解到核心 t。建议先手写三个目标扩展的降解产物验证核心够用，再动机制——这一步最便宜也最容易被跳过。
3. **运算符是符号级不是结构级**：`&&` / `?` 这类能做，`for x in xs where p` 这种结构做不了。要结构级需"未认领的语法结构槽位"，那时才逼近 GLR。一期只做符号级。
4. **开放问题**：`Vec` / `SparseSet` 放 `lib/std` 还是由 ECS 工程自写？——前者放大第二个用例的收益，但进入自举；后者保持核心最小。
5. **开放问题**：ECS 运行时是否需要加载新组件类型（脚本层 / 热更新 / mods）？若需要，"运行时 seal"成为硬约束，本方案需在该小块上让路。

## 6. 里程碑建议

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| M0 | `Box<T>` 最小探路（G1 对不动点的影响） | `g2==g3==g4` 仍绿 |
| M1 | G1 + G2 + G4 落地 | `Vec<T>` / `SparseSet<T>` 能写出来并使用 |
| M2 | G3 未认领派发 + 未认领即报错 | 无降解器时 `A && B` 在值位置报"未认领"硬错 |
| M3 | ECS 侧 E1–E5 首版 | `PlayerArchetype` 端到端编译通过，双后端一致 |
| M4 | 访问器语义判据进 gate | 缺 `T?` 访问器时报错 |
