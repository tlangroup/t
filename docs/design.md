# t 语言设计提案与合规检查框架

> 本文档沉淀本对话中的「元设计」讨论：一套用于评审新特性提案的合规检查框架（rubric），以及若干已提出的特性设计提案及其合规体检矩阵。
> 本文档**只记录设计讨论与结论，不包含任何实现代码**，也不是对当前语言的规范（规范见 `docs/reference.md`；`docs/spec.md` 已废弃）。

---

## 1. 特性提案合规检查框架（rubric）

任何新语法 / 新类型 / 新内建提案，进入设计阶段前**必须**先按统一清单逐条过，输出「不违反 / 部分违反 / 较违反 / 强烈违反」的判定。目的是把前几轮手动做的「违规体检」系统化、可复用。

### 1.1 四层检查维度

| 层 | 检查项 | 自检问题 |
|---|---|---|
| **L1 设计五柱** | ① 静态类型/编译期查错 ② ECS·数据驱动 ③ 轻量 runtime ④ 确定性/性能 ⑤ fail-fast 报错 | 新特性把错往前推（编译期）还是往后推（运行期）？要不要往 `t_runtime.c` 塞东西？有没有隐藏 GC/魔法？ |
| **L2 实现铁律** | `shadow_check`（同名局部不同型）、`"assign"` 节点（非 `"assignment"`）、双后端逐字节一致、`sb_catN` 实参严格 = N、`TypeInfo`/`FieldInfo` 按指针、line/col UTF-8 字节计数 | desugar 产物在两后端会不会不一致？会不会触发已有守卫？ |
| **L3 规范约定** | spec §2.3（variant 用 helper、免改表达式推导）、`out/{dbg,rls}` 目录、命名红线（`✅ tote` / `status='tote'` 不可改名）、CLI 契约（`--mode` 等） | 是否偏离既定 spec 约定？是否平行另立机制？ |
| **L4 冲突分类** | 类型层 / 运行层 / 哲学层 / 范围层 | 违的是哪一类？——决定「能不能吸收」 |

**L4 是关键洞察**：
- 撞**类型层** → 几乎都能接纳甚至加分（t 的静态类型比 Erlang 动态类型更强）；
- 撞**运行层** → 看 runtime 增量大小（match = 0 成本 ✅，spawn/信箱 = 重 ❌）；
- 撞**哲学层** → 世界观冲突（如 "let it crash" 监督树 vs t 的 fail-fast）；
- 撞**范围层** → 明显越界（如分布式/网络）。

### 1.2 判定分级

每个检查项给一个档，整张表汇总出总判定：

- ✅ **不违反**（且常加分）
- ⚠️ **部分违反**（mild 错位，可调和，如 ECS vs actor 范式）
- ❌ **较违反**（哲学/运行层冲突，加了会别扭）
- 🚫 **强烈违反**（范围越界，明显不该做）

### 1.3 每个提案必交的三样东西（落点要求）

1. **desugar 姿势**：糖衣版 A（复用现有机制，如 match → `Name_is_CaseX` helper）还是另立 B（平行新机制）。**只允许 A**，B 直接判违规。
2. **双后端发射草图 + 一致性论证**：LLVM IR 与 C 后端各长什么样、为何逐字节一致（挂钩 `catn_check`/`shadow_check`/`conformance`）。
3. **依赖标注**：如 `match` 的元组解构 → 依赖 `tuple`。

## 2. 设计提案清单

### 2.1 tuple 类型（#2）

**事实基础**：当前 t 无 tuple 类型（`docs`/`src` 中 `tuple`/`元组` 零命中；`reference.md` 的 `Type` 产生式仅 `Scalar | []T | [N]T | NamedType`）；复合类型只能是切片、定长数组、命名类型（struct/enum/flag/variant/union/别名）；无多返回值语法，临时聚合值只能用具名 struct 或 out 指针。

**合规矩阵**

| 检查项 | 判定 | 理由 / 落点 |
|---|---|---|
| L1-①②③④⑤ | ✅ | 静态类型 / 数据驱动 / 轻量 runtime(0 成本) / 确定性 / fail-fast 全契合 |
| L2 `shadow`/`"assign"` | ⚠️ | 解构绑定多变量须守「同名不同型」「走 assign 分支」（达标线） |
| L2 双后端一致 | ⚠️ | LLVM 聚合 vs C struct 布局须逐字节一致——**唯一真风险点** |
| L3 spec §2.3 | 🟡 | 新类型，扩展 `Type` 产生式，不偏离既有约定 |
| L4 冲突分类 | 类型层 + 运行层 0 成本 | — |

**总判定：不违反**（守铁律 + 姿势 A：desugar 成聚合/struct）。唯一真风险是**双后端聚合布局一致性**——设计阶段须论证清楚。

### 2.2 Atom 类型（#3）

**设计澄清（关键）**：Atom = 一个在编译期就固定下来的 `Sym32`，只是这个 `Sym32` 的使用方法和其他 `Sym32` 有区别。即：
- 非新存储类型，**复用已有 `Sym32`**（`src/tc.tc:4883` 识别 `"Sym32"`/`"Sym16"`；`:6478` `Sym` 类型带 `bw`/`name`）；
- 值由编译器对字面量分配**固定 32-bit 值**，无运行期 intern / 全局原子表；
- 「用法区别」= 封闭字面量值集 + 可作 `match` 模式 / 消息 tag，区别于其他 `Sym32` 的通用不透明句柄用法。

**事实基础补充**：`enum`/`flag` 需显式声明、无匿名原子字面量；Erlang 通信提案与 match 提案依赖轻量标签。

**合规矩阵**

| 检查项 | 判定 | 理由 / 落点 |
|---|---|---|
| L1-①②③④⑤ | ✅ | Atom = 编译期固定 `Sym32`，静态 / 数据驱动 / 轻量 runtime(0 成本) / 确定性 / fail-fast 全契合 |
| L2 双后端一致 | ✅ | 与 `Sym32` 同表示（单 `i32`），两后端天然一致 |
| L2 拼接类型 | ⚠️ | 若 atom 进 StringBuilder 拼接需处理类型（同 `Sym32` 约束，达标线；cat 内建已移除） |
| L3 spec §2.3 | 🟡 | 新增字面量语法，但复用已有 `Sym32` 类型，不新增存储类型 |
| L4 冲突分类 | 类型层接纳；运行层 0 成本（复用 `Sym32`） | — |

**总判定：✅ 不违反**（已澄清 = 编译期固定 `Sym32`，无运行期 intern；原「取决于姿势」悬空项已消解）。

**关键设计点**：
- Atom 不是 `enum` 的替代，而是 **`Sym32` 的字面量语法层**——`enum` 是需声明的具名整型集，atom 是随手可写的封闭符号字面量。
- **实现依赖**：`Atom` 实现需 `Sym32`（即 `sym` 特性）真正落地；`sym` 已于 M40 实装（`sym_demo` + `sym_global` 示例、f15/f16/p16 用例全绿，C / LLVM 双后端一致）。

**其他 Sym32 vs Atom 用法对照**

| 维度 | 其他 Sym32（通用句柄） | Atom（编译期固定 Sym32） |
|---|---|---|
| 产生方式 | 运行期 intern / 由字符串算出的句柄 | 编译期由字面量分配固定值 |
| 集合 | 开放（可运行期新增） | 封闭（仅源码里出现过的字面量） |
| 主用途 | 不透明标识、哈希键 | 相等比较 + match 模式 + 消息 tag |
| 字面量语法 | 无 | 有（`ok`/`error`，需解决与标识符歧义） |

### 2.3 数据模式匹配 / match 表达式（#4）

**设计基准（4 类匹配能力）**：
1. **常量字面量匹配**：`fact(0) -> 1; fact(N) -> N * fact(N-1)` —— 对值做常量相等匹配并绑定变量。
2. **带守卫 `when` 条件过滤**：`abs(X) when X > 0 -> X; abs(X) -> -X` —— 分支加条件，守卫失败落下一分支。
3. **下划线 `_` 通配匹配**：`_ 匹配任意值但不产生变量绑定（仅占位）。
4. **元组解构匹配**：`do_msg({add,A,B}) -> A+B; do_msg({sub,A,B}) -> A-B; do_msg(_) -> error` —— 对 tuple 字段位置解构并绑定（**依赖 #2 tuple 先落地**）。

**合规约束**：须做成纯编译期糖衣，desugar 成现有 variant 的 `Name_is_CaseX`/`Name_as_CaseX` helper 调用（姿势 A），不得另立平行匹配机制（姿势 B 违反 spec §2.3）。守实现铁律：`shadow_check`、`"assign"` 节点、双后端逐字节一致。加编译期**穷尽性检查**强化 fail-fast。

**合规矩阵**

| 检查项 | 判定 | 理由 / 落点 |
|---|---|---|
| L1-①②③④⑤ | ✅ | 模式 + 穷尽性检查是编译期安全，强化「把错挡在编译期」文化；纯前端特性，确定性分支，无 GC |
| L2 `shadow`/`"assign"` | ⚠️ | 各分支绑定的局部变量若同名不同型会触发 `shadow_check`；绑定必须走 `assign` 分支（M32 坑） |
| L2 双后端一致 | ⚠️ | desugar 产物在两后端须逐字节一致，否则破 conformance |
| L3 spec §2.3 | 🟡 | 取决于姿势：糖衣 A（desugar 成 helper）= 合规；另立 B = 违规 |
| L4 冲突分类 | 类型层 + 运行层 0 成本 | — |

**总判定：不违反**（守铁律 + 姿势 A）。第 1/2/3 类匹配可立即由现有 variant helper 支撑；第 4 类（元组解构）依赖 #2 tuple。

### 2.4 用户态协程（#6）

**提案概述**：在 t 中引入用户态协程（user-space coroutine）——一种可在 `yield` 点挂起、之后 `resume` 恢复的执行单元，不依赖操作系统线程。设计须明确选型，因不同模型对「极简 runtime」柱的冲击天差地别。

**两种模型与合规对比**

| 模型 | 机制 | L1-③ 轻量 runtime | L4 冲突分类 | 判定 |
|---|---|---|---|---|
| **A. 无栈协程（stackless / 生成器式）** | 编译期把协程 desugar 成状态机（一个堆分配的状态 struct + 单 `resume` 函数，遇 `yield` 切 case） | ✅ 接近 0 运行时（只需状态 struct + 一次间接调用） | 类型层 + 运行层近 0 成本 | ⚠️/✅ 部分违反~不违反 |
| **B. 有栈协程（stackful）** | 每协程独立栈 + 上下文切换（ucontext/汇编/setjmp） | ❌ 需栈分配 + 上下文切换原语，撞「极简 runtime」柱 | 运行层重量 | ❌ 较违反 |

**结论**：只有 **模型 A（无栈生成器式）** 不（显著）违反设计五柱；模型 B 与之前评估的 Erlang `spawn`/`!`/`receive` 同类，属运行层重负载，建议不做或单列。

**事实基础**：t 当前无协程/生成器；控制流为顺序 + 函数调用；runtime 仅 `t_runtime.c` + `t_shim_ll.c`。`yield`/`resume` 均为新增原语。

**合规矩阵（以模型 A 为准）**

| 检查项 | 判定 | 理由 / 落点 |
|---|---|---|
| L1-① 静态类型 | ✅ | 协程句柄可类型化（如 `Coro<T>`，T 为 yield 类型），挂起/恢复点编译期已知 |
| L1-② ECS·数据驱动 | ⚠️ | 协程是顺序控制流，与 ECS 数据并行范式 mild 错位，但非硬冲突 |
| L1-③ 轻量 runtime | ✅/⚠️ | 模型 A：状态机 desugar，近 0 运行时；模型 B：❌ 撞极简 runtime |
| L1-④ 确定性/性能 | ⚠️ | 状态机确定；但多协程调度顺序需显式，否则非确定；上下文切换有开销 |
| L1-⑤ fail-fast | ✅ | `yield` 只能出现在协程内、`resume` 类型匹配等均可编译期查 |
| L2 `shadow`/`"assign"` | ⚠️ | 状态机 desugar 后局部变量提升为状态字段，须守同名不同型/assign 节点（达标线） |
| L2 双后端一致 | ⚠️ | 状态机 lowering 在 LLVM/C 两后端须一致；上下文切换（若 B）汇编后端相关 |
| L3 spec §2.3 | 🟡 | 新增 `yield`/`resume`/协程类型语法，不偏离既有约定 |
| L4 冲突分类 | 类型层接纳；运行层取决于模型 | — |

**总判定**：
- 模型 A（无栈生成器式）：**⚠️ 部分违反 ~ ✅ 不违反**——只要 desugar 成状态机、零新增 runtime 原语，即契合「轻量转译器」定位；主要达标线是双后端 lowering 一致。
- 模型 B（有栈协程）：**❌ 较违反**——撞「极简 runtime」柱，与 Erlang actor 同档，建议不纳入。

**关键设计点（模型 A 草方案）**：
- 协程类型：`Coro<T>`（T = yield 值类型）；或 `Gen<T>` 以示生成器语义。
- 原语：`yield expr`（挂起并返回 expr）、`resume(co)`（恢复，返回下一次 yield 值）、`done(co)`（是否已结束）。
- desugar：把协程函数改写成「状态 struct + `resume` 大 `switch(state)` 状态机」，每个 `yield` 是一个 case 出口；局部变量提升为 struct 字段。
- 与 match/tuple 的交互：协程 yield 的值若是 tuple / 参与 match 解构，复用 #2/#4 机制。

**依赖/交互**：
- 与 Erlang 式通信提案：无栈协程可作「单线程 mailbox 模拟」的载体（前轮提过的低代价折中），但仍不提供真并发。
- 与 match（#4）：协程 produce 的值可用 `match` 消费。
- 与 tuple（#2）：多值 yield 可借 tuple 表达。

### 2.5 网络通信模块（轻量路径：编译器只做语法检查 + 数据写入抽象接口，通信功能由通信库提供）（#7）

**提案核心（用户给定）**：为网络通信模块铺路，但不违反「轻量 runtime」柱。做法是把重活从编译器核心推到外部通信库——`tc` 仅负责：
1. **语法 / 类型检查**：网络相关代码仍完整走编译期检查；
2. **数据写入抽象接口**：提供一层编译期抽象接口（如 `Writer` / `Sink` / `Conn`），作为通信库与用户代码之间的 I/O 契约。

真正的通信功能（TCP/UDP 套接字、连接管理、序列化、收发调度）由**可选的通信库**（如 `net.t`）实现该接口来提供，不进入 `t_runtime.c` 核心。

**合规矩阵（#5 框架）**

| 检查项 | 判定 | 理由 / 落点 |
|---|---|---|
| L1-① 静态类型 | ✅ | 网络代码仍走完整编译期类型检查；抽象接口可参数化（端点/缓冲类型），强化静态安全 |
| L1-② ECS·数据驱动 | ✅/⚠️ | 通信与 ECS 正交，但「消息即数据」（tuple/atom 承载）正中数据驱动；mild 错位非硬冲突 |
| L1-③ 轻量 runtime | ✅ | **关键动作**：重运行时（套接字/调度/序列化）外置到可选库，不进 `t_runtime.c`；tc 仅加抽象接口声明（编译期），核心 runtime 仍极小 |
| L1-④ 确定性/性能 | ✅/🟡 | tc 侧是确定性的编译期检查；库的运行期行为被隔离在库内，由库负责，不污染语言语义 |
| L1-⑤ fail-fast | ✅ | 网络代码的类型/接口错在编译期由 tc 拦下 |
| L2 `shadow`/`"assign"` | ⚠️ | 仅当抽象接口引入新绑定形态时须守（达标线） |
| L2 双后端一致 | ✅ | 抽象接口是纯编译期契约，无新运行时代码生成；通信库为预编译/外部提供，在 tc 代码生成范围外，无分叉风险 |
| L2 拼接类型 | ⚠️ | 若接口字符串流入 StringBuilder 拼接，同 `Sym32` 约束（达标线；cat 内建已移除） |
| L3 spec §2.3 | 🟡 | **唯一真风险点**：须引入「抽象接口」机制（interface/trait 类），属新语言特性；必须姿势 A（编译期分发、0 运行成本，如静态派发/关联函数），不得姿势 B（vtable/Rtti 运行期派发），否则撞极简 runtime 柱 |
| L4 冲突分类 | 范围层（网络）原本 🚫，经库外置后消解 | 语言层面不承接网络范围；编译器只提供接口抽象，网络范围转为「通信库」关切 |

**总判定：✅ 不违反**（前提是抽象接口机制自身走姿势 A）。

**为什么能消解早前的「网络 = 强烈违反」结论**：早前把 Erlang 式通信（`spawn`/`!`/`receive`）评为 ❌/🚫，根因是它把重运行时（调度器/信箱/监督树）塞进语言核心。本提案把同一能力**挪到可选库**，语言核心只保留「类型检查 + 数据写入抽象接口」——冲突在语言层被溶解，只在库层存在。这本质是把 t 既有的架构哲学从「前端自研 + 后端外包给 clang」推广为「核心语言自研 + 通信运行时外包给库」。

**关键设计点**
- **抽象接口形态**：建议编译期接口（`interface Writer { fn write(buf: []u8) -> i32 }` 类声明），静态派发、0 运行成本；避免引入 vtable/RTTI。这与 #4 match 的类型层接纳一致。
- **复用既有合规特性**：消息体用 #2 tuple、消息标签用 #3 atom（编译期固定 `Sym32`）、消息分发用 #4 match——三者均 ✅ 合规，在类型层把通信脚手架搭好，运行层全交给库。
- **与 #6 协程的关系**：无栈协程（模型 A）可作「单线程 mailbox / 异步 I/O 状态机」的承载；库内用协程编排收发，语言不新增并发原语。

**依赖/交互**
- #7 → #2 tuple / #3 atom / #4 match：类型层脚手架依赖三者。
- #7 → 「抽象接口机制」（新轻量特性，须姿势 A）：实现前提。

### 2.6 链式计算 / 管道运算符（#8）

**提案概述（用户给定）**：引入一组「链式计算」中缀运算符，把对集合/数据流的多阶段变换写成从左到右的管道。核心是「`>` 把左侧（的元素）传入右侧进行计算」，前缀选择模式：

| 运算符 | 语义（用户描述） | 提议含义 |
|---|---|---|
| `|>` | **多态管道**：左操作数标量 → 直接应用 `F(S)`；左操作数可迭代 → 逐元素映射（类型定向：若 `F` 形参接受整体类型则整体应用，否则逐元素映射） | **前向管道 / map / 应用**（统一算子，详见 `docs/reference.md` §3.15） |
| `|->` | 显式逐元素映射（左操作数**必须**可迭代，否则报错） | **explicit map**：对左侧集合每个元素调用右侧函数，收集结果成新集合 |
| `|>?` | 带过滤的传入右侧进行映射（取代原 `=?(exp)>`） | **filtered map**：先按谓词过滤元素，再映射 |
| ~~`~>` / `~!` / `~?(exp)>`（Delta 体系）~~ | **整体缓议（2026-08-10 裁定）**：标量形态经审查证明确为 `x = x + 20` 的冗余糖，唯一非冗余场景是 ECS 并行确定性合并，须待该法律落地后重新提案。详见 §2.6.2（已转为历史提案）。 | — |

> 统一心智模型（2026-08-10 修订）：`>` 是「传入右侧计算」的公共箭头。`|>` 是**多态**管道（标量→应用、可迭代→映射，按左操作数类型定向）；`|->` 是**显式**逐元素映射（左操作数必须可迭代）；`|>?` 是**过滤**映射（取代原 `=?(exp)>` 内嵌表达式形态）。三者共用最低优先级级 L0、全左结合，脱糖为 `for` 循环（姿势 A，0 新增 runtime）。Delta 体系（`~>`/`~!`/`~?(exp)>`）整体缓议，见 §2.6.2。

**示例（串联管道，2026-08-10 修订）**
```
// 过滤 + 映射 + 链尾聚合（|> 在可迭代上映射，末段 |> 整体应用 sum_i32）
es |>? is_alive |-> hp_of |> sum_i32;

// 显式映射（|-> 强制左操作数可迭代）
xs |-> fn(v: i32) i32 { return v * 2; };

// 多态 |>：标量 → 直接应用，集合 → 映射 / 整体应用
PI |> sin;                       // ⇔ sin(PI)（标量应用）
xs |> fn(v: i32) i32 { return v + 1; };   // ⇔ 逐元素 +1（集合映射）
xs |> sum_i32;                   // ⇔ sum_i32(xs)（整体应用）
```

**合规矩阵（#5 框架）**

| 检查项 | 判定 | 理由 / 落点 |
|---|---|---|
| L1-① 静态类型 | ✅ | 元素类型 T 流经管道；右侧为 `fn(T) U`（FuncType M45-48）或 lambda，谓词须 `fn(T) bool`——编译期可查，强化静态安全 |
| L1-② ECS·数据驱动 | ✅✅ | 对数据集合做链式变换正中「数据优先」；是迄今与 ECS 取向**最契合**的提案（优于 match/atom） |
| L1-③ 轻量 runtime | ✅ | **关键**：须姿势 A（贪心展开成 `for` 循环逐元素调 lambda），0 新增 runtime；若做成惰性流 / 迭代器对象则需 runtime → 违规 |

**关键设计点（落点）**
- **姿势 A（贪心展开）是合规前提**：`L |> f`（可迭代情形）desugar 为 `var r: []U = []; for (x in L) { append(r, f(x)); }`；`L |>? p` 在循环内加 `if (p(x))`；`L |-> f` 同 `L |> f` 的映射形态。`|>` 的标量情形直接脱糖为 `f(L)`。全部复用现有 `for ... in ...`（map/slice/array 已支持）与 lambda 调用，无新 runtime。delta 提交（`~!`）已缓议。
- **优先级塔落位**：建议置于 `or` 同级或更低（管道通常最低优先级、左结合），与既有塔不冲突；必须在 `reference.md` 的 10 级塔中显式登记，遵守 L-03「不可调换」。
- **词法最大匹配必须实现**：新增 token `|->` / `|>` / `|>?`（按 §2.6 L3 的降序最大匹配）；lexer 采用 maximal munch，确保 `|->` / `|>?` 优先于 `|`(BitOr)、`|>` 优先于 `||`(Or)。
- **完全显式铁律**：`|>` 产生的新集合须在 desugar 中显式构造（新建 slice 并 append），不得隐式分配。

#### 2.6.1 优先级 / 结合性定位（推演，2026-08-03）

- **真实 10 级塔（来自 `src/tc.tc:6751-6957` 解析链）**：`primary`(atom/lambda/match/ident/paren/array) → `postfix`(`. [] () as`) → `unary`(`! - ~`) → 10 个二元级（紧→松）：`* / %`(L10) > `+ -`(L9) > `<< >>`(L8) > `< > <= >=`(L7) > `== !=`(L6) > `&`(L5) > `^`(L4) > `|`(L3) > `&&`(L2) > `||`(L1)。`parse_or` 为表达式入口（`src/tc.tc:5001`）。
- **定位结论**：**新增最低二元级 L0，包在 `parse_or` 外层为 `parse_pipe`；全族 `|>`/`|->`/`|>?` 共用此级且全部左结合（`~>`/`~!` delta 体系缓议，见 §2.6.2）。**
- **理由**：① 结合性须左结合（链 `(a |> b) |> c` 左→右）；② `|>` 须低于算术，使 `1 + 2 |> f` 解析为 `(1+2) |> f` 而非 `1 + (2 |> f)`，左侧必为完整求值后的集合；③ 管道须比几乎一切运算符都松，使 `result = src |> f |> g` 整体成为 `=` 右侧；④ RHS 为函数/lambda（`primary`/`postfix`，高优先级）本就被完整吞入，与级别无关。
- **合规（L-03）**：属**塔的向下扩展**、非重排——既有 10 级相对顺序一字不变，`parse_pipe` 仅包裹 `parse_or`；表达式入口由 `parse_or()` 改 `parse_pipe()` 即可。未引入右结合二元运算符（仍全左结合），不违反 L-03「不可调换 / 无右结合」。
- **实现点**：`parse_pipe` 循环识别 `|>`/`|->`/`|>?`（词法最大匹配，见 §2.6 L3）；`|>` 的多态分派在 sema 期按左操作数类型决定（直接应用 / 逐元素映射 / 整体应用），详见 `docs/reference.md` §3.15.3。

#### 2.6.2 `~>` 精确语义 —「延迟累加（delta）模型」（2026-08-03，依用户澄清修订）

> ⚠️ **本小节（§2.6.2 / §2.6.2.1 / §2.6.2.2）于 2026-08-10 裁定为「历史提案 / 缓议」**：经审查，标量 delta（`x ~> +20` ⇔ `x = x + 20`）为冗余语法糖，唯一非冗余场景是宪法第12条的 ECS 并行确定性合并，须待该法律落地后重新提案。当前 t 不实现 `~>`/`~!`/`~?(exp)>` 任何记号。管道算子以 `|>`/`|->`/`|>?` 为准（见 `docs/reference.md` §3.15）。以下原文保留备查。

- **用户澄清**：`~>` 是**延迟累加（deferred accumulation）**——`~>` 把运算**暂存进一个 delta 累加器**，`~!` 才把整个 delta **一次性提交**到目标变量。这推翻了本节早前「增量映射（立即 apply）」与「表达式树 + 优先级组合」两种假设。
- **规范示例（用户给定，权威语义）**
  ```
  x = 10;
  x ~> +20 ~> * 2 ~!;     // 自运算：x += delta_x；x 最终结果 = 50
  ```
  其**确切展开**为：
  ```
  x = 10;
  delta = 0;
  delta += 20;        // 来自 ~> +20
  delta += x * 2;     // 来自 ~> * 2（x 取「链开始前」的原值 = 10）
  x += delta;         // 来自 ~!（自运算）
  // => delta = 40, x = 50
  ```
- **精确规则（delta 累加模型）**
  - 每个 `~> rhs` 阶段 ⇒ `delta += rhs`，其中 `rhs` **在 `~!` 提交那一刻求值**，且此时目标变量仍持有**进入 `~>` 链之前的值**（提交 `x += delta` 是最后一步，故 rhs 内引用的目标变量是原始值）。
  - **`~!` 的两种合规提交形式（保证表达唯一性）**：① `x ~!` **自运算** ⇒ `x += delta_x`（源即目标，等价于被删除的 `x ~! x`）；② `x ~! y` **提交到另一变量** ⇒ `y += delta_x`（对 `x` 的 delta 做最终运算、结果存入 `y`，`x` 自身不变）。**`x ~! x` 写法删除**（与 `x ~!` 完全等价，避免冗余歧义）。
- **RHS 表达式的三种写法（delta 模型下天然统一）**
  - **带符号字面量**（如 `+20`、`-5`）：lex 为带正负号字面量，贡献该字面量（`+20` ⇒ 贡献 `20`；`-5` ⇒ 贡献 `-5`）。
  - **运算符区段 / section**（如 `* 2`、`/ 3`）：缺失的左操作数**自动填入目标变量**，故 `* 2` ⇒ 贡献 `目标 * 2`；`/ 3` ⇒ 贡献 `目标 / 3`。
  - **显式函数**（`fn(v){ E }`）：参数 `v` 绑定目标当前值，贡献 `fn(目标)` = `E[v:=目标]`。即 `x ~> fn(v){ v + 20 }` 与区段式 `x ~> + 20` 贡献一致——函数就是「显式写出贡献表达式」的形式，三种写法在 delta 模型下统一。
  - ⚠️ **潜在歧义（设计点）**：带符号字面量 `+20`（无空格，lex 为字面量 `20`）与区段 `+ 20`（带空格，左操作数=目标）语义不同——前者贡献 `20`、后者贡献 `目标+20`。建议约定：**`~> ` 后紧跟运算符且运算符紧接符号字面量时按字面量处理；若运算符后有空格或显式区段分隔，则按「左操作数=目标」区段处理**。此 lexer 细节待最终敲定。
- **与 `|>` 的对照**：`|>` 是 eager（对流逐元素立即应用右端函数）；`~>` 是 lazy + 累加（把各阶段贡献攒进 delta，`~!` 才提交）。一个 eager、一个 lazy 累加，正交互补。
- **desugar 形态（0 运行成本）**
  ```
  // x ~> +20 ~> * 2 ~!       （~! 自运算：x += delta_x）
  var delta: T = 0;          // T 同目标类型；与 x 配对
  delta += 20;               // ~> +20
  delta += x * 2;            // ~> * 2（x 为原始值）
  x += delta;                // ~!（自运算）
  // 可进一步常量折叠：x = x + 20 + x*2 即 x = 3*x + 20（本例 x=10 ⇒ 50）
  ```
  全部顺序语句，编译期可知、确定性、无隐含迭代器 / 惰性流 → 守姿势 A。
- **合规论证**：仍落 L0 级、左结合（§2.6.1）；本质是「一个临时 delta 变量 + 顺序累加 + 提交」的纯前端 desugar，0 运行成本、不引入 runtime 原语；不引入新 token 形状（`~>` 已在 §2.6 L3 词法风险登记）；与 `|>`/`~!`/`=?(exp)>`/`~?(exp)>` 同族同级。**总判定不变：✅ 不违反。**
- **ECS 契合（宪法第 12 条）**：延迟累加让「系统 staged 计算、批量提交 delta」成为一等公民；`~!` 在 sync 点统一提交，满足「ECS 数据并行须顺序无关以保持确定性」——且因 delta 链可编译期折叠，性能可预测。
- ⚠️ **与 §2.6 集合管道示例的衔接**：§2.6 顶部示例在集合上下文（`xs |> ... ~> ... ~! ...`）里用了 `~>`，其「逐元素 delta」须与本节标量模型对齐——统一口径：集合 `~>` 等价于「对每个元素维护 element-local delta，折叠进 `~!` 的累加器」。该集合形态 desugar 复用 §2.6 的 `for` 循环骨架，待另立 §2.6.3 展开（不影响本节的标量权威语义）。

#### 2.6.2.1 跨函数 / 多作用域延迟语义（用户澄清，2026-08-03）

- **用户澄清**：`~>` 与 `~!` 在代码层可被**拆成多个语句、乃至多个函数**。多个函数里各自对变量做 delta 运算时，**基础变量的值保持不变**；一直延迟到某个函数里执行 `val ~!`（提交），才把累积的 delta 真正应用到基础变量。
- **核心含义**：delta 累加器必须是**跨函数 / 跨作用域存活的显式状态**，而非块级临时变量。基础变量 `x` 在所有参与 delta 的函数中保持**只读**，`~!` 是唯一的写点。
- **关键不变量**：在 `~!` 提交之前，任何函数读取 `x` 得到的都是**进入 delta 链之前的原值**（不是 `x + delta`），从而保证跨函数观察一致、确定性（契合宪法第 12 条）。
- **desugar 草图（显式 delta 累加器）**
  ```
  var dx: T = 0;            // delta 累加器，跨函数显式存在（与目标 x 配对）
  fn stage_a() { dx += 1; }          // 对应  x ~> +1   （x 不变，dx 攒 1）
  fn stage_b() { dx += x * 2; }      // 对应  x ~> * 2   （x 仍是原值，dx 攒 x*2）
  fn commit()  { x += dx; dx = 0; }  // 对应  x ~!       （唯一写点：提交并清零 delta）
  ```
  即：`~>` 在各函数内只写 `dx`（delta 槽），绝不写 `x`；`~!` 才写 `x`。基础变量在 delta 链存活期间被冻结。
- **⚠️ 强制设计约束（维持合规的前提）**：跨函数 delta 状态**必须显式**（用户可见的 delta 变量，或 desugar 生成的显式 `dx`），**不得由语言隐藏**（不能做成「变量自动携带 pending delta、用户无感」的隐藏运行期机制——那会引入隐式状态，撞「极简 runtime」柱，判 ❌）。换言之：`~>`/`~!` 的跨函数延迟是**编译期 / 代码层对显式 delta 变量的编排**，不是运行时魔法。
- **合规论证**：仍是「临时 delta 变量 + 顺序累加 + 提交」的纯前端 desugar 扩展；delta 累加器跨函数通过参数 / 返回值或模块级显式变量延续，0 运行成本、确定性、无 GC / 无惰性流 → 守姿势 A。`~!` 提交点即唯一状态变更点，fail-fast 可静态检查「`~!` 前基础变量是否被意外写入」（若某函数直接写 `x` 而绕过 delta，编译器可报错）。**总判定不变：✅ 不违反（前提：delta 累加器显式化）。**

#### 2.6.2.2 delta 运算测试用例（已与用户对齐，2026-08-03）

> 以下用例经用户逐条确认与现行语义一致。前提约定：① `+20`（无空格）= 带符号字面量 20；`+ 20`（带空格）= 区段 ⇒ 目标 + 20。② `x ~> fn(v){ E }` ⇒ `delta += E`，`v` 绑定进入链前的原值 x。③ 标量权威语义 `x ~> rhs` ≡ `delta += rhs`（rhs 在 `~!` 提交时求值，引用原值 x）；`x ~!` ≡ `x += delta`（自运算），`x ~! y` ≡ `y += delta_x`（提交到 y）；`x ~! x` 写法已删除。

**一、标量基础**
- **T1 单字面量**：`x=10; x ~> +5 ~!;` ⇒ `x==15`（delta=5）。
- **T2 规范示例（用户给定）**：`x=10; x ~> +20 ~> * 2 ~!;` ⇒ `x==50`（delta=20+10*2=40）。
- **T3 区段**：`x=7; x ~> * 3 ~!;` ⇒ `x==28`（delta=7*3=21）。
- **T4 负 delta**：`x=10; x ~> -3 ~!;` ⇒ `x==7`。
- **T5 多段链式**：`x=100; x ~> +1 ~> +2 ~> * 0 ~!;` ⇒ `x==103`（1+2+0）。

**二、函数形态 & 混合**
- **T6 函数**：`x=10; x ~> fn(v){ v+20 } ~!;` ⇒ `x==40`（delta=10+20=30）。
- **T7 函数+区段**：`x=10; x ~> fn(v){ v+20 } ~> * 2 ~!;` ⇒ `x==60`（30+20）。

**三、延迟 / 冻结（核心）**
- **T8 未提交不生效**：`x=10; x ~> +5 ~> +5;`（无 `~!`）⇒ `x==10`（delta 累加但丢弃）。
- **T9 提交前读原值**：`x=10; x ~> +1; y=x; x ~!;` ⇒ `y==10, x==11`。
- **T10 跨函数 delta**：`var x=10; var dx=0; fn stage_a(){ dx+=1; } fn stage_b(){ dx+=x*2; } fn commit(){ x+=dx; dx=0; } stage_a(); stage_b(); commit();` ⇒ `dx=21, x==31`。
- **T11 stage 内读原值**：上例 `stage_b` 中 `x` 仍为 10，`dx==20`。

**四、确定性 / ECS 契合（宪法第 12 条）**
- **T12 顺序无关**：`x=10; x ~> * 2 ~> +20 ~!;` ⇒ 仍 `x==50`（两段均引用原值 10，顺序不影响结果）。
- **T13 空 delta**：`x=10; x ~!;` ⇒ `x==10`（delta=0）。

**五、集合 / 过滤**
- **T14 过滤 delta**：`xs=[1,2,3,4,5]; xs ~? (e>2) > +10 ~! ...` ⇒ 仅 `e>2` 元素 +10，结果 `[1,2,13,14,15]`。
- **T15 eager/lazy 对比**：`xs=[1,2,3]; xs |> fn(v){v*2} ~> +1 ~! ...` ⇒ 先翻倍 `[2,4,6]`，再各 +1 ⇒ `[3,5,7]`。

**六、反直觉对照（常见误解）**
- **T16 误当立即左折**：`x=10; x ~> +20 ~> * 2 ~!;` ❌ 错误直觉 `((10+20)*2)=60`；✅ 正确 delta 模型 `=50`。
- **T17 提交到另一变量（新形式 `x ~! y`）**：`x=10; y=0; x ~> +5 ~! y;` ⇒ `x==10（基础变量不变）, y==5`（delta_x=5 提交到 y）。

**依赖/交互**
- #8 → 迭代机制（已有 `for ... in ...`，map/slice/array）✅ 无新依赖。
- #8 → FuncType/lambda（M45-48 已实装）✅ 复用闭包 desugar，双后端一致性继承。
- #8 复用 #4 match（stage 内可 match 解构）、#2 tuple（多值传递）可选。
- #8 ↔ #7 网络通信：管道可作通信库的消息处理流（`recv_stream |> decode |> dispatch`），类型层脚手架复用 #2/#3/#4。
- #8 ↔ #6 协程：无栈协程可驱动惰性 / 异步管道，但本提案默认贪心即时展开，不依赖协程。

#### 2.7.1 人类可读诊断输出模式（flag 命名冲突，待决策）

**背景**：REPL 面向终端用户，需要 `tc` 在报错时输出人类可读文本（格式 `file:line:col: severity[CODE]: message` + note / hint + 计数摘要），而非仅供机器解析的 JSON。

**现状实现（已落地，未审查）**：
- `tc` 侧：`src/tc.tc` 各子命令新增 `--diagnostics <fmt>`（`human`/`json`）与 `--json` 别名；默认 `json`（机器可读，供 tote / CI / 对拍）。
- 渲染：`src/base.tc` `emit_diags()` 分发器 + `print_human()`；驱动层报错点由 `print_json()` 改调 `emit_diags()`。
- REPL：`lib/repl.tc` `repl_build` 调用 `tc build ... --diagnostics human`。

**⚠️ 与已批准规范的冲突（审查核心）**：`docs/diagnostics.md` §6（已批准 ratified）明确规定：
> 输出模式互斥：`--format=human`（默认）、`--format=json`，禁止混合输出

即规范采用 `--format=human` / `--format=json`，而现状实现用 `--diagnostics human` / `--diagnostics json` + 别名 `--json`。两者**命名不一致**，且默认值不同（规范默认 human，现状默认 json）。这违反「单一事实源 / 已批准规范优先」原则，属审查必须消解项。

**审查决策项（二选一）**：
- **方案 A（对齐已批准规范）**：把现状实现统一为 `--format=human` / `--format=json`，默认 human（规范定义）；REPL 改用 `--format=human`。优点：直接符合 ratified 规范，零规范改动；代价：需改 `tc.tc` 三处 flag 解析 + `repl.tc` 调用。
- **方案 B（修订规范）**：在 `docs/diagnostics.md` §6 增补 `--diagnostics` 为等价别名，保留 `--format` 为主名，并澄清「默认 human」条款。优点：不改现状运行行为；代价：规范需走修订流程，且与「默认 human」条款冲突需同步澄清。

**合规矩阵（按 #5 框架）**

| 检查项 | 判定 | 理由 |
|---|---|---|
| L1-① 静态类型 | ✅ | 诊断渲染是纯输出层，不影响类型系统 |
| L1-③ 轻量 runtime | ✅ | 纯字符串格式化，0 运行成本 |

**总判定**：能力本身 ✅ 合规；**flag 命名冲突 ❌ 待审查消解**（推荐方案 A，直接对齐已批准规范）。在决策落地前，现状 `--diagnostics human` 作为「审查中临时实现」保留，REPL 依赖项见 `docs/repl.md` §5 R2。

### 2.8 cell 块（Notebook 单元）（#9）

> ⏳ **状态：设计中（proposed）**。本提案把「类似 Observable 的 notebook 的单元格」对应为一个轻量语言级作用域块 `cell <name> { ... }`。依据 `docs/notebook.md` 红线——**notebook 不独占任何语法/语义**——`cell` 是通用语言构造，notebook 仅作为复用方之一。完整路线与已锁定决策见 `docs/notebook.md` §13 / §13.8。

**事实基础**：
- `docs/notebook.md` 已裁定 **Model C**：Notebook = 一个 `.tc` Module，单元格为文件内 `cell` 块；编译器按 cell 做二进制缓存与增量（文件级 `.tlib`/链接粒度下放至 cell）；所有 cell 链入同一二进制/同一 wasm 实例 → 共享地址空间 → 跨 cell 免序列化。
- 已锁定四项决策（§13.8）：①可见性自上而下；②增量缓存先 host 侧（零 tc 改动验证）；③关键字 = `cell`（非 `region`，`region` 保留给未来内存区域语义）；④不隔离（整本单一 `.tc`、共享 scope）。

**desugar 姿势（落点要求 1）**：姿势 **A**——`cell` 块脱糖为「带名作用域 + 可选 `fn <name>__run()`」，复用既有块 / 函数机制，不平行另立机制。@main 存在时 `cell` 块作顶层声明容器（与 `emit-ll`/`build --lib` 已有行为一致）；无 @main 的表达式型 cell 由宿主包装为 `var <id> = E;`（见 `docs/notebook.md` §4）。

**双后端发射草图 + 一致性（落点要求 2）**：
- C 后端：`cell` 块 → 一层 `{ }` 花括号包裹（C 复合语句即作用域），或脱糖为 `static`/函数；ABI 不变。
- LLVM 后端：块内声明落在当前函数/模块作用域，仅多一层 LLVM 块（basic block 或嵌套 `{ }`）；ABI 不变。
- 一致性论证：脱糖产物在两后端均为「同名作用域 + 可选函数」，无类型层差异，逐字节一致由既有 `catn_check` 守卫保障（同 `match`/`for` 等既有块构造）。**唯一注意点**：cell 级「按内容哈希增量缓存」若下沉至 tc 侧，须保证 cell 接口（导出符号/大小）未变时下游仅重链不重编——属链接器重定位，不影响 codegen 一致性。

**依赖标注（落点要求 3）**：无硬依赖（不依赖 tuple/match/协程）；仅依赖既有块/作用域机制与 `build --lib`/`.tlib` 增量编译（均已实装）。

**合规矩阵（按 §1.4 模板）**

| 检查项 | 判定 | 理由 / 落点 |
|---|---|---|
| L1-① 静态类型 | ✅ | 仅加作用域块，类型系统不变 |
| L1-③ 轻量 runtime | ✅ | 0 运行成本（脱糖成花括号/函数） |
| L1-⑤ fail-fast | ✅ | 诊断定位到 cell 内行列不变（file 即 cell 标识） |
| L2 `shadow`/`"assign"` | ✅ | 嵌套作用域复用现有 shadow_check |
| L2 双后端一致 | ✅ | 脱糖成「花括号/函数」，ABI 不变（catn_check 守一致性） |
| L3 spec §2.3 | 🟡 | 新增保留字 `cell` + 扩展 `Statement`/`Item` 产生式（见 `reference.md` §2.3/§3.3/§3.17），不偏离约定 |
| L4 冲突分类 | 类型层 + 运行层 0 成本 | 与 `region`（内存区域语义）分工明确、互不抢占 |

**总判定：不违反**（守铁律 + 姿势 A：脱糖成带名作用域/函数；双后端逐字节一致；无硬依赖）。改动集中在前端（lexer + parser）+ sema（嵌套作用域 + 顺序可见性），typeck/IR/ABI 不动，属新增路径非重写。`region` 关键字保留给未来类 Cone 内存区域语义，本提案不引入。

**Stage 1 过渡**：在 `cell` 关键字经本提案落地前，notebook 编排层（host 侧，零 tc 改动）可在 cell 边界切分、拼接为单一 `.tc` 复用 `emit-ll`/`build --lib` 缓存，等价获得 Model C 语义（`docs/notebook.md` §11 Stage 1）。即本特性在 tc 接入前后 notebook 体验一致，风险可控。
