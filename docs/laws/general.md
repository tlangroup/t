# t 语言法律总则

> **法律编号：L-01** ｜ 名称：t 语言法律总则 ｜ 制定依据：《t 语言设计宪法》(docs/constitution.md)
> **状态：草案（待宪法审查）**
> 本法律为法律体系的元规范:规定法律文件的内容框架、法律的制定/审查/生效流程,以及执行法律(检查代码)的标准步骤。具体领域的开发指导由后续细则法、契约法承载。

---

## 第一章 法律的定义与层级

- **第1条 法律的定义** — 法律是宪法之下、指导 t 语言具体开发的根本规范,以「法律文件」形式存在;其用途是**检查代码执行**是否合规(对照宪法铁律与本条法律条文,检验编译器、运行时、工具链实现)。
- **第2条 法律层级** — 宪法 > 法律 > 代码。法律不得与宪法任何条款冲突;冲突时以宪法为准。法律之间效力平等,特别法优于一般法。
- **第3条 法律分类** — ①基础法(如本总则,规定法律体系的框架);②细则法(类型系统、运行时契约、工具链约定等具体领域);③契约法(ABI / 版本 / 接口稳定契约);④**语法规则**(以规范 EBNF 书写的语法产生式子层,依 L-15 起草工作流产出草稿 → 法律验证 → 并入 `docs/reference.md`,详见第16条)。

---

## 第二章 法律文件内容框架

每条法律文件须包含以下要素：

- **第4条 文件头** — 载明法律编号、名称、制定依据(对应宪法条款)、状态(草案 / 已生效 / 已废除)。
- **第5条 适用范围** — 明确本法律约束的对象(编译器 `src/tc.tc`、运行时 `runtime/*`、工具链 `tools/*`、示例代码 `examples/*` 等)与不适用情形。
- **第6条 正文条款** — 以「第N条」编号的规范性条文;每条为**一句可执行约束 + 必要释义**;禁用模糊措辞("尽量""通常""应尽量避免")。
- **第7条 与宪法关系** — 明示本条法律对应的宪法铁律(第一章第X条)或管理条款,作为审查与争议裁决依据。
- **第8条 合规判据** — 给出可观测、可验证的合规标准(具体命令 / 函数名 / 产物特征 / 输出格式),供执行时逐条对照。
- **第9条 生效与修订** — 载明生效条件(经宪法审查取得 ✅ 或经确认的 ⚠️)与修订程序(依第三章)。

---

## 第三章 法律的制定、审查与生效

- **第10条 制定** — 具体语言开发指导须编写为法律文件,内容框架依第二章;分类依第3条。
- **第11条 宪法审查** — 任何法律的制定、修改、废除,均须提交宪法审查,由宪法提供**四层评审意见**:
  - ✅ **合规** — 与宪法一致或属澄清性补充,可直接纳入;
  - ⚠️ **警示** — 与宪法存在轻微张力,须说明理由并经用户确认;
  - ❌ **违宪** — 与宪法条款冲突,须先修订或废除冲突条款方可生效;
  - 🚫 **禁止** — 触及根本原则(如未经审查令法律生效、绕过评审),绝对不可为。
- **第12条 生效** — 法律经宪法审查取得 ✅ 或经确认的 ⚠️ 后,方可生效执行;取得 ❌ / 🚫 者须先行修订。

## 第四章 法律的执行(检查代码)

- **第13条 执行触发** — 下列情形须执行相关法律检查代码:①代码提交 / 合并前;②编译器 / 运行时 / 工具链变更后;③宪法或法律修订后;④定期合规审计。
- **第14条 执行步骤** —
  1. **选定法律** — 依变更范围确定适用的法律条文(细则法 / 契约法),并回溯其对应的宪法铁律;
  2. **对照检查** — 依第8条合规判据,逐条检查代码(源码 / 构建产物 / 运行时输出),收集证据(文件 / 函数 / 行号);
  3. **记录结论** — 产出合规矩阵,每条给 ✅ / ⚠️ / ❌ 评级并附证据;
  4. **生成评审意见** — 汇总为四层评审意见(✅ 合规 / ⚠️ 警示 / ❌ 违宪 / 🚫 禁止);
  5. **设计建议(新增关键字 / 语法时)** — 当执行范围涉及**新增关键字、新增语法或修改既有关键字 / 语法形态**(落入第19条适用场景)时,除合规检查外,须主动基于第19条四项设计取向(输入最小化 / Token 经济性 / 一致性降噪 / 可追溯兜底),**参考当前知名编程语言的既有实践**(如 Rust 的 `fn` / `->` / 模式匹配、Go 的极简关键字集、Kotlin 的 `when`、Swift 的 `guard`、Zig 的显式 `defer`、Python 的缩进即结构、TypeScript 的类型推导等),对照评估用户提案,并**提出更合理的替代建议**——每条建议附理由:可输入字符数 / 预估 token 数 / 与既有构造一致性 / 与宪法铁律契合度。建议属第19条非强制层级,用户可采纳或驳回,不阻断合规流程;
  6. **处置违例** — 依第15条处置;
  7. **归档** — 检查报告、评审意见与设计建议一并记入项目记忆 / 审计记录,供后续追溯。
- **第15条 违例处置** —
  - ✅ 通过 — 准予合并 / 发布;
  - ⚠️ 警示 — 经用户确认后放行或修订;
  - ❌ 违宪 / 不合规 — 阻断合并 / 发布,须修订至合规;
  - 🚫 禁止 — 立即中止流程并上报用户。
- **第16条 语法规则起草工作流** — 语法规则(词法 / 句法产生式等)依 L-15 语法规则法起草:先建草稿文件(`docs/syntax/drafts/`)→ 经法律验证(四层评审)→ 用户令生效 → 并入 `docs/reference.md` → 原草稿标记失效。本总则第四章执行步骤适用于语法规则的合规检查;当用户**提出新增 / 修改关键字或语法**时,须先行联动第14条(5)设计建议步骤,依第19条取向与知名语言实践提出优化建议,再进入草稿与法律验证。

## 第五章 附则

- **第17条 本总则自身适用** — 本总则亦为法律,其制定 / 审查 / 生效依第三、四章执行;其执行步骤(第四章)适用于对本总则自身的合规审计。
- **第18条 解释与冲突** — 宪法条款优先;本总则与宪法冲突时以宪法为准。本总则与后续细则法 / 契约法冲突时,依第2条(特别法优于一般法)裁决。
- **第19条 非强制性设计建议(开发者友好 · 智能体友好)** — 〔本条为**非强制性建议**,不构成第6条所指"可执行约束",仅供制定细则法 / 语法规则 / 新增关键字时参考;是否采纳由制定者裁量,不进入合规判据。〕在引入新关键字或设计新语法时,应本着**开发者友好**与**智能体友好**两项原则,降低双方输入与生成成本:
  - **(a) 输入最小化** — 优先采用最短且仍无歧义的关键字与符号(如 `fn` 优于 `function`、`->` 优于 `returns`);避免冗余定界符(如声明绑定符 `::` 在无歧义处可省略)。
  - **(b) Token 经济性** — 语法形态应使智能体常见生成结果更紧凑、消费更少 token;高频构造尤须精简,低频 / 罕见构造允许较长形式以保可读性。
  - **(c) 一致性降噪** — 同类构造采用统一形态(呼应宪法"唯一确定语义"与 L-04),减少人类误写与智能体生成非法语法的可能;正交的关键字(一词一义)优于重载关键字,更易被智能体稳定生成。
  - **(d) 可追溯兜底** — 即便采用简写,仍须能在 `docs/reference.md` 与编译器诊断中无歧义还原其语义,不得为精简牺牲"全行为显式可追溯"铁律(宪法第一章第3条)。
  - **释义** — 本条与宪法六目标中"AI Agent 友好""AI 稳定生成"一致;近期 `func → fn` 关键字精简、声明 `::` 绑定符移除即本条原则的实践样例。属**建议**层级:当精简与可读性 / 显式性 / 其他宪法铁律冲突时,以宪法铁律为准,本条让位。
